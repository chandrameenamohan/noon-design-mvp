The map: what a job is promised here, and who keeps the promise

Epic 3 made a job a row: the jobs table is the run, the preview and the ship, and the queue only tells a worker to look (SPEC §2.9). Epics 4 to 8 built on that without asking what happens when the parts around the row misbehave: a browser that presses twice, a worker that dies with a job half done, a Redis that is flushed, a page reloaded mid-run, a tenant that asks for more than its share. Epic 9 asks those five questions and answers each one from the same place, the row in Postgres. A press is one job (F27): a retry with the same Idempotency-Key is answered with the job the first press made, however many arrive at once, because the key is claimed with the row's primary key before the job exists. A dead worker's job runs again, once (F28): a running job heartbeats its row every second, a sweep puts a silent one back in the queue, and the attempt number fences a worker that was only slow. Losing Redis loses nothing (F28, §4): the sweep rebuilds the queue from whatever Postgres still calls queued, and no code changed to make that true, only the proof was missing. Progress is a column (F30): the run's steps ride the row, written by the attempt that holds it, read by whoever asks. Limits are counted where the work is (F31): one upsert in the run's own transaction for AI runs, and the same upsert for every HTTP route, so every api instance shares the count and nothing fails open.

Four ideas carry the epic, and they are what an interviewer will press on. Exactly-once is a property of the whole, never of a delivery (sections 1 and 3): messages arrive at least once or at most once, never exactly once, so "once" is manufactured by an idempotent receiver: a key claimed by a primary key, an op id the room has already answered, a node the retry finds already there. The industry word is effectively once. A heartbeat is not a lease (section 2): lesson 7's lease said "I may write until this time"; a heartbeat only says "I was alive a second ago", and the decision to give the job away is made by whoever reads it, so a slow worker that was given up on must be fenced by something the write itself checks, the attempt number. Postgres is the truth and Redis is a cache (sections 4 and 6): a queue message is a hint that a row exists, a lease is a hint that a room is owned, and a counter that must be shared and must not fail open lives beside the rows it protects. Who is asking is a trust decision (section 7): an address in a header is written by whoever sent the header, and only the hop you trust can vouch for the one before it.

1 · Idempotency keys: the claim is the row, and the answer is the job as it now is

A browser presses "Ask the AI", the request leaves, and the answer never comes back: a proxy timed out, the tab lost its network, the api returned a 502 while restarting. The person presses again. Without a key, two runs exist (or one 409 and a confused person); with one, the retry is the same request and gets the same answer. Stripe's version of this is the model: the client mints a key per operation, the server stores what it did under the key for 24 hours, and a replay returns the stored result. The design question is where the key lives and how two requests carrying it at the same moment are told apart, because a retry is often a duplicate on the wire rather than a person's second press, and both arrive within milliseconds.

From packages/db/migrations/0018_idempotency_keys.sql

-- E9.1 (F27): "start AI run" and "ship" may be retried. The client sends an Idempotency-Key with the press; a retry
-- with the same key is answered with the job the first one made (or joined), never a second job. The PRIMARY KEY is
-- the check, not a look-then-insert: of two requests at the same moment, the second waits on the first's row and
-- then reads it. Scoped to (org, user): a key can only ever name a job of the caller's own org, made by the caller.
-- `request` is what was asked (queue, document, input): the same key with a different request is refused (422).
-- A key lives 24 hours (as Stripe's do): each claim first forgets that user's older keys, so a key may be used again
-- after that. It also goes with its job, its user and its org.
create table idempotency_keys (
  org_id     uuid not null references orgs (id) on delete cascade,
  user_id    uuid not null references users (id) on delete cascade,
  key        text not null check (key ~ '^[!-~]{1,255}$'),
  request    jsonb not null,
  -- Null only inside the claiming transaction (the key is claimed BEFORE the job is made); never seen committed.
  job_id     uuid references jobs (id) on delete cascade,
  created_at timestamptz not null default now(),
  primary key (org_id, user_id, key)
);
-- Back the cascades from jobs and users.
create index idempotency_keys_job on idempotency_keys (job_id);
create index idempotency_keys_user on idempotency_keys (user_id);

Read the primary key first: (org_id, user_id, key). The key belongs to a user in an org, so a key from one tenant can never resolve to another tenant's job, and the same string from two users is two keys (the test "a key belongs to its user in its org" makes bob use ann's key and asks for his own job, then makes him use it on her document and asks 404). The request column stores what was asked: the queue, the document, the input. That is what lets the same key with a different instruction be refused as 422 idempotency_key_reused rather than silently answered with the wrong job, which is what Stripe does too (an idempotency_error when the parameters differ). job_id is nullable, and the comment says why: the key is claimed before the job exists, inside the transaction that will make it, and nobody outside that transaction ever sees the null.

From apps/api/src/app.ts

/** F27: the request's `Idempotency-Key`, if it sent one. A malformed one is refused, never ignored: the retry it was meant to make safe would not be. */
function idempotencyKey(c: Context): string | undefined {
  const key = c.req.header("idempotency-key");
  if (key === undefined) return undefined;
  if (IdempotencyKey.safeParse(key).success) return key;
  throw new HTTPException(400, { res: fail(c, 400, "invalid_body", [{ field: "idempotency-key", message: "1 to 255 printable ASCII characters" }]) });
}

A malformed key is a 400, never ignored. The tempting shape is "if the key does not parse, proceed without one", and it is wrong for the same reason a malformed cookie is not "nobody": the retry the key was meant to make safe would then make a second job, and the client would believe it was protected. Refusing is the honest answer.

From packages/db/src/index.ts

      /**
       * F27: `make` runs in a transaction that first claims (this user, `key`) in this org. A second request with the key
       * waits on that row, then is answered with the job the first one made: `{ replay }` (its id), never a second job.
       * "key_reused": the key was claimed for a different request. When `make` made no job (busy, no such document) the
       * claim is rolled back, and the retry that follows is free to use the key. Keys live 24 hours (migration 0018).
       */
      const withKey = async <T>(userId: string, key: string, request: object, make: (via: PoolClient) => Promise<T>, jobOf: (made: T) => string | undefined): Promise<{ made: T } | { replay: string } | "key_reused"> => {
        const params = [orgId, userId, IdempotencyKey.parse(key), JSON.stringify(request)];
        const client = await pool.connect();
        let broken: Error | undefined;
        try {
          await client.query("begin");
          await client.query("delete from idempotency_keys where org_id = $1 and user_id = $2 and created_at < now() - interval '24 hours'", params.slice(0, 2));
          if ((await client.query("insert into idempotency_keys (org_id, user_id, key, request) values ($1, $2, $3, $4) on conflict do nothing", params)).rowCount !== 1) {
            // A statement of its own, so it sees the winner's row, committed while the insert waited on it (read committed).
            const found = await one(z.object({ same: z.boolean(), job_id: z.string() }), "select request = $4::jsonb as same, job_id from idempotency_keys where org_id = $1 and user_id = $2 and key = $3", params, client);
            await client.query("commit");
            if (!found) throw new Error("idempotency key held by nobody");
            return found.same ? { replay: found.job_id } : "key_reused";
          }
          const made = await make(client);
          const jobId = jobOf(made);
          if (jobId === undefined) {
            await client.query("rollback");
            return { made };
          }
          await client.query("update idempotency_keys set job_id = $5 where org_id = $1 and user_id = $2 and key = $3", [...params, jobId]);
          await client.query("commit");
          return { made };
        } catch (err) {
          await client.query("rollback").catch(() => undefined);
          broken = err instanceof Error ? err : new Error(String(err));
          throw err;
        } finally {
          client.release(broken);
        }
      };

This is the section's centre, and the drill plants its bug. withKey opens a transaction, sweeps this user's keys older than 24 hours (a ponytail named in the migration: rows of users who never return stay until they do), and then claims the key with insert ... on conflict do nothing. Under READ COMMITTED, a second transaction inserting the same primary key does not fail at once: it blocks on the first transaction's row until it commits or rolls back, then sees either a conflict (the winner committed) or a free key (the winner rolled back). That blocking is the whole mechanism. Twenty requests arrive together; one inserts and goes on to make the job; nineteen wait inside their insert; when the winner commits, each of the nineteen gets rowCount 0, reads the winner's row in a statement of its own (the comment says why: a statement started before the winner committed would not see it), and answers with the winner's job id. No lock was named, no retry loop written; the primary key did it.

Then the two branches that make the key safe as well as unique. If make made no job (the document was busy, or gone), the transaction rolls back, and the claim with it: the key was never used, and the retry that follows the 409 may use it to start the next run. If it did, the job id is recorded on the key and both commit together, so a crash between "job made" and "key recorded" cannot leave a job without its key (and a replay would then make a second one). The client.release(broken) at the end is pg's way of throwing a connection away rather than returning a possibly poisoned one to the pool.

"As its row now is" is the sentence to remember. A replay is answered by select * from jobs where id = $replay, never from the queue's add() and never from a cached copy of the first response: the first test claims the run after making it and asserts the replay says running. Stripe stores the original response bytes; this repo stores the job's id and reads the job, because the job is the truth and the person retrying wants to know where it is now. The ship route does the same with 200 rather than 201, because a ship press may have joined a waiting ship rather than made one, and the key keeps naming the ship it pressed even after newer ships are queued behind it.

From apps/web/src/api.ts

/**
 * F27: a POST that makes a job. One press, one Idempotency-Key: when the answer is lost or is a 5xx, the retry sends
 * the same key and the api answers with the job the first attempt made, never a second one. A refusal is not retried,
 * and neither is a rate limit (F31): the same request a moment later is refused again.
 */
async function postJob<S extends z.ZodType>(path: string, schema: S, body?: unknown): Promise<z.infer<S>> {
  const key = { "idempotency-key": crypto.randomUUID() };
  try {
    return await post(path, schema, body, key);
  } catch (problem) {
    if (problem instanceof Refused || problem instanceof Limited) throw problem;
    return post(path, schema, body, key);
  }
}

The client's half is short on purpose. One press mints one crypto.randomUUID(); a lost answer or a 5xx is retried once with the same key; a 4xx is not retried (the same request a moment later is refused again), and neither is a 429 (section 6). A retry loop with backoff is the upgrade; one retry is what makes the common case, a dropped connection, invisible to the person.

The key as columns on the jobs row was rejected.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

A refused run rolls its claim back rather than recording the refusal.

Stripe records every outcome under the key, including errors, so a retry of a failed request gets the same failure. That is right for a payment (the client must not be charged on a retry of a declined card) and wrong for a busy document: the person who got a 409 waits for the run to end and presses again with a retry of the same request, and a recorded refusal would answer 409 for 24 hours. So a make that made nothing rolls the whole transaction back, and the key is as if never sent.

The principle: a delivery is never exactly once, so make the effect idempotent and let the delivery repeat. The key is claimed by the database's own uniqueness, in the same transaction as the work, before the work exists, so that two claims at one moment are serialised by a row lock nobody had to name. The replay reads the truth, not a memory of the first answer. And a claim that produced nothing is undone, so the key protects the retry it was sent for and nothing else.

2 · Heartbeats, the stale sweep, and the attempt as a fence

kill -9 says nothing. A worker that is killed, or whose host is lost, or that the OOM killer takes, leaves its job's row saying running, and E3 built one unfinished run per document on that row: the document's next run is refused for ever, a sandbox job left running blocks the preview and keeps its container from the reaper (the E4.2b finding), a ship never ends. BullMQ has a stalled-job checker for this, and it was rejected in one sentence: Redis is not the truth, and a message can be dropped. So the job's own row says whether its worker is alive, and Postgres decides what to do about a silent one.

      async requeueStale(staleMs, maxAttempts) {
        // ONE statement, `skip locked`: every worker process sweeps, and two sweeps never both take a row.
        // coalesce(heartbeat_at, started_at): a row left running by a worker from before heartbeats (0019) is stale too.
        // `distinct on`: of the ships of one document that went silent together, only the newest may wait again
        // (0011: one waiting ship per document); it reads the document afresh, so it ships what they would have.
        // A job someone asked to stop is not run again: it ends as `cancelled` (F10), as its worker would have ended it.
        // A sandbox's address dies with its worker (the next attempt reports one); a ship's commit stays, as the git
        // peer asks it "did Ship push this?" (E5.5), and the push may still be on its way. An AI run's steps are the
        // dead attempt's (F30): the next attempt starts its list afresh, so a reload never shows steps nobody is taking.
        const counted = await one(
          z.object({ requeued: z.number().int(), lost: z.number().int() }),
          `with stale as (
             select id, queue, document_id, attempts, created_at, cancel_requested_at is not null as cancel from jobs
             where status = 'running' and coalesce(heartbeat_at, started_at) < now() - make_interval(secs => $1::float8 / 1000)
             for update skip locked),
           again as (
             select distinct on (case when queue = 'ship' then document_id else id end) id from stale s
             where not cancel and attempts < $2 and not (queue = 'ship' and exists (select 1 from jobs w where w.queue = 'ship' and w.status = 'queued' and w.document_id = s.document_id))
             order by case when queue = 'ship' then document_id else id end, created_at desc),
           requeued as (
             update jobs set status = 'queued', started_at = null, heartbeat_at = null, output = case when queue in ('sandbox', 'ai') then null else output end
             where id in (select id from again) returning 1),
           lost as (
             update jobs set status = case when stale.cancel then 'cancelled' else 'failed' end, error = case when stale.cancel then null else 'worker_lost' end, finished_at = now()
             from stale where jobs.id = stale.id and stale.id not in (select id from again) returning 1)
           select (select count(*) from requeued)::int as requeued, (select count(*) from lost)::int as lost`,
          [staleMs, maxAttempts],
        );
        return counted ?? { requeued: 0, lost: 0 };
      },

A job someone asked to cancel is not run again: it ends cancelled, as its worker would have ended it.       if (stale.requeued + stale.lost > 0) log("warn", "jobs left running by a dead worker", stale);

      for (const ref of await jobs.queued(100)) await producer.enqueue(ref).catch((err: unknown) => log("warn", `offer failed: ${describeError(err)}`, { jobId: ref.jobId }));

Case study · found by review, by a learning test, or by a test that was written to refute a claim

BullMQ's stalled-job retries were rejected.

BullMQ can notice a worker that stopped renewing its lock and re-deliver the message. It lives in Redis, which section 4 wipes on purpose, and it knows nothing about the row: a re-delivered message for a job the row still calls running would be refused by claim() anyway. Putting the heartbeat on the row makes the row self-sufficient, and makes the stalled check the same statement on every worker.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

The fence exists because of a worker that was only slow.

The first version had the heartbeat and the sweep and no attempt number: a job silent past 15 s was requeued, and the dead worker was assumed dead. A test then held a worker's handler open, bumped the row to attempt 2 by hand as the sweep and another claim would, and released it: the slow worker's finish("succeeded") landed on the row attempt 2 was running, and the second worker's later finish then updated nothing because the status was no longer running. Naming the attempt in every write, and telling the slow worker lost on its next beat, made both writes land where they should: nowhere and on the row respectively.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

The sweep's ship clause was found by 0011, not by design.

Requeueing every stale ship would have inserted two queued ships for one document when two had gone silent together, and the partial unique index from E5 (one waiting ship per document) would have failed the whole sweep statement, for every queue. The distinct on picks the newest, the older one fails as worker_lost, and a running ship whose document already has a ship waiting fails too, because the waiting one will ship everything. Each of those cases is one line of the heartbeat test.

The principle: a retry system has three parts and most have two. Detection: something says the worker is gone (a heartbeat read by a sweep). Redelivery: the work is offered again (the row back to queued, and a bound on how often). Fencing: the write path refuses the worker that was wrongly given up on (the attempt in every update ... where). Without the third, every false positive of the first is a duplicate, and the first has false positives by construction, because a timeout cannot tell slow from dead.

3 · Replaying a dead attempt without a duplicate: ids that are functions of the step

Attempt 2 of an AI run starts its conversation with the model over, because the run's transcript is not stored (SPEC §6). The model, given the same instruction and the same document, will usually do the same first steps again, and each of them is an add_node the dead attempt already sent to the room. Without care the document ends with every early node twice. The tempting fix, "let the retry read the document and skip what is there", asks the model to be idempotent, which no model is. The repo's answer is to make the ids idempotent instead: the n-th node id and the n-th op id of a job are functions of the job and the step, the same on every attempt, so a replayed add_node either finds its node already there or is refused by the room as a duplicate op the room already answered.

From apps/worker/src/ai.ts

/**
 * The ids a run mints, the same on every attempt of its job (F28): the n-th node is always the same id, and the n-th
 * op the same opId when it is the same op. A retry after a crash replays the dead attempt's steps first; a node it
 * finds already there is that step done, and an op the room journaled already gets its original answer (the
 * journal's key is (sender, opId)), so the document never holds anything twice. The op's content is in its id: a
 * model that does something ELSE at step n on the retry sends a new op, never one the room would take for the old.
 */
export function replayIds(jobId: string): { opId: (op: Op) => string; nodeId: () => string } {
  let ops = 0;
  let nodes = 0;
  const digest = (text: string): string => createHash("sha256").update(text).digest("hex");
  return {
    // Shaped as a version-8 (custom) UUID, which the contract's z.uuid() accepts.
    opId: (op) => {
      const h = digest(`${jobId}:op:${String(ops++)}:${JSON.stringify(op)}`);
      return `${h.slice(0, 8)}-${h.slice(8, 12)}-8${h.slice(13, 16)}-${((parseInt(h.slice(16, 17), 16) & 0x3) | 0x8).toString(16)}${h.slice(17, 20)}-${h.slice(20, 32)}`;
    },
    nodeId: () => `n_${digest(`${jobId}:node:${String(nodes++)}`).slice(0, 12)}`,
  };
}

Read the op id's input: jobId:op:n:JSON.stringify(op). The content of the op is in its id, on purpose, and the commit's reasoning is worth keeping whole: with (job, n) alone, a model that does something else at step n on the retry would send a different op under an id the room already journaled, the room would answer with the old op's seq (E6.1's dedupe answers a known (sender, opId) from the journal), the replica would never match that answer to its op, and it would resend for ever. Putting the op's bytes into the hash makes "a different op at the same step" a different id: a new op, refused or accepted on its own merits. The id is shaped as a version-8 UUID because the contract says z.uuid() and the room's dedupe key is that string.

4 · Redis is a cache: the wipe, and why no code changed

E9.2b is the epic's shortest bead and its most instructive: no production code changes. SPEC §4 asks that a Redis lost (flushed or restarted with no persistence) loses no job and no room, and the answer had been built piece by piece since epic 3. What was missing was the proof, and the proof is a chaos script with two rounds and a pure judge. Read the list of what already made it true, because each item is a place where an earlier epic chose Postgres over Redis for the truth.

Jobs. The worker's sweep (E3.1) re-offers every row Postgres still calls queued, every five seconds in compose; jobId as the BullMQ id plus claim() make a second offer harmless. A running job heartbeats Postgres, not Redis, so the wipe never notices it; BullMQ loses the job's lock and cannot record its end, which it logs, and Postgres records it, which is what counts. Rooms. After a wipe the owner's compare-and-renew finds no key and gives the room up at once (4409 to its peers), the next acquire takes the token floor from the journal's fence (E7.3), so the token keeps rising and no second owner can write, and the routing heartbeats come back within a tenth of a ttl. Roles. The E8.2 pub/sub subscriber re-reads every role ("all") on reconnect, and a FLUSHALL keeps subscriptions alive anyway.

// What chaos:redis-wipe-rebuild (E9.2b, SPEC §4 "Redis lost") judges, as pure checks: Redis is wiped while AI runs
// are running and others are waiting in it, and while a room is open. Postgres is the truth, so afterwards:
//   - every run succeeded, claimed ONCE (a wipe must not start a job twice), each of its steps journaled once, the
//     document's seqs 1..n without a gap;
//   - the room has one owner again: a lease with a token above the one before the wipe, and the journal's fence
//     (Postgres) naming that same token, so no second node holds a claim it could still write under.
// Vacuity guards (SPEC §4a): no job waiting in Redis at the wipe, or none running, proved nothing, and says so.

/** One run after the wipe: its row, and its document's journal counted (its own ops, and the room's seqs). */
export type RunAfter = { id: string; status: string; attempts: number; ops: number; opIds: number; nodes: number; seqs: number; maxSeq: number };
export type Holder = { token: number; node: string };

export function runViolations({ steps, runs, waitingAtWipe, runningAtWipe }: { steps: ReadonlyMap<string, number>; runs: readonly RunAfter[]; waitingAtWipe: number; runningAtWipe: number }): string[] {
  const violations: string[] = [];
  if (waitingAtWipe === 0) violations.push("vacuous: no job was waiting in Redis at the wipe, so no queue had to be rebuilt");
  if (runningAtWipe === 0) violations.push("vacuous: no job was running at the wipe");
  for (const [id, want] of steps) {
    const run = runs.find((r) => r.id === id);
    if (!run) {
      violations.push(`run ${id} has no row`);
      continue;
    }
    if (run.status !== "succeeded") violations.push(`run ${id} ended ${run.status}, not succeeded`);
    if (run.attempts !== 1) violations.push(`run ${id} was claimed ${String(run.attempts)} times: the wipe started it again`);
    if (run.ops !== want || run.opIds !== want || run.nodes !== want) violations.push(`run ${id} journaled ops=${String(run.ops)} opIds=${String(run.opIds)} nodes=${String(run.nodes)}, not ${String(want)} of each`);
    if (run.seqs !== run.maxSeq) violations.push(`run ${id}'s document has ${String(run.seqs)} distinct seqs up to ${String(run.maxSeq)}: a gap or a repeat`);
  }
  return violations;
}

 * F30: one tool call as the panel shows it. The subject is the MODEL's own argument, so it is untrusted text: only a

export function stepOf(tool: string, args: unknown, ok: boolean): RunStep {

export function withProgress(tools: AgentTool[], onSteps: (steps: RunStep[]) => void): AgentTool[] {
  const steps: RunStep[] = [];

    ...t,
    run: async (args) => {
      const result = await t.run(args);
      steps.push(stepOf(t.name, args, result.ok));
      if (steps.length > MAX_RUN_STEPS) steps.shift();
      onSteps([...steps]);
      return result;
    },
  }));
}

6 · Rate limits in Postgres: one upsert, inside the transaction, with the database's clock

An org that starts too many AI runs costs money and holds worker slots; F31 asks for a per-org limit with a 429 that says exactly how long to wait. The first design question is where to count, and the answer decides everything else. A counter in each api process lets N instances allow N times the limit. Redis INCR with EXPIRE is shared, and it was rejected for two reasons the commit names: it is a second store that can fail on its own, so the code must pick between failing open and failing closed when Redis is away; and it cannot join the run's transaction, so a run that was refused as busy, or rolled back, or replayed, would have been charged, and the code would need a compensating decrement. Counting in Postgres, in the same transaction as the run, makes the count exactly the runs that exist.

From packages/db/src/limit.ts

import { z } from "zod";

/**
 * E9.5 (F31): a rate limit is `limit` hits per key in each fixed window of `windowSeconds`, counted in Postgres (the
 * rate_limits table, migration 0020) so every api instance shares one count. Reused by E9.6 (per user, per address,
 * session minting) through `Db.take`. ponytail: fixed windows, so a key may spend `limit` at the end of one window and
 * `limit` again at the start of the next (twice the rate for a moment); upgrade: a sliding window (two counters,
 * weighted) if that burst ever matters.
 */
export const Rule = z.strictObject({ limit: z.number().int().min(1), windowSeconds: z.number().int().min(1).max(86_400) });
export type Rule = z.infer<typeof Rule>;
export type Verdict = { ok: true } | { ok: false; retryAfterSeconds: number };

/**
 * `hits`: this key's count in `window` (the window's index since the epoch), this hit included; `now`: the DATABASE's
 * clock in seconds, so api instances whose clocks disagree still give one answer. Over the limit, the wait is until the
 * window ends, rounded up (a client that waits exactly that long is let in), and never under one second.
 */
export function verdict({ hits, window, now }: { hits: number; window: number; now: number }, rule: Rule): Verdict {
  if (hits <= rule.limit) return { ok: true };
  return { ok: false, retryAfterSeconds: Math.max(1, Math.ceil((window + 1) * rule.windowSeconds - now)) };
}

A fixed window: time is cut into windows of windowSeconds, numbered since the epoch, and a key may be hit limit times per window. verdict is pure and takes the database's clock as now, so two api instances whose clocks disagree still give one answer, and the wait is until the window ends, rounded up and never under one second: a client that waits exactly what it is told must be let in, and a "retry in 0 seconds" is a lie. The unit test pins the rounding at the boundary.

The header you may not believe. X-Forwarded-For is a comma-separated list, and the rule is that each proxy appends the address it saw the request come from. So the rightmost entry was written by the last proxy, the one before it by the proxy before, and the leftmost by whoever started the chain, which may be the client, who may write anything. The classic bug reads the leftmost entry as the client ("the original IP"): every guesser then picks a fresh address per request and the per-address limit counts nothing. The correct read is from the right: skip every entry that is itself a proxy you trust, and the first entry that is not is the client, vouched for by a trusted hop. And the whole header is believed only when the TCP peer itself is a trusted proxy; from anyone else it is ignored, because anyone can send one.

/** `spec`: comma-separated "loopback", "private", addresses and CIDRs. Anything else throws: a typo must not trust the world, or no one. */
export function trustedProxies(spec: string): Trusted {
  const list = new BlockList();
  for (const entry of spec.split(",").map((each) => each.trim()).filter((each) => each !== "")) {
    const named = NAMED[entry];
    if (named) {
      for (const [net, prefix] of named) list.addSubnet(net, prefix, family(net));
      continue;
    }
    const [net = "", prefix, extra] = entry.split("/");
    const bits = isIP(net) === 6 ? 128 : 32;
    if (isIP(net) === 0 || extra !== undefined || (prefix !== undefined && !(/^\d{1,3}$/.test(prefix) && Number(prefix) <= bits))) {
      throw new Error(`not an address, a CIDR, "loopback" or "private": ${entry}`);
    }
    if (prefix === undefined) list.addAddress(net, family(net));
    else list.addSubnet(net, Number(prefix), family(net));
  }
  return (address) => {
    const plain = unmap(address);
    return isIP(plain) !== 0 && list.check(plain, family(plain));
  };
}

From apps/api/src/client-address.ts

/** The client's address (see above), or undefined when there is no socket to ask (a request made in-process, in tests). */
export function clientAddress(peer: string | undefined, forwardedFor: string | undefined, trusted: Trusted): string | undefined {
  if (peer === undefined) return undefined;
  let client = unmap(peer);
  if (!trusted(client) || forwardedFor === undefined) return client;
  const hops = forwardedFor.split(",");
  for (let i = hops.length - 1; i >= 0; i--) {
    const hop = unmap((hops[i] ?? "").trim());
    // Not an address: stop at the last one a trusted hop vouched for (a garbled header costs its sender, not others).
    if (isIP(hop) === 0) return client;
    client = hop;
    if (!trusted(hop)) return hop;
  }
  return client; // every hop a trusted proxy: the furthest one
}

Two more decisions in the code. unmap turns ::ffff:127.0.0.1, an IPv4 client on a dual-stack socket, into 127.0.0.1, so one client is one key and the loopback check works whichever family the socket reported. And a garbled entry (1.2.3.4:80, a word) stops the walk and charges the last address a trusted hop vouched for: a client who sends nonsense costs themselves, never someone else. trustedProxies refuses a spec it does not understand rather than trusting nobody or everybody: a typo in TRUST_PROXY must not start the api.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

The probes exempted after asking what an orchestrator does with a 429.

A liveness probe that is refused is a container that is restarted; a readiness probe that is refused is a pod taken out of the load balancer. A limit that can do either under load makes the outage it was meant to prevent. The webhook is exempt for a different reason: its gate is the HMAC, and a limited delivery only delays the reconcile.

The principle: a rate limit is only as good as the identity it counts. Count the user when you know one; when you do not, count an address you can actually attribute, which means the TCP peer or an X-Forwarded-For entry a proxy you configured has vouched for, read from the right. And exempt the two callers whose refusal would hurt you more than their traffic: the probes and the signed webhook.

The idempotency key is claimed with insert ... on conflict do nothing inside the transaction that makes the job, before the job exists; a replay is answered by reading the job's row; a run that was refused as busy rolls the claim back. Defend each against the obvious alternative (a look-then-insert, storing the first response, recording the refusal), and say what Postgres does to the second of two claims at the same moment.

A look-then-insert has an await between the look and the insert, and twenty requests that arrive together all look before any inserts: each finds nothing and each makes a job; the unique constraint then fails nineteen of them and the code must catch the error and read again, which is the same statement the design starts from, written the long way. With on conflict do nothing the claim and the check are one statement, and the second transaction to insert the same primary key blocks on the first's uncommitted row until it commits or rolls back: if it committed, the loser gets rowCount 0, reads the winner's row in a statement of its own (a statement started earlier would not see the commit) and answers with the winner's job; if it rolled back, the key is free and the loser becomes the winner. Storing the first response, as Stripe does, would answer queued to a retry of a run that is now running; the person retrying wants to know where the job is, and the job's row is the truth, so the replay reads it. Recording a refusal under the key is right for a declined payment and wrong for a busy document: the person who got the 409 waits and presses again with the same request, and a recorded 409 would answer 409 for 24 hours; rolling the claim back with the refused run makes the key as if never sent, so the retry after the busy run ends may use it. Scoping the key to (org, user) keeps a key from ever resolving to another tenant's job, and storing the request lets the same key with another instruction be refused as 422 rather than silently answered with the wrong job.

2. A running job heartbeats its row every second; a sweep requeues one silent for 15 s; every write of an attempt carries and attempts = $n. Why is a heartbeat not a lease, why does the sweep need the fence, and what does a worker that was only slow experience?

A lease (lesson 7) is a promise with a deadline: the holder knows until when it may act, renews before then, and gives up on its own clock; it is the right tool where the holder must act alone for a while, like a room ordering ops. A heartbeat is a report with no promise: the worker says "alive a second ago" and has no idea whether anyone still believes it; the decision to give the job away is made by whoever reads the row. That is enough where the work can be handed to someone else and the only harm of a wrong guess is a duplicate, provided the duplicate is made harmless, which is the fence's job. The sweep needs it because a timeout cannot tell slow from dead: a 20-second GC pause, a blocked event loop or a partition from Postgres looks exactly like kill -9 for 15 seconds, and the sweep will requeue a job whose worker is about to wake. Without the fence, that worker's finish("succeeded") lands on the row attempt 2 is running, and attempt 2's own finish later updates nothing because the status is no longer running. With it, the slow worker's next beat returns no row, the store reads that as lost, the worker aborts its handler with a warning, and its finish, its beats and its progress reports all match zero rows: they land nowhere. The sweep itself is one statement with for update skip locked so every worker process may run it and two never take the same row, coalesce(heartbeat_at, started_at) so rows from before the migration are judged too, and a bound of three claims so a job that kills its worker every time still ends, as worker_lost.

3. The AI run limit is one upsert on a rate_limits row, taken inside the run's transaction before the insert, with Retry-After computed from clock_timestamp(); Redis INCR was rejected. Why each, and what does a fixed window get wrong that a token bucket gets right?

Counting in Postgres makes the count shared across every api instance (a counter per process allows N times the limit) without a second store: with Redis, the code must decide what to do when Redis is away, and both answers are bad under load (open: every org unlimited exactly when the system is struggling; closed: no runs with Postgres healthy). Inside the run's transaction, before the insert, makes the count exactly the runs that exist: a busy document, a vanished one, a replayed key and a refused run are all rolled back with their hit, so nothing needs a compensating decrement, and a refused request's idempotency claim rolls back too, so the retry after Retry-After may reuse the key. The upsert is atomic per row, so two hits at one moment take turns, and greatest(win) keeps a hit that computed its window before a boundary but reached the row after one computed past it from moving the row back and resetting the count. clock_timestamp() rather than now() because now() is the transaction's start and this is several statements in, and the database's clock rather than the api's so two instances with drifting clocks give one wait; the wait is rounded up and never under one second so a client that waits exactly what it was told is let in. A fixed window lets a key spend its whole limit in the last second of one window and again in the first of the next, twice the rate for a moment; a token bucket refills at a steady rate and allows a burst only up to the bucket's size, which is the shape most public APIs want, and it costs two columns (level, last refill) and a little arithmetic in the same upsert. For sixty AI runs an hour the boundary burst is a nuisance and not a cost, so the fixed window stayed and the ponytail is named where it lives.

Recall first

Look away. Name the three parts of a retry system and what this epic uses for each. Then say which X-Forwarded-For entry is the client and under what condition the header is read at all. Then check.

Check yourself

Detection: a 1 s heartbeat on the row, read by a sweep that calls 15 s of silence stale. Redelivery: the row back to queued, offered again in the same sweep, at most three claims, then worker_lost. Fencing: the attempt number in every write's where, so a worker wrongly given up on writes nothing and learns lost on its next beat. The client is the rightmost entry that is not itself a trusted proxy, walking from the right and skipping trusted hops; and the header is read only when the TCP peer is a trusted proxy (TRUST_PROXY: loopback on the host, loopback and private in compose), otherwise the peer is the client and the header is ignored.

Then test it

Eight questions. Options are shuffled each visit.

1. Twenty requests carrying the same Idempotency-Key arrive within a millisecond. What happens?

No lock is named: the primary key does it. The test asserts twenty 201s, one row in jobs, one id in every answer.

2. The same key arrives with a different instruction. And a request refused as busy: what does its key do?

Stripe records refusals because a declined card must stay declined on retry; a busy document is a wait, not a verdict.

3. A worker's event loop blocks for 20 seconds mid-job. The sweep has requeued the job and another worker is running it as attempt 2. The first worker wakes and calls finish("succeeded"). What happens?

A timeout cannot tell slow from dead, so every false positive would be a duplicate without the fence; the test bumps attempts by hand under an open handler and watches the finish land nowhere.

4. Why does the AI run's op id hash the op's content, not only (job, step)?

Two runs never collide anyway: the job id is in the hash. The content makes "the same step, a different action" a different op.

5. Redis is flushed while three runs wait in bull:ai:wait and four are running. What brings the three back, and what happens to the four?

No production code changed for this bead; the chaos judge asks for attempts = 1 on every run and refuses a round that wiped an empty queue.

6. A slow dead attempt reports its steps after attempt 2 has started. What does the panel show?

The integration test reports from attempt 1 after the requeue and after attempt 2's claim, and asserts an empty list both times.

7. Why is the AI run limit counted in Postgres inside the run's transaction rather than with Redis INCR + EXPIRE?

The flush is true too, but incidental: the deciding questions are "what when the store is away" and "how is a refused run uncounted".

8. X-Forwarded-For: 10.0.0.1, 1.2.3.4, 198.51.100.1 arrives from a loopback peer with TRUST_PROXY=loopback. Who is charged?

From an untrusted peer the header is ignored entirely; the integration test sends four different headers over a real socket to an api that trusts nobody and gets [200, 200, 200, 429].
