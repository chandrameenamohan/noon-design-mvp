D3 · Explain a decision before reading mine. Answer out loud or on paper, then open the answer.

1. The browser's session is 32 random bytes in a row, kept as a SHA-256; the password is kept as scrypt; the sync token is a signed JWT with no role in it. Defend each choice against the obvious alternative (a JWT for the browser, scrypt for the token, a role claim in the sync token), and say what one property decides the first.

Revocation decides the first. A signed stateless token is valid until it expires wherever it is; signing out would delete the browser's copy only, and a stolen copy or another tab keeps working until exp. Revoking early needs a server-side list checked on every request, which is a session table with worse ergonomics, so the browser gets the row from the start and sign-out is a DELETE that kills the token on its next request. The hash is chosen by entropy: a password can be guessed, so it gets a KDF that is slow and memory-hard (scrypt, 32 MiB per guess, its parameters in the string so they can rise); the token is 256 random bits that cannot be guessed at any speed, so one fast SHA-256 is right, and its only job is that a leaked table hands nobody a live session; a KDF there would cost tens of milliseconds on every request for nothing. The sync token stays a JWT because its stateless property is the point (the api signs, the sync node verifies, they never call each other) and its lifetime is 60 seconds, which is the only revocation a signature allows; the role is not in it because a token is checked once at connect and the socket then lives for hours, so a role claim is stale the moment an owner changes anything. The sync server reads the role itself, at the moments section 4 names.

2. The api reads the role from the same row that proves membership and declares a role per route; the sync server reads the role before the upgrade, at the join, on every announcement and every 30 seconds, and the room checks mayEdit at the op's turn. Why each of those, and why did E8.3 have to move the first read to before the upgrade when the token only lives 60 seconds?

Authorise where you fetch: the membership query already returns the row, and the role is a column of it, so one read answers both "may you see this" (404 for a stranger, F2) and "as what" (403 for a member without the role). Declaring the role per route with need makes the requirement visible, and the test that walks app.routes makes a forgotten guard a red test instead of an open route, which is the failure mode of every handler-level scheme. The socket is the hard case because it is authenticated once and lives for hours: the role must be re-read where the socket lives. The join read sets mayEdit; the announcement (a Redis hint that names who changed and never the role, so a forged message can only cause a re-read) makes the node re-read the sessions it concerns within F24's ten seconds; the 30-second sweep covers an announcement the api could not publish; and the room checks the flag at the head of its queue so that an op queued before a demotion is refused too. The upgrade read exists because a revoked outsider's client holds a token that is validly signed for up to 60 more seconds; admitting on the signature and closing at the join would open a socket that should never exist and let a reconnecting client reopen one for a minute. Reading the row while the request is still HTTP makes that token a plain 401, and the socket's lifetime, the token's lifetime and the cookie's lifetime are all beaten by the same fact: the row is read at the moment of asking.

3. The audit row is inserted in a CTE of the action's own statement, or in its transaction; the table has no foreign keys; provisionAppRole revokes UPDATE, DELETE and TRUNCATE on every deploy; and a trigger refuses them to everyone. Why each, and why are both the revoke and the trigger needed?

Same statement or transaction, for completeness in both directions: an action cannot commit without its row (a crash between two separate writes would lose it), and a row cannot outlive an action that rolled back (a refused last_owner, a run that hit run_in_progress, a share of nobody write nothing). No foreign keys, for durability: on delete cascade from orgs would erase the trail exactly when someone wants to read it, and on delete set null from users is an UPDATE the trigger refuses, so the email is copied in and a row may name things that no longer exist. The revoke, for immutability against the application: the app role gets a blanket grant plus default privileges for new tables, so audit_log would be writable unless the three privileges are taken away after the grant, and doing it on every provisioning means a grant made by hand is gone after the next deploy; has_table_privilege answers whether it worked. The trigger, for immutability against everyone the grants do not bind: the table's owner (grants never restrict an owner) and any role widened between deploys. The app role cannot disable it because it owns nothing, so alter table is refused. Either layer alone leaves a path: grants alone let the owner edit; the trigger alone could be disabled by a role that owned the table. Together, the only way to change the trail is to be a superuser, which nothing in the stack connects as.

Recall first

Look away. Name the three moments the sync server reads a peer's role, and what happens at each when the answer is "no access". Then name the two layers that make audit_log append-only and who each one binds. Then check.

Check yourself

Before the upgrade (admits): no access is an HTTP 401, no socket is ever opened, and a token minted before a revoke is refused here. At the join (applyRole, after the socket is registered): no access is a 4404 close, fatal to the client. On every announcement and every 30 seconds (recheck, numbered so an older read never overwrites a newer one): no access is a 4404 close; a demotion flips mayEdit, which the room checks at each op's turn. The two layers: provisionAppRole revokes UPDATE, DELETE and TRUNCATE from the app's login role after the blanket grant, on every deploy, binding the application; the trigger raises on UPDATE, DELETE and TRUNCATE for every role that connects, the owner included.

Then test it

Eight questions. Options are shuffled each visit.

1. Why scrypt for passwords rather than SHA-256, and why memory-hard rather than merely slow?

The stored string names N, r and p, so the cost can rise without a migration; Django and Spring's DelegatingPasswordEncoder store hashes the same way.

2. Someone signs in with an email that has no account. What does the route do, and why?

The unit test times five unknown emails and five wrong passwords through the real scrypt and compares medians; drill 2 plants the early return.

3. Why is the browser's session a row in Postgres and not a signed token like the sync token?

The sync token stays a JWT because the api and the sync node never call each other, and its 60-second life is its revocation; section 4 is about the one case where 60 s was too long.

4. The session token is kept as its SHA-256, the password as scrypt. Why not the same hash for both?

Pick the hash by the entropy of what it protects; isSessionToken also refuses anything that is not exactly the 43-character shape before the database is asked.

5. An editor has three ops waiting in the room's queue when an owner demotes them to viewer. What happens to those ops?

The first shape checked in submit and let every queued op through; the room test and the integration test ("its next op is refused within 10 s") pin the turn-time check.

6. An outsider's share is revoked. Their client holds a sync token minted 20 seconds earlier, valid for 40 more. What does the sync server answer when the client presents it?

F25's clause: neither a reconnect nor a token minted before the revoke gets them back in. /session is a 404 too, which peer-client reads as "give up".

7. Why is the audit row inserted in a CTE of the action's own statement rather than by an audit service after the action returns?

The test "a failed action leaves no audit row" refuses two actions and counts; setMember uses a transaction instead, and writes only when the role really changed.

8. Why does provisionAppRole revoke UPDATE, DELETE and TRUNCATE on audit_log on every deploy, and why is there a trigger as well?

has_table_privilege answers the first; the tests re-grant and re-provision, then try every statement as the app role (42501) and as the owner (append-only exception).
