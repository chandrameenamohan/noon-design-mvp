Four ideas carry the epic. The UI is a function of the replica (section 1): no pane holds a copy of the document; React re-renders every pane from peer.doc when the replica's revision moves, which is why another person's move appears in the tree, on the canvas and in the inspector at once, and why the selection is derived (a node someone removed is simply the page again). Geometry in, one op out (sections 3 to 6): a pointer's height on a row, a point on an infinite sheet, a blur on a number field are read by pure modules into a Drop, a Slot or a value, and each becomes one of the four ops through the one submit; nothing in the editor knows a second way to write. Refuse only the impossible (section 4): the tree, the library and the inspector build every op the document's shape allows and let the replica and the room say no, so validate() has one copy. The screen decides nothing (section 9): a role in the session shows or hides a button; the api and the room read the row for themselves on every request and every op.

1 · React from zero: a component is a function of its inputs, and the editor is a function of the replica

You know the desktop model: a widget is an object with state, an event mutates the object (label.setText(...), tree.getModel().insertNodeInto(...)), and the toolkit repaints what changed. React inverts it. A component is a function from props (its inputs) to a description of what should be on the screen (JSX, which compiles to calls that build a tree of plain objects); when an input changes, React calls the function again and diffs the new description against the last one, touching only the DOM nodes that differ. You never say "update this label"; you say "given this document, here is the whole inspector", and React works out that one <input value> changed. State that belongs to a component (a draft in a text field, whether a row is collapsed) lives in a hook, useState, whose setter schedules a re-render; state that lives outside React (a WebSocket, the OS theme, a clock) gets in through useSyncExternalStore, which is the whole trick of this app.

From apps/web/src/usePeer.ts

function openStore(documentId: string, onRejected: (rejection: Rejection) => void, onOp: (message: SequencedOp) => void, onSession: (session: SessionResponse) => void) {
  const listeners = new Set<() => void>();
  const tell = (): void => { for (const listener of listeners) listener(); };
  // Every session minted passes here (a reconnect too), so the role the editor shows controls by is the api's latest word.
  const session = async (): Promise<SessionResponse | null> => {
    const minted = await openSession(documentId);
    if (minted) onSession(minted);
    return minted;
  };
  const peer = connectPeer({ manifest, session, onChange: tell, onStatus: tell, onRejected, onOp });
  return {
    peer,
    subscribe: (listener: () => void) => { listeners.add(listener); return () => { listeners.delete(listener); }; },
    // peer.doc is edited IN PLACE and never changes identity, so the snapshot is built from what does move.
    snapshot: () => `${String(peer.revision)}:${String(peer.pendingCount)}:${peer.status}:${String(peer.readOnly)}:${String(peer.presenceRevision)}`,
  };
}

Read openStore as an adapter. The peer changes on its own (a message arrives, a reconnect happens); React cannot see that. useSyncExternalStore(subscribe, getSnapshot) asks for two things: how to be told something changed (subscribe registers a listener; the peer's onChange and onStatus call every listener) and how to read a value that React compares with Object.is to decide whether to re-render (snapshot). The document is edited in place by the replica, so peer.doc is the same object before and after an op and would never look different; the snapshot is therefore a string of the numbers that do move: revision, pendingCount, status, readOnly, presenceRevision. A new string, a re-render of Canvas; the same string, nothing.

 * It holds TWO documents:
 *   confirmed   what the server has said, in the server's order. Never guessed at.

That is why the editor can be a view: the replica already holds what the person should see (optimistic: what the server said plus every op of ours it has not answered yet, an invariant tested as a property in lesson 2), and revision is bumped whenever it changes. Every pane renders from peer.doc; none keeps a copy; so a move made in the tree is on the canvas in the same render, and a move made by someone else, arriving as a message, is in the tree, on the canvas and in the inspector in the render the message causes.

From apps/web/src/usePeer.ts

export function usePeer(documentId: string, onOp?: (message: SequencedOp) => void) {
  const [refusals, setRefusals] = useState<Refusal[]>([]);
  const [store, setStore] = useState<ReturnType<typeof openStore>>();
  const [role, setRole] = useState<Role>();
  const refuse = (reason: Reason, op?: Op): void => { setRefusals((before) => [...before, { id: crypto.randomUUID(), reason, ...(op === undefined ? {} : { op }) }]); };
  const latestOnOp = useRef(onOp);
  latestOnOp.current = onOp;
  useEffect(() => {
    // `quiet` (someone else removed the node first) is not news: the canvas already shows it (F5).
    const opened = openStore(documentId, (rejection) => { if (!rejection.quiet) refuse(rejection.reason, rejection.op); }, (message) => latestOnOp.current?.(message), (session) => { setRole(session.role); });
    setStore(opened);
    return () => { opened.peer.close(); };
  }, [documentId]);
  useSyncExternalStore((store ?? NOTHING).subscribe, (store ?? NOTHING).snapshot);
  return { peer: store?.peer, role, refusals, refuse, dismiss: (id: string): void => { setRefusals((before) => before.filter((each) => each.id !== id)); } };
}

Two rules of the hook are load-bearing. Side effects go in useEffect, never in the render body. A render is a pure computation React may run and throw away (StrictMode does this on purpose in development, twice, to catch exactly this), so opening a WebSocket during render would open two; an effect runs after the commit, once per change of its dependencies ([documentId]), and returns a cleanup that closes the peer when the document changes or the component unmounts. A callback that may change every render is held in a useRef (latestOnOp): a ref is a box React does not watch, so Canvas may pass a fresh arrow function each render without the effect re-running and the peer being reopened. The Java analogue is a listener registered once in addNotify and removed in removeNotify; the Python analogue is a signal connected in __init__ and disconnected in closeEvent; the difference is that React will call your render function far more often than a toolkit calls paint, and it must be safe to.

Derive, do not store. The canvas keeps only which id the person wanted (wanted); the node shown is doc.nodes[wanted] ?? root, computed every render. When someone else removes the selected node, no event handler has to notice: the next render finds no such node and the selection is the page, and one live sentence says so. Every derived value in this file (the labels, which nodes are containers, who has what selected, the AI's anchor) is recomputed from the document on each render, which sounds wasteful to a Swing programmer and is the reason the panes can never disagree: there is no second copy to fall out of date. Last, state versus ref, the distinction a React beginner gets wrong most. useState is for values the screen renders from: change it and React re-renders. useRef is for values that change without anything on the screen depending on them: the last pointer position during a pan, a press that may or may not become a drag, "focus the tab stop once it has rendered". 2 · Tokens, theming and contrast as a test

A CSS custom property (--accent: #1d4ed8) is a variable that lives in the cascade: it is set on an element, inherited by its descendants, and read anywhere below with var(--accent). Unlike a Sass variable, which is substituted at build time, it is resolved at style time, per element, so changing it on <html> recolours the page without touching a rule, and setting it again on a subtree recolours only that subtree. tokens.css declares every colour, size, space and radius the app uses as a custom property and nothing else declares one; app.css only refers to them.

export function useTheme(): { theme: Theme; toggle: () => void } {
  const [preference, setPreference] = useState<ThemePreference>(remembered);
  const dark = useSyncExternalStore(onSystemChange, systemDark, () => false);
  const theme = resolveTheme(preference, dark);
  useEffect(() => { apply(theme); }, [theme]);
  return {
    theme,
    toggle: () => { const next = toggled(theme); remember(next); setPreference(next); },
  };
}

theme.ts is pure: a remembered preference and the OS's answer come in, a theme comes out, and toggled remembers the opposite of what is shown as an explicit choice, so a person who pressed the toggle on a dark OS gets light and keeps light when the OS flips. useTheme binds it: the OS preference is an external store (a matchMedia change is not a render), read through useSyncExternalStore exactly as the peer is; the choice is useState initialised from localStorage, read defensively (a private window may refuse it); and an effect writes the resolved theme onto <html>. main.tsx calls applyStoredTheme() before the first render, so the first paint is already right: no flash.

3 · Coordinate systems: one transform, outlines in world space, and the deepest box wins

An infinite canvas has two coordinate systems. World: the page frame's own pixels at 100 %, where the Button is at (240, 100) for ever. Screen: where a world point is drawn inside the canvas element right now, given the zoom and the pan. One convention everywhere, and the whole of viewport.ts follows from it:

From apps/web/src/viewport.ts

export const toWorld = (v: Viewport, screen: Point): Point => ({ x: (screen.x - v.x) / v.zoom, y: (screen.y - v.y) / v.zoom });
export const toScreen = (v: Viewport, world: Point): Point => ({ x: world.x * v.zoom + v.x, y: world.y * v.zoom + v.y });

/** Zooms to `zoom` (clamped) so that the world point under `anchor` (a screen point: the pointer, the view's centre) stays under it. */
export function zoomAt(v: Viewport, zoom: number, anchor: Point): Viewport {
  const next = clampZoom(zoom);
  const held = toWorld(v, anchor);
  return { zoom: next, x: anchor.x - held.x * next, y: anchor.y - held.y * next };
}

zoomAt is the function a beginner gets wrong: zooming about the pointer means the world point under the pointer must stay under it, so take that point (toWorld at the old zoom), then choose the new offset so toScreen of it at the new zoom is the anchor again. The test asserts exactly this for four zooms, and that a point elsewhere on the screen moves away from the anchor by the right factor. Everything is pure, clamped to 10–400 %, and tested as arithmetic; Surface only wires events to it.

From apps/web/src/viewport.ts

export function fit(view: Size, content: Size, padding = 32): Viewport {
  const zoom = clampZoom(Math.min((view.width - 2 * padding) / content.width, (view.height - 2 * padding) / content.height));
  return { zoom, x: (view.width - content.width * zoom) / 2, y: (view.height - content.height * zoom) / 2 };

export function dropToMoveOp(doc: Doc, drop: Drop): MoveOp | null {
  const node = doc.nodes[drop.nodeId];
  const target = doc.nodes[drop.targetId];
  if (!node || !target || node.parentId === null) return null;
  if (within(doc, drop.targetId, drop.nodeId)) return null; // onto itself, or into its own subtree
  if (drop.placement === "into") return { type: "move_node", nodeId: node.id, newParentId: target.id, index: target.children.filter((id) => id !== node.id).length };
  if (target.parentId === null) return null; // beside the page: there is no such place
  const parent = doc.nodes[target.parentId];
  if (!parent) return null;
  const siblings = parent.children.filter((id) => id !== node.id);
  return { type: "move_node", nodeId: node.id, newParentId: parent.id, index: siblings.indexOf(target.id) + (drop.placement === "after" ? 1 : 0) };
}

This is the function the chapter is named for. A Drop (which node, over which row, before/after/into) becomes one move_node, or null when there is nowhere to go. Two details are load-bearing. The index is the node's FINAL position among its new siblings, counted after it was taken out (SPEC keystone 3): dropping card after stack in [card, stack, text2] means [stack, card, text2], index 1, not 2, which is why the siblings are filtered before indexOf. It refuses only what is structurally impossible on the document it can see: the page itself, a node onto itself or into its own subtree (a cycle; within carries a seen set so a corrupt document with a cycle cannot hang the tab), a place beside the page. A container that takes no children, an index past the end, a node someone removed meanwhile: those are the replica's and the room's verdict, shown as their refusal like any other edit's, because a second copy of validate() here would drift.

export function controlFor(prop: Prop): Control {
  const placeholder = prop.default === undefined ? (prop.required ? "required" : "") : String(prop.default);
  const type = prop.type;
  switch (type.kind) {
    case "string":
      return { kind: "text", prop, placeholder };
    case "number":
      return { kind: "number", prop, placeholder };
    case "boolean":
      return { kind: "toggle", prop, fallback: prop.default === true };
    case "enum": {
      const fallback = typeof prop.default === "string" ? prop.default : undefined;
      return { kind: type.options.length <= SEGMENTED_MAX ? "segmented" : "select", prop, options: type.options, fallback };
    }
    default: {
      // The compiler's check that every kind above is handled, and the runtime's answer when a manifest
      // from a newer extractor arrives with a kind this build has never heard of.
      const unknown: never = type;
      throw new Error(`no control for prop kind ${JSON.stringify((unknown as { kind?: unknown }).kind)} (${prop.name})`);
    }
  }
}

Read the default branch twice. const unknown: never = type is the compiler's exhaustiveness check: type is a discriminated union of four kinds, and after four cases TypeScript narrows it to never; add a fifth kind to the contract and this line stops compiling until a control exists for it. export function actionFor<S extends Scope>(scope: S, event: KeyLike): ActionOf<S> | null {

10 · Trade-offs and comparisons: where this editor sits

Retained widgets versus a view of the state. Swing, JavaFX, Qt and Tk are retained-mode: a widget tree is built once and mutated by events, and the toolkit repaints the damage. React is declarative over a retained DOM: your code describes the whole screen from state on every change and React mutates the DOM to match. The desktop model is faster per event and puts the truth in the widgets, where it drifts (the classic Swing bug is a TreeModel that no longer matches the data). The React model puts the truth in one place (here the replica) and makes every pane a projection; the cost is that render must be cheap and pure, which is why the pure modules of this epic are small and the components thin. JavaFX's property bindings and Qt's model/view are each half-way to this: the view updates from a model, but the model is yours to keep in step.

Optimistic versus confirmed. The document is optimistic because the replica can afford it: the same validate() runs locally, a refusal is a rebuild from confirmed plus the remaining pending ops, and the invariant is tested as a property. The members list is confirmed-only because its truth is rows behind locks and side effects, and a guessed row would lie. The rule of thumb: be optimistic where you can run the server's rule locally and recover from a refusal by recomputation; otherwise show the answer.

One transform versus re-layout. A canvas that re-lays its content out at every zoom (setting widths and font sizes) is how a browser's own page zoom works and is right for text. A design canvas wants the frame to be a picture that scales: one transform on one layer, composited, with the editor's own strokes divided back to screen size. Figma does the same on a WebGL canvas; here the "picture" is live DOM, so the components stay real and inspectable, and the price is that measuring must happen after render.

HTML drag and drop versus pointer events. HTML DnD gives you cross-window drags, a ghost image and the OS's drop semantics, at the cost of a second event vocabulary, a ghost to fight, and dragover on its own clock. Pointer events with capture give one vocabulary for the canvas, the tree and the library, an indicator that follows the exact pointer, and Escape to cancel; they cannot drag out of the window, which nothing here needs.

Where Figma differs. Figma's canvas is freeform vectors on a WebGL surface with its own layout engine, and multiplayer is a CRDT-like property map with last-writer-wins per property. Noon's canvas is a tree of real components laid out by the design system itself (SPEC §5: no freeform drawing, no absolute positioning, so the design can become code), and multiplayer is a server-ordered op log (the note on multiplayer approaches has the comparison). The Figma feel (a dotted infinite sheet, zoom at the pointer, layers left and inspector right, one accent, a ? sheet, cursors with name tags) is borrowed; the model is not.

/** Counts the move_node ops THIS browser sends: the proof that a drag is one op, not a remove and an add, nor one per pixel. */
async function countingMoves(page: Page): Promise<{ moves: () => number }> {
  let moves = 0;
  await page.routeWebSocket(/\/documents\//, (ws) => {
    const server = ws.connectToServer();
    ws.onMessage((message) => {
      const parsed: unknown = JSON.parse(String(message));
      if (typeof parsed === "object" && parsed !== null && "op" in parsed && typeof parsed.op === "object" && parsed.op !== null && "type" in parsed.op && parsed.op.type === "move_node") moves++;
      server.send(message);
    });
    server.onMessage((message) => { ws.send(message); });
  });
  return { moves: () => moves };
}

1. The layers tree, the canvas drop and the library all refuse only what is "structurally impossible on the document they can see" (the page, a node onto itself, beside the page) and build every other op, including a drop into a Button, which the replica then refuses. Defend that against the obvious alternative: disable the drop the moment the pointer is over a leaf, so the person never sees a refusal.

The rules that say what a document may become live in one place, validate() in the doc-model, and they are run twice on every op already: by the replica the moment submit is called (the synchronous verdict, so a refused drop is a notice within the same frame and the tree never shows the node moved) and by the room when it orders the op (the asynchronous verdict, for what the replica could not know: a parent someone removed meanwhile, a viewer whose role changed). A tree that greyed out leaves would be a third copy of the rule "this component takes no children", written in a different language (a CSS state instead of a refusal reason), and copies drift: the manifest gains a component that takes children conditionally, or the rule gains "not into its own ancestor at sequencing time", and the tree is wrong in a way no test of validate() can see. So the tree knows only geometry: the page has no parent (nowhere "beside" it), a node cannot be its own ancestor (a cycle), a node that is gone has no place. Those are facts about the tree's own rows, not about the document's rules, and they are the only refusals that would otherwise build an op with no meaning. The cost is one honest sentence ("Button does not take children") where a greyed row would have been silent; the gain is that the refusal path is the same for a person's drop, a slow room, a viewer and the AI, and the e2e spec asserts the sentence appears for Alt+Right into a Button rather than asserting a colour.

2. Cursors changed from "a fraction of the canvas" (epic 2) to world coordinates, and the AI's cursor is derived from the ops the room ordered through a new onOp hook on the peer rather than from presence. Why each, and why is onOp "a window onto who did what, not a write path"?

A fraction of the canvas element was right when every window drew the whole page in the same box at 100 %: half-way across meant the same component everywhere. With zoom and pan per window (E10.2) the canvas element is a viewport onto an infinite sheet, and half-way across one window is a different spot on the sheet from half-way across another; only a point on the sheet itself (the frame's own px at 100 %, what toWorld returns) names the same component in both, and the receiving side needs no conversion at all: the mark sits inside .world and the same transform that places the frame places it. The contract bounds the value at ±1e6 so a wild number never rides the wire, and Surface rounds to hundredths because a sub-pixel is noise. The AI has no pointer, so presence cannot carry where it is; but the room stamps every ordered op with its actor, and the peer already applies those ops, so telling a listener after each apply costs one call and no wire change. cursors.ts keeps one anchor per agent actor id and hands back the same map for anyone else's op, so React renders nothing for a person's edits. It is a window because nothing in it can change the document: the listener is told after the replica applied the op, receives a value it cannot answer, and the peer does not depend on anyone listening; the ONE write path (keystone 2) is still submit, and a reader of peer.ts can see from the option's type that onOp returns void. Rejected: mapping a fractional cursor through the frame's box (breaks the moment either side pans), a cursor-per-node attribute in presence (a wire change beyond what world coordinates need), an aria-live on the cursors (decoration must not talk; the bar's list is the record).

3. The document is optimistic (the replica shows an edit before the room answers) but the members list and the Share dialog are not (a row changes only when the api has answered), and the session carries a role the editor shows Share by but never decides by. Defend all three, and say what a role change under an open page does.

The document can be optimistic because its ops were designed for it: they are small, the replica runs the same validate() the room runs so a refusal is rare and local, the invariant "optimistic = confirmed + pending in order" is tested as a property, and a refused op is simply dropped from pending and the guess rebuilt. A membership change has none of that: its truth is a Postgres row behind need("owner"), an advisory lock for the last owner, a 404 for an email nobody signed up with, and side effects (a revoked share closes a live session on every sync node); a guessed row could show "editor" for a person the api refused, and there is no journal to rebuild from. So withMember applies the api's own answer, never the request, and a 403 or 404 makes the page read the list again because "the world moved under it". The role in the session is read from the same row that proved access when the session was minted, and it is beside the token, never inside it, because E1.5 stands: the token says who, and the routes and the room read the row for themselves on every request and every op. Showing Share only to an owner saves a viewer from a 403 in their console (the e2e fixture fails on any console error) and saves a route the api would refuse; it decides nothing, because pressing Share on a stale page reaches GET /shares with need("owner"), and the api's refusal comes back as a sentence in the dialog. A role change under an open page is therefore met at the next action, as a sentence, and the room meets it sooner: it re-reads the role on every Redis hint and at the 30 s sweep (E8.3), so a demoted editor's next op is refused by the room whatever the screen still shows.

Then test it

Eight questions. Options are shuffled each visit.

1. A WebSocket message arrives with another person's set_prop. How does the inspector on your screen learn about it?

No component holds a copy of the document: every pane renders from the one replica, which is why another person's move shows in the tree, the canvas and the inspector at once.

2. Why is the dark theme :root[data-theme="dark"] and not @media (prefers-color-scheme: dark)?

useTheme still reads the OS through matchMedia, as an external store, so a browser that never chose flips live when the OS does; the spec asserts exactly that.

3. You zoom to 300 %. What happens to the selection outline's 2 px stroke and to the outline's position?

The measuring pass runs after a render, not after a zoom; a box-shadow spread was chosen over a border because Chrome snaps border widths to whole pixels.

4. A person drags "Text 2" and drops it after "Button 1", which sits inside a Card. What goes over the wire?

The e2e spec routes the WebSocket and counts move_node frames, so "one op per move" is measured, not assumed.

5. The manifest is regenerated and Card gains a subtitle: string prop. What changes in the inspector's code?

The one thing that would change code is a new prop kind: controlFor's default branch types the value as never and throws, so a prop without a control can never render as nothing.

The node id is how the AI's cursor works, because the AI has no pointer; a person's pointer can rest on empty sheet, which is a place too.

Ctrl and Cmd are never bound on purpose: actionFor returns null for them, so browser chords stay the browser's.

The members list is deliberately not optimistic: withMember only ever applies the api's own answer.
