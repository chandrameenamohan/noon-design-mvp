The map: what multi-node means here

Epic 6 made one sync process trustworthy: an acknowledged edit survives a crash. Epic 7 asks what happens when there are two of them. The whole design rests on lesson 2's first rule: one room per document orders the ops, and there can never be two rooms for one document, because two rooms would mean two orderings and two documents. So with two processes the question is not "how do they share a room" but "how do they agree, at every moment, on which one has it", including the moments when one of them is dead, frozen, or cut off, and cannot be asked. Three features answer it. F20, one room globally: every peer of a document lands in the same room, whichever node it asked first. F21, failover: kill the node that owns a room and the room moves to the other within one lease, with F18's guarantees intact. F22, fencing: a node paused past its lease and then resumed cannot append to the journal; it closes its sockets; the journal has no gap and no duplicate.

Four ideas carry the epic, and they are the four an interviewer will ask about. A lease is a lock with an expiry (section 1): a holder that dies stops renewing, and the lock frees itself; the price is that "I hold it" is now a statement about time. Only your own clock, and only the moment you sent (section 2): a holder trusts its lease until sent + 0.9 ttl on a monotonic clock, never a wall clock, never Redis's clock, and gives up its peers when that passes. Liveness is a hint, never a truth (sections 3 and 4): heartbeats decide where a peer is sent; the lease alone decides who owns; a dead owner's lease is waited out, never stolen. The lock is not the safety; the storage is (section 5): a process frozen past its lease cannot know it, so the journal append itself refuses a writer whose claim is no longer the document's, in the same statement that writes. Kleppmann's fencing-token argument is the spine of the chapter, and the repo's own learning-tests/redis reproduced the zombie before a line of the epic was written.

1 · The lease: one script, one token, three compare-and-sets

Redis was already in the stack for queues (lesson 3). SPEC §2a fixed the lease's shape from the learning test: SET NX PX plus a fencing token from INCR in the same Lua script; renew and release are compare-and-set in Lua. The package that implements it is small on purpose: index.ts talks to Redis, lease.ts is pure and holds every decision (parsing, deadlines, routing, waiting), so the decisions have unit tests and the I/O has an integration test against the real server.

From packages/lease/src/index.ts

/**
 * Room leases in Redis (SPEC §2a): who owns each document's room, for how long, under which fencing token.
 * Keys: `<prefix>lease:<documentId>` holds "<token>:<nodeId>" with a PX expiry; `<prefix>lease-token:<documentId>`
 * is the document's token counter, never expiring, so a later owner always gets a larger token.
 * `<prefix>node:<nodeId>` is a sync node's heartbeat (E7.2): it expires a third of a ttl after the node's last
 * beat, so a killed owner is known dead long before its leases expire. Routing reads it; nothing safe does.
 * The counter lives in Redis, so a flushed Redis would start the tokens again at 1: an acquire therefore takes a
 * `floor` (the largest token the journal's fence has seen, E7.3) and never issues a token at or below it.
 */
export type Leases = {
  /** How long a lease lives without renewal. The holder renews every third of it. */
  readonly ttlMs: number;
  /**
   * Take the room if nobody holds it, under a token above `floor`. Answers the holder either way: compare its
   * nodeId (and token) with yours.
   */
  acquire(documentId: string, nodeId: string, floor?: number): Promise<{ acquired: boolean; holder: Holder }>;
  /** Extend, only if `holder` is still exactly the lease's value. False: it expired or is someone else's. */
  renew(documentId: string, holder: Holder): Promise<boolean>;
  /** Let go, only if still ours: a late release must never delete the NEXT owner's lease. */
  release(documentId: string, holder: Holder): Promise<void>;
  owner(documentId: string): Promise<Holder | undefined>;
  /** "This node is alive" for a third of a ttl. A sync node calls it every tenth of one. */
  beat(nodeId: string): Promise<void>;
  /** Which of these nodes beat recently. */
  alive(nodeIds: readonly string[]): Promise<ReadonlySet<string>>;
  /** Resolves once Redis answered a PING; rejects after `timeoutMs`. */
  ready(): Promise<void>;
  close(): Promise<void>;
};

From packages/lease/src/index.ts

// One script, so nothing can happen between "nobody holds it", the token and the SET. The token is issued
// only when the SET happens: N racing acquirers of a free room move the counter by exactly one.
const ACQUIRE = `
local current = redis.call('GET', KEYS[1])
if current then return {0, current} end
if tonumber(redis.call('GET', KEYS[2]) or '0') < tonumber(ARGV[3]) then redis.call('SET', KEYS[2], ARGV[3]) end
local holder = redis.call('INCR', KEYS[2]) .. ':' .. ARGV[1]
redis.call('SET', KEYS[1], holder, 'PX', ARGV[2])
return {1, holder}`;
// Compare-and-extend and compare-and-delete: a plain PEXPIRE or DEL would touch a lease that expired and was
// taken by another node in the meantime (reproduced in learning-tests/redis, finding 2).
const RENEW = `if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('PEXPIRE', KEYS[1], ARGV[2]) else return 0 end`;
const RELEASE = `if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end`;

Read ACQUIRE as one atomic step, because that is what Redis makes it. Redis runs commands on one thread, and a Lua script is one command: nothing from any other client runs between its first line and its last. So GET (is it held?), the counter floor, INCR (issue a token) and SET ... PX (take it, with an expiry) happen with no gap, and the two properties the tests demand follow. Exactly one of N racing acquirers wins, because only the first to run sees no value. The counter moves by exactly one per acquisition, because the token is issued only on the branch that also does the SET; a loser returns the current holder and touches nothing. That second property is why the join-race test can assert token: 1 after ten simultaneous joins and 2 after the room closes and is taken again. The naive version, INCR then SET NX as two round trips, would burn a token per loser and could hand a smaller token to a later owner if two acquirers interleaved, which section 5's fence could not survive.

RENEW and RELEASE compare the exact value "<token>:<node>" before touching the key. The learning test reproduced why: a holder whose lease had expired issued a plain DEL and deleted another client's freshly acquired lease. A bare PEXPIRE has the same flaw in the other direction: it would extend a lease that is now someone else's. Comparing the whole holder, not just the node id, also stops a node that took the same room twice from renewing its own earlier, dead acquisition (the integration test's "same node, another acquisition" line).

export function createLeases({ redisUrl, ttlMs = 10_000, prefix = "", timeoutMs = 1000 }: { redisUrl: string; ttlMs?: number; prefix?: string; timeoutMs?: number }): Leases {
  // Every call must FAIL within a deadline when Redis is away (E3.1 lesson 1): no offline queue, a command
  // timeout, one retry. A caller that cannot ask refuses to open the room; it never guesses.
  const redis = new Redis(redisUrl, { enableOfflineQueue: false, commandTimeout: timeoutMs, maxRetriesPerRequest: 1, connectTimeout: timeoutMs });
  // Never log the error object: a failed AUTH carries the password in err.command.args.
  redis.on("error", (err: unknown) => process.stderr.write(`${JSON.stringify({ level: "warn", source: "lease", message: err instanceof Error ? err.message || err.name : "unknown" })}\n`));
  const leaseKey = (documentId: string): string => `${prefix}lease:${documentId}`;
  const ready = (): Promise<void> => new Promise((resolve, reject) => {
    if (redis.status === "ready") { resolve(); return; }
    const timer = setTimeout(() => { reject(new Error(`redis did not answer within ${String(timeoutMs)} ms`)); }, timeoutMs);
    redis.once("ready", () => { clearTimeout(timer); resolve(); });
  });
  return {
    ttlMs,
    async acquire(documentId, nodeId, floor = 0) {
      const [taken, value] = (await redis.eval(ACQUIRE, 2, leaseKey(documentId), `${prefix}lease-token:${documentId}`, nodeId, String(ttlMs), String(floor))) as [number, string];
      const holder = parseHolder(value);
      if (!holder) throw new Error(`lease of ${documentId} holds a value that is not a holder`);
      return { acquired: taken === 1, holder };
    },
    renew: async (documentId, holder) => (await redis.eval(RENEW, 1, leaseKey(documentId), formatHolder(holder), String(ttlMs))) === 1,
    async release(documentId, holder) {
      await redis.eval(RELEASE, 1, leaseKey(documentId), formatHolder(holder));
    },

Three TypeScript things in createLeases. The client options are the E3.1 lesson again: enableOfflineQueue: false, a commandTimeout and one retry, so every call fails within a deadline when Redis is away; a lease library that hangs is a room that never opens and never says why (the integration test times every failure). redis.eval(...) as [number, string] is a type assertion, not a conversion: ioredis types eval's result as unknown because a script can return anything, and the cast records what this script returns. parseHolder then checks the string at runtime, so a key that holds something that is not ours reads as "nobody" rather than as a crash. The error handler never logs the error object: a failed AUTH carries the password in err.command.args, so only err.message goes to stderr.

From packages/lease/src/lease.ts

/**
 * Who owns a document's room: a sync node, and the fencing token its acquisition was issued. The token
 * rises with every acquisition of that document (INCR), so two holders are never confused, even when one
 * node takes the same room twice, and a later owner always carries the larger number (the fence of E7.3).
 */
export type Holder = { token: number; nodeId: string };

/** A node id is a URL path segment and a compose service name: lowercase, digits, dashes. */
export const NodeId = z.string().regex(/^[a-z0-9][a-z0-9-]{0,31}$/, "a sync node id is 1-32 of a-z, 0-9 and -, starting with a letter or digit");

export const formatHolder = ({ token, nodeId }: Holder): string => `${String(token)}:${nodeId}`;

/** A value read back from Redis. Anything else there is not ours to trust: undefined. */
export function parseHolder(value: string): Holder | undefined {
  const match = /^([1-9]\d{0,15}):(.+)$/.exec(value);
  if (!match?.[1] || !match[2] || !NodeId.safeParse(match[2]).success) return undefined;
  return { token: Number(match[1]), nodeId: match[2] };
}

Holder is two numbers of information: who, and which acquisition. The token is the second one, and the whole of section 5 is built on it rising. parseHolder is strict by design: the regex refuses a leading zero, a token of more than sixteen digits (past Number's safe range) and any node id that NodeId would refuse. A node id is a URL path segment and a compose service name, so it is lowercase letters, digits and dashes, and Zod's .regex carries that rule into every config file that names one.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

The token issued only with the SET, or the join-race test could not count.

An earlier shape issued the token first (INCR) and then tried the SET NX, so ten racing joiners moved the counter by ten and the winner's token was whichever number its INCR happened to get. The test that asks "exactly one acquisition happened" cannot be written against that: token 1 for the winner is only meaningful if losers cost nothing. Moving the INCR after the GET check inside the one script made "the counter moved by one" a checkable fact, and the same script later took the floor (section 5) in the only place it can be applied safely: before the INCR, under the same atomicity.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

The api acquiring leases on a node's behalf was rejected.

It looked simpler: /session knows the document and could pick a node and take the lease for it. But a lease has to be renewed, and only the process that holds the room knows whether it still holds the room. A node that did not acquire cannot know it must renew, and a lease renewed by a third party is a lease that outlives the room it protects. The node takes its own lease when its first peer arrives, and the api only reads.

The principle: a lease's three operations must each be atomic with their own check. Acquire checks "free" and takes; renew checks "still mine" and extends; release checks "still mine" and deletes. Redis gives atomicity for free inside one script, so the design puts each check and its effect in one script and never splits them across a round trip. Section 5 applies the same rule to Postgres, where the one statement is the atom.

2 · Clocks against tokens: when a holder must stop believing itself

A lease is a promise with a time on it, and a time raises the question every distributed-systems text spends a chapter on: whose time? Redis expires the key on its own clock, starting when it receives the command. The holder can only read its own clock. The two clocks run at slightly different rates, the message between them takes time, and the holder can be paused for a minute by the operating system, the garbage collector or docker pause without noticing. keepLease is the answer to "until when may this process act as the owner", and it is deliberately conservative.

From packages/lease/src/lease.ts

export type LeaseKeeper = {
  /** False from the moment this process can no longer be sure it holds the lease. Never true again. */
  readonly held: boolean;
  /** Renew once (call every ttl/3). Also the moment an unrenewable lease is declared lost. */
  tick(): Promise<void>;
};

/**
 * Keeps a lease that was just acquired, and decides when to stop trusting it.
 *
 * Only OUR monotonic clock is used, never a wall clock, never a time from another machine: Redis starts a
 * PX countdown when it RECEIVES the command, which is after we sent it, so "sent + ttl" (on our own clock)
 * is never later than Redis's expiry. The margin covers the two clocks running at slightly different rates.
 * `renew` answers false when the lease is someone else's now (lost at once) and throws when Redis cannot be
 * asked (still ours until the deadline passes). `acquiredAt` must be read BEFORE the acquire was sent.
 *
 * This is not safety: a process frozen past the deadline believes `held` until it runs again. The journal's
 * fence (E7.3) is what refuses that zombie's writes; this only makes a live node give its peers up promptly.
 */
export function keepLease({ renew, ttlMs, now, acquiredAt, onLost }: { renew: () => Promise<boolean>; ttlMs: number; now: () => number; acquiredAt: number; onLost: () => void }): LeaseKeeper {
  const trusted = (sentAt: number): number => sentAt + ttlMs * 0.9;
  let validUntil = trusted(acquiredAt);
  let lost = false;
  let renewing = false;
  const lose = (): void => {
    if (lost) return;
    lost = true;
    onLost();
  };
  const expired = (): boolean => {
    if (!lost && now() >= validUntil) lose();
    return lost;
  };
  return {
    get held() { return !expired(); },
    async tick() {
      // A renewal still in flight (a hung Redis, bounded by the client's command timeout) is not waited
      // for twice, but the deadline is still checked: a hang must not keep a room alive.
      if (expired() || renewing) return;
      renewing = true;
      const sentAt = now();
      try {
        if (await renew()) validUntil = trusted(sentAt);
        else lose();
      } catch {
        // Redis did not answer: keep trying on the next tick while the deadline allows.
      } finally {
        renewing = false;
      }
      expired();
    },
  };
}

Three decisions, each with a test. Only our monotonic clock. now is performance.now() in production, which cannot jump when NTP corrects the wall clock (Date.now() can, backwards). Java's System.nanoTime() and Python's time.monotonic() are the same instrument. Counting from the send, not the reply. Redis starts its PX countdown when the command arrives, which is after we sent it, so a deadline of sent + ttl on our clock can never be later than Redis's expiry; the 0.9 is the margin for the two clocks drifting. The test "the deadline counts from when a renewal was SENT" has a renewal that takes 800 ms to answer and asserts the lease is trusted until 300 + 900, not 1100 + 900. A hang does not extend anything. A renewal in flight is not awaited twice, but the deadline is still checked on every tick and every read of held, so a hung Redis cannot keep a room alive by never answering.

The idiom to notice is that held is a getter with a side effect: reading it may fire onLost. That is a deliberate trade. The room's server needs "are we still the owner" to be true at the moment of the question, not at the last timer tick, and the cheapest way to make every reader honest is to make the read itself check the clock. lose is idempotent so that onLost runs once however many readers ask.

Now the point the doc comment makes in its last paragraph, because it is the point of the epic. This is not safety. A process frozen for two seconds does not run expired() during those two seconds; when it wakes, its first read of held says false and it gives up, but between the wake and that read it may already have done something, and an await it was inside when it froze will simply continue. The learning test measured exactly that: owner A blocked its own event loop with Atomics.wait for two seconds, owner B took the lease 1.7 seconds before A woke, and A's in-memory flag still said "mine". Kleppmann's argument in How to do distributed locking (and chapter 8 of DDIA) is that no amount of care with clocks closes this gap, because the pause can happen at any instruction, including the one after the check. The only thing that closes it is a check by the storage, at write time, of a token that the frozen process cannot have updated. That is section 5; keepLease only makes a live node let go promptly, so that failover takes one ttl rather than a ttl plus a discovery.

A renewal that fails must not shorten what an earlier one earned.

A first version set validUntil from the failed attempt's send time when Redis threw, which under a flaky network would have made the room give up its peers every time one renewal failed, although the previous one had bought it another 900 ms. Principal-level point: there are two independent instruments here and they answer different questions. The clock answers "may I still act as the owner" and it is allowed to be wrong in one direction only, towards giving up early. The token answers "was this write made by the current owner" and it is never wrong, because it is compared by the storage, not by the process that might be frozen. A system that uses only the first is unsafe under pauses; a system that uses only the second is safe but has no failover time bound, because nobody ever gives anything up. This repo uses both, and keeps them in separate modules so that each has its own tests.

// A query or fragment would swallow the "/documents/<id>" that gets appended to the address.
const wsBase = (value: string): string | undefined => {
  if (!URL.canParse(value)) return undefined;
  const url = new URL(value);
  return ["ws:", "wss:"].includes(url.protocol) && url.search === "" && url.hash === "" && !value.includes("?") && !value.includes("#") ? value.replace(/\/+$/, "") : undefined;
};

export function parseSyncNodes(value: string): SyncNodes | undefined {
  if (!value.includes("=")) {
    const url = wsBase(value);
    return url === undefined ? undefined : { kind: "one", url };
  }
  const nodes = new Map<string, string>();
  for (const entry of value.split(",").map((part) => part.trim()).filter(Boolean)) {
    const at = entry.indexOf("=");
    const id = entry.slice(0, at).trim();
    const url = wsBase(entry.slice(at + 1).trim());
    if (!NodeId.safeParse(id).success || url === undefined || nodes.has(id)) return undefined;
    nodes.set(id, url);
  }
  return nodes.size > 0 ? { kind: "many", nodes } : undefined;
}

/**
 * Where a peer of `documentId` dials: the room's owner if it has one and is alive, otherwise any live node
 * (`pick`), whose first peer then tries to take the lease. Two nodes racing for a free room is fine: exactly one
 * wins, and the other closes its peers with 4409, sending them back here, where the owner is now known.
 * An owner that stopped beating (killed, E7.2) still holds its lease until it expires: its peers are sent to a
 * live node, which waits that lease out and takes the room (takeLease below), instead of dialling a dead one.
 * `owner` or `alive` throwing means Redis cannot be asked: the caller answers "try again".
 * Liveness is only a hint for routing: a node wrongly thought dead costs a peer one 4409, never a second room.
 */
export function syncRouter({ nodes, owner, alive, pick = randomNode }: { nodes: SyncNodes; owner: (documentId: string) => Promise<Holder | undefined>; alive: (nodeIds: readonly string[]) => Promise<ReadonlySet<string>>; pick?: (ids: readonly string[]) => string }): (documentId: string) => Promise<string> {
  return async (documentId) => {
    if (nodes.kind === "one") return `${nodes.url}/documents/${documentId}`;
    const ids = [...nodes.nodes.keys()];
    const [holder, beating] = await Promise.all([owner(documentId), alive(ids)]);
    // Owned by a node this table does not name: sending the peer anywhere else would loop on 4409 for ever.
    if (holder && !nodes.nodes.has(holder.nodeId)) throw new Error(`the room is owned by sync node "${holder.nodeId}", which is not in the routing table`);
    const live = ids.filter((id) => beating.has(id));
    // Nobody beating at all (Redis just restarted, or heartbeats cannot be written): route as if all were alive.
    const id = holder && (beating.has(holder.nodeId) || live.length === 0) ? holder.nodeId : pick(live.length > 0 ? live : ids);
    return `${nodes.nodes.get(id) ?? ""}/documents/${documentId}`;
  };
}

The router's contract, in order. An owner that beats: its address. An owner that stopped beating: any live node, which will wait the dead lease out (section 4). No owner: any live node, whose first peer takes the lease. Nobody beating at all: route as if everyone were alive, because "no heartbeats" after a Redis restart must not mean "no service". An owner the table does not name: an error, because sending the peer anywhere else would bounce on 4409 for ever, and a loud error is how a misconfigured table is found. And Redis unreachable propagates, so the caller can say "try again" honestly. pick is injectable so the tests can force a first dial to the wrong node, which is how the race in F20 is provoked on purpose.

  /**
   * Takes the document's lease (when there are several nodes), then loads the room. Never rejects.
   * `forget` drops this room from `rooms` if it is still the current one there.
   */
  async function open(documentId: string, orgId: string, forget: () => void): Promise<Opened> {
    const owned = (loaded: Loaded, release: () => Promise<void>): Owned => ({ ...loaded, sockets: new Set(), lost: false, release });
    if (!lease) {
      const loaded = await load(documentId, orgId);
      return "closeCode" in loaded ? loaded : owned(loaded, () => Promise.resolve());
    }
    const { leases, nodeId } = lease;
    // The largest token that ever claimed the document (E7.3): ours must be above it, even after a Redis flush.
    let floor = 0;
    if (store) {
      let fence;
      try {
        fence = await store.fence(orgId, documentId);
      } catch {
        return { closeCode: CLOSE.unavailable };
      }
      if (fence === undefined) return { closeCode: CLOSE.documentNotFound };
      floor = fence;
    }
    let holder: Holder;
    let acquiredAt: number; // BEFORE the winning send: our deadline must never outlast Redis's (lease.ts)
    try {
      // Another live node owns the room: its peers are sent back to /session, which names the owner. A dead
      // one's lease (or our own previous run's) is waited out here, up to one ttl, and then the room is ours (F21).
      const taken = await takeLease({
        acquire: () => leases.acquire(documentId, nodeId, floor), alive: async (id) => (await leases.alive([id])).has(id),
        nodeId, ttlMs: leases.ttlMs, now: () => performance.now(), sleep: (ms) => new Promise((resolve) => setTimeout(resolve, ms).unref()),
      });
      if (!taken) return { closeCode: CLOSE.roomElsewhere };
      ({ holder, acquiredAt } = taken);
    } catch (err) {
      // Redis cannot say who owns it: opening anyway could make a second room. "Try again" instead.
      log(documentId, `lease not taken: ${err instanceof Error ? err.message : "unknown"}`);
      return { closeCode: CLOSE.unavailable };
    }
    // Renewal starts NOW, not after the load: a long replay must not let the lease lapse unnoticed.
    const opened: { room?: Owned } = {}; // filled once loaded
    // The lease ran out (our clock) or the journal fenced us (a newer owner claimed the document): stop writing,
    // send the peers to the new owner.
    const drop = (why: string): void => {
      clearInterval(renewing);
      const { room } = opened;
      if (!room || room.lost) return; // still loading: the check after load() below refuses it
      log(documentId, `lease ${String(holder.token)} ${why}: its peers are sent to the new owner`);
      room.lost = true;
      room.snapshot?.stop();
      forget(); // the next peer asks Redis again
      for (const socket of room.sockets) socket.close(CLOSE.roomElsewhere, "room_elsewhere");
    };
    const keeper = keepLease({
      renew: () => leases.renew(documentId, holder), ttlMs: leases.ttlMs, now: () => performance.now(), acquiredAt,
      onLost: () => { drop("lost"); },
    });
    const renewing = setInterval(() => void keeper.tick(), leases.ttlMs / 3);
    renewing.unref();
    const release = async (): Promise<void> => {
      clearInterval(renewing);
      if (!keeper.held) return;
      await leases.release(documentId, holder).catch((err: unknown) => {
        log(documentId, `lease not released, it expires by itself: ${err instanceof Error ? err.message : "unknown"}`);
      });
    };

Read drop and keepLease's onLost together: when the deadline passes or a renewal is refused, the room is marked lost, snapshots stop, the room is forgotten (so the next peer asks Redis again rather than joining a corpse), and every socket is closed with 4409. Renewal starts before load(), because replaying a long journal can take longer than a third of a ttl. And a room whose lease lapsed during the load is refused at the end (!keeper.held), released, and answered 4409, so a peer never joins a room that is already dead.

Heartbeats. Every node writes node:<id> with an expiry of a third of a ttl, every tenth of one. A killed node is known dead within ttl/3, long before any of its leases expire. Two things are not done with that knowledge, on purpose. It does not decide ownership: the router uses it only to choose where a peer is sent, and a node wrongly thought dead costs a peer one 4409, never a second room. And it does not steal: a lease held by a node that stopped beating is still that node's until Redis lets it go, because "stopped beating" and "stopped writing" are different facts (a paused node does neither, and wakes).

From packages/lease/src/lease.ts

/**
 * A node's first peer of a room has arrived: take the lease. Held by a live node: refused at once (its peers
 * go to the owner). Held by a node that stopped beating, or under OUR id by a run of this node that is gone
 * (killed and restarted): that lease can only expire, so wait for it, polling, for at most one ttl, then take
 * the room (F21). Never stolen early: until it expires, the dead holder's lease is the only truth there is.
 * `acquiredAt` is read BEFORE the winning acquire was sent (keepLease's deadline counts from it).
 * ponytail: polls every ttl/10 rather than waiting for the key's exact expiry; ceiling: the takeover lands up to
 * ttl/10 after the lease expired. Upgrade: return the PTTL from the acquire script and sleep exactly that.
 */
export async function takeLease({ acquire, alive, nodeId, ttlMs, now, sleep }: { acquire: () => Promise<{ acquired: boolean; holder: Holder }>; alive: (nodeId: string) => Promise<boolean>; nodeId: string; ttlMs: number; now: () => number; sleep: (ms: number) => Promise<void> }): Promise<{ holder: Holder; acquiredAt: number } | undefined> {
  const giveUpAt = now() + ttlMs + ttlMs / 10;
  for (;;) {
    const acquiredAt = now();
    const taken = await acquire();
    if (taken.acquired) return { holder: taken.holder, acquiredAt };
    if (taken.holder.nodeId !== nodeId && (await alive(taken.holder.nodeId))) return undefined;
    if (now() >= giveUpAt) return undefined; // it did not expire when it should have: renewed after all
    await sleep(ttlMs / 10);
  }
}

Waiting the lease out. takeLease is the pure decision a node makes when its first peer of a room arrives and the acquire is refused. Held by a live node: refuse at once, the peer belongs with the owner. Held by a node that stopped beating, or by our own id from a previous run that was killed: poll every ttl/10 until the lease expires, then take it; if it does not expire within about a ttl it was renewed after all, so refuse. The peer's socket stays open the whole time, connecting, so the takeover lands within ttl/10 of the expiry rather than at the peer's next backoff. This is also what retires E7.1's ponytail: a restarted node no longer bounces its own peers with 4409 for up to a ttl.

The for (;;) with a return in the middle is the idiom for a poll with a deadline; acquiredAt is read before each acquire is sent, for the reason section 2 gave. The sleep is injected and the tests wind a fake clock through it, so a test of "waited out, taken within a poll of expiry" runs in microseconds and asserts on exact numbers.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

Stealing the lease as soon as the heartbeat is gone was rejected.

It would make failover take ttl/3 instead of a ttl. It would also make a paused owner's writes overlap with the new owner's from the moment of the steal, with nothing yet to stop them (the fence is E7.3, built after). Even with the fence, a steal turns "the old owner is fenced when it wakes" from a rare event into the normal one, and every op it accepted meanwhile is an op its peers were told about and the journal refused. Waiting for the expiry keeps the invariant that at most one node believes it owns a room at any wall-clock moment, except during a pause, and pauses are what the fence is for.

Shortening peer-client's backoff was rejected.

The second-ttl delay came from the client's retry curve: a peer that bounced on 4409 backed off, and by the time it asked again the lease had long expired. The tempting fix is a faster curve. The chosen one is that the server holds the connecting peer while it waits the lease out, so the bound on takeover comes from the node, and every client, including the worker's peers, gets it without touching their retry behaviour.

CAP, honestly: during the ttl after a kill the room is unavailable: the old owner is gone, the new one refuses to take the room until the lease expires, and peers hold their edits. That is a consistency-over-availability choice, made because two rooms for one document is a divergence the design cannot repair (lesson 2), while a ten-second pause is something peer-client already absorbs. The dial is LEASE_TTL_MS: shorter means faster failover and more false losses under load (a renewal that misses its window by a scheduler hiccup drops a healthy room); longer means the reverse. Ten seconds, renewed every three, is the default; the chaos run's budget is expressed in ttl so the test moves with the dial.

5 · The fence: the check and the write are one statement

Section 2 ended with the argument: a process frozen past its lease cannot know it, so the storage must refuse it. F22 spells the fault out twice: docker pause the owner past its lease and resume it; and cut the owner off from Redis while Postgres still answers (a partition, scripted with toxiproxy). In both, the old owner wakes believing it owns the room, with ops queued and appends in flight, and the journal must end with no gap, no duplicate, and no row from it after the new owner read the journal.

Three statements, and the whole feature is in how they relate. fence reads the largest token that ever claimed the document; the acquire in section 1 takes it as the floor, so a token issued after a Redis flush is still above every token the journal has seen. claim is how an opening becomes the document's only writer: one update that moves fence_token up to the lease token and sets fence_claim to a fresh random id, guarded by fence_token < $3. Strictly less, not less-or-equal: two openings under one token (a node paused between acquire and claim, then a flush that reissues the number) cannot both claim. append is one statement: insert ... select ... from documents where ... fence_claim is not distinct from $9 for update. If the row still names this opening's claim, the row is written; if not, zero rows, and the store throws Fenced.

Why the check must be in the statement rather than before it is the naive control in fence.int, and it is exactly the interleaving a pause produces: A reads the claim (still its own), freezes, B claims and reads the journal, A wakes and inserts. A read-then-write in app code lets that row in, one past what B read, so B's room never has it and B's next append collides on the seq. In one statement Postgres does the work. FOR UPDATE takes a row lock on the documents row, so an append and a claim on the same document serialise: the claim waits for an in-flight insert to commit (and B's replay then contains that row, correctly, because it was written under a claim that was still valid), or the claim commits first, and the append, which was blocked on the lock, re-evaluates its WHERE against the updated row (Postgres's behaviour under READ COMMITTED when a locked row changed) and inserts nothing. The test "an append racing an uncommitted claim waits for it, then is refused" is that second branch, with two real connections.

 * document, so this room must stop at once and send its peers to that owner. The refusal itself still reaches
 * the room (which answers "unavailable" and applies nothing); any other failure is only an outage, left to
 * E6.1b's read-only mode. `onFenced` runs once, however many queued appends are refused after it.

export function watchFence<A extends unknown[], R>(append: (...args: A) => Promise<R>, onFenced: () => void): (...args: A) => Promise<R> {
  let fenced = false;
  return async (...args) => {
    try {
      return await append(...args);
    } catch (err) {
      if (err instanceof Fenced && !fenced) {
        fenced = true;
        onFenced();
      }
      throw err;
    }
  };
}

      append: watchFence((op: SequencedOp) => bounded(store.append(orgId, documentId, op, fence?.claim)), () => {
        fenced = true;
        fence?.onFenced();
      }),
      find: (actorId: string, opId: string) => bounded(store.find(orgId, documentId, actorId, opId)),
      everAdded: (nodeId: string) => bounded(store.everAdded(orgId, documentId, nodeId)),
      since: (after: number) => bounded(store.since(orgId, documentId, after)),
    };

watchFence is a higher-order function typed with a tuple rest parameter, the same shape as lesson 6's guard: it wraps the append, keeps its signature, and tells the server once when a Fenced comes through, however many queued ops are refused behind it. The distinction it draws is the design decision of the bead: a fence is not an outage. Lesson 6's read-only mode is for a journal that will answer again; a fenced room will never be allowed to write again, so it must not sit in a heal loop pinging the database for ever. onFenced calls the same drop a lost lease calls: 4409 to every socket, snapshots stopped, room forgotten. onReadOnly checks fenced first so the heal loop is never started. The refusal itself still reaches the room, which answers "unavailable" to a socket that is already closing and applies nothing.

const STREAMS = ["upstream", "downstream"] as const;
async function toxics(node: string, cut: boolean): Promise<void> {
  for (const stream of STREAMS) {
    const res = cut
      ? await fetch(`${toxiproxy}/proxies/${node}/toxics`, { method: "POST", body: JSON.stringify({ name: `cut-${stream}`, type: "timeout", stream, toxicity: 1, attributes: { timeout: 0 } }) })

  }
}

A node acquires token 7, is paused before it claims, Redis is flushed, another node acquires and gets 7 again from a floor of 6, claims, and reads the journal. The distributed-systems shape, in one sentence: the lease says who should write, the clock says how long they may believe it, and the storage says whose writes actually land, by comparing a token the writer received when it became the owner. Chubby's sequencers, ZooKeeper's zxid, Kafka's producer epoch and etcd's revision are the same third piece with other names. A design with only the first two is the one Kleppmann's essay takes apart.

Why Redis is enough here. The lease is a performance mechanism in this design, not a safety one. Its job is to make sure that, almost always, exactly one node believes it owns a room, so that peers are not bounced and ops are not refused. Safety, the guarantee that no two writers ever both land rows for one document, is Postgres's job through the fence, and Postgres was already the truth for the journal. A consensus system would make the lease itself more reliable, at the cost of a second quorum to run, and it would still need the fence in the storage, because a leader elected by Raft can also be paused. Kleppmann's point is that the lock service is the wrong place to look for safety whatever it is built on.

What is not solved. A room moves only when its owner dies or lets go; there is no rebalancing, so a node that happened to be picked for many free rooms keeps them. The pick for a free room is random among live nodes, with no load signal. Both are named ponytails with an obvious upgrade (a room count per node in Redis, read by pick). Failover takes one ttl, which is visible: peers show "offline" for up to ten seconds. And redis-proxy is in the path of every run, not only chaos runs, one hop and one container that a compose override would move aside.

Redis flushed while everything runs. Every lease disappears at once. Every owner's next renewal is refused (the key is gone), so every room drops its peers within a third of a ttl; every peer asks /session, which sees no owner and picks a live node (or, with no heartbeats written yet, any node); the node acquires with a floor read from fence_token, so its token is above every claim the journal has seen, claims, replays, and opens. No op is lost: acknowledged ops are in the journal, in-flight ones are held by peer-client and re-offered after the next welcome. SPEC §4's row, Redis lost: leases re-acquired; no document data lost, is this paragraph.

The interview answer in one breath: one lease per document in Redis with a monotonic token from the same script; holders trust it for 0.9 ttl from the send on their own monotonic clock; heartbeats route but never decide; a dead lease is waited out, never stolen; and the write path in Postgres checks a per-opening claim in the same statement that inserts, so a zombie's writes are refused whatever it believes. Consistency over availability for up to one ttl, by choice, because two rooms for one document cannot be repaired.

1. A holder could trust its lease until "the renewal's reply arrived plus ttl", read from Date.now(). Instead it trusts until "the renewal was sent plus 0.9 ttl" on performance.now(), and the doc comment says this is "not safety". Defend all three choices, then say what the fourth mechanism is that makes it safe.

Redis starts its expiry countdown when the command arrives, which is after we sent it; so a deadline counted from the send can never outlast Redis's, while one counted from the reply trusts the lease for a whole round trip longer than Redis will keep it, and under a slow network that is a window in which two nodes both believe they own the room. The 0.9 is the allowance for the two clocks running at slightly different rates. performance.now() is monotonic: it cannot jump when NTP corrects the wall clock, and a backwards jump of Date.now() would extend a deadline by exactly the jump. "Not safety" because none of this runs while the process is frozen: a pause of two seconds inside an await resumes with the flag still true and the next instruction already chosen, and the learning test measured the other node owning the room 1.7 s before the frozen one could notice. The fourth mechanism is the fence: the storage compares a token the writer received when it became the owner, in the statement that writes, so what a frozen process believes is irrelevant to what lands. The clock bounds failover time; the token gives safety; neither does the other's job.

2. When an owner's heartbeat stops, the other node could take the room at once. Instead it sends new peers to a live node that polls until the dead lease expires, up to about one ttl, and never steals. Why, and why is the same rule applied to a node's own previous lease?

Because "stopped beating" is not "stopped writing". A killed node does neither; a paused node does neither and then wakes; a node cut off from Redis stops beating and keeps its Postgres connection. Stealing on a missed heartbeat would make the paused case the normal one: two nodes owning a room from the moment of the steal until the old one's clock runs out, and every op the old one accepts in that window an op its peers were told about that the fence must then refuse. Waiting for the expiry keeps the invariant that at most one node believes it owns the room at any moment, pauses aside, and turns the fence into the rare backstop it should be. Liveness therefore only chooses where a peer is sent (a wrong guess costs one 4409), and the lease alone says who owns. A node's own dead lease is the same case seen from inside: the previous run was killed mid-room, its lease is real until Redis lets it go, and the new run cannot renew a holder value it does not have, so the honest thing is to wait exactly as it would for a stranger's. Doing that on the server, with the peer held connecting, is also what bounds failover to one ttl rather than a ttl plus a client backoff.

3. The fence compares a random claim id in insert ... select ... where fence_claim is not distinct from $9 for update, and claim uses strictly <. Why not read the claim first in TypeScript and then insert; why a claim id and not "token at least the largest seen"; why < and not <=; and what does for update buy?

Read-then-write has an await between the two, and a process can be frozen for a minute inside an await: A reads its claim (valid), freezes, B claims and reads the journal, A wakes and inserts a row one past what B read. The naive control in fence.int performs exactly that and asserts the zombie row is in the journal. In one statement the check and the write cannot be separated by a pause. A token high-water mark fails for two reasons specific to this repo: the counter lives in Redis and a flush restarts it, so the floor from fence_token is needed to keep tokens rising at all; and even then one token can be issued twice (a node paused between acquire and claim, then a flush that reissues the number), so the thing an append carries is an id of this one opening, and the loser of two openings under an equal token cannot write. < rather than <= is the same case at the claim: with <= both openings under token 7 would claim and both would hold a valid claim id. for update takes a row lock on the documents row so that an append and a claim serialise: the claim waits for an in-flight insert to commit (and the new owner's replay then contains the row), or the claim commits first and the blocked append re-evaluates its where against the updated row and inserts nothing. Without the lock the two could interleave at the statement level and the "waits, then is refused" test would not hold.
