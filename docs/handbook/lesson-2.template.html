One room, many peers

The win: you can explain, to an interviewer or to yourself, how several people edit one document at once and all end up with the same one, and you can point at the line of code for every claim.

How to use this page. Every code block is cut from the repo at commit {{COMMIT}}, so what you read is what runs. It is long: one section a day is a fine pace. Sections 3, 5 and 9 are the ones an architect interview will dig into.

./init.sh                             # Postgres + api + sync
pnpm --filter @noon/web dev         # the canvas, http://localhost:5173
make sim                           # the reconcile simulator, every committed seed
node apps/sync/src/sim-cli.ts --seed 7 --trace | head -40

Try it: open http://localhost:5173 in two windows, press New document in one, paste its address into the other, and edit in both.

D3 · Explain a decision before reading mine. Answer out loud or on paper, then open the answer.

1. Why is the server the only thing that orders ops, instead of a CRDT that lets every peer merge on its own?

A design tree has invariants a merge function cannot see locally: no cycles, a parent must accept children, props must match the component. A single sequencer makes every peer apply the same ops in the same order through the same validator, so the invariants hold by construction, and "who won" is one integer comparison. The price is that editing needs the server: offline edits are optimistic guesses that may be refused. For a team tool with a server anyway (auth, AI, git), that is the cheap side of the trade. A CRDT earns its complexity when peers must merge with no server at all.

2. The replica is pure (no socket, no timer) and the transport is separate. What did that buy, concretely?

Seventy-odd rules tested in under a second with no network; a property test over random histories; a simulator that drives the real code deterministically; and one client for the browser, the AI worker and the git peer, because only the thin shell knows what a WebSocket is. The same split on the server (room versus server) bought the same things.

3. Presence is relayed by the same room. Why does it not go through the op pipeline?

It has none of an op's needs and all of its costs. Nobody needs cursors in order, durable, deduplicated or replayable; they need the latest one, now. Through the pipeline every pointer move would take a sequence number, a journal row and a slot in the dedupe memory, and a fast pointer would starve real edits of their budget. So: no queue, no seq, no persist, latest wins, and silence removes a peer.

Recall first

Look away. Name the room's checks in order, from a frame arriving to a broadcast, and for two of them say which bug put them where they are. Then check.

Check yourself

Budget, on arrival (floods piled up behind a slow journal) → seen this (sender, opId)? answer as before (honest resends were refused as duplicates) → older than anything remembered? stale (a resend was applied twice) → the document's rules, precise reason → the room's limits (a move escaped the depth cap) → persist, and only then take the seq (no gaps, nobody hears of an op that could be lost) → apply → remember → broadcast, serialised once; the sender's copy is its acknowledgement.

Then test it

Eight questions. Options are shuffled each visit.

1. In the default branch of a switch over all four op types, what is the type of op, and why assign it to a never variable?

After every member is handled nothing is left: the empty type. The assignment only compiles while that stays true.

2. The room has no lock. Why can two ops still interleave wrongly without the promise queue?

Single-threaded means interleaving only at an await. The queue makes each op wait for the one before it.

3. Why does the room check "have I seen this opId?" BEFORE validating the op?

A client that lost its acknowledgement sends again and must get the ORIGINAL answer.

4. An op comes back stale after a server restart. It was already on the wire of an earlier connection. What does the replica do, and why?

"Would change the document" is not "was not applied". Resending could put an old write over a newer one, or re-add a deleted node.

5. rebuild() copies only the node MAP and shares the node objects with the confirmed document. What makes that safe?

Immutability by discipline, enforced by a property test that freezes the nodes and runs sixty random histories.

6. Where is the rate-limit token spent, and what went wrong when it was spent elsewhere?

Limit where work ARRIVES, not where it is processed.

7. Why is peer.doc useless as a useSyncExternalStore snapshot?

React compares snapshots with Object.is. The snapshot is built from revision, pendingCount, status and presenceRevision.

8. The simulator's replay check passed even when last-writer-wins was broken inside doc-model. Why?

An oracle must not share code with what it judges. The fix computes "the latest write per prop" from first principles.
