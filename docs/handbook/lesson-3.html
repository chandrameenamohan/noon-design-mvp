The map: an instruction becomes ops

Epic 3 adds an AI that edits the document. One decision shapes everything that follows: the AI is not a feature bolted onto the document. It is one more peer on the same write path. It joins the room with a session token, it submits ops through peer-client, the room validates and orders them like anyone's, and its edits reach every canvas the way a colleague's do. Nothing in epic 2 was changed to let it in. What epic 3 adds is around the edges: how the work starts, how it is bounded, how it stops, and what it cost.

1 · Redis is not the truth

The first decision: where does a run live? Not in Redis. A row in the jobs table is the run: its input, its status, its start and end, its reason for failing. The queue carries one thing, a note saying "go and look at job X". A note can be lost, delivered twice, delivered late, or forged. None of that can change what a job is or does, because the row decides.

From packages/queue/src/index.ts

/**
 * ALL a queue message carries: where to look in Postgres. The job's input and status live in the
 * `jobs` table, so a lost, duplicated or stale message can never change what a job is or does.
 */
export const JobRef = z.strictObject({ queue: z.enum(QUEUES), jobId: Id, orgId: Id });

The api writes the row first and enqueues second. If Redis is away the enqueue throws, and the api still answers 201: the run exists. Failing the request would invite a retry, and a retry would create a second run.

From apps/api/src/app.ts

  // An AI run (F9) is a job: the row in Postgres IS the run; the queue only tells a worker to look.
  app.post("/documents/:id/runs", async (c) => {
    const doc = await db.getDocumentForMember(c.req.param("id"), c.var.user.id);
    if (!doc) return notFound(c);
    const { instruction } = await body(c, CreateRunBody);
    const run = await db.forOrg(doc.orgId).createRun({ documentId: doc.id, instruction, createdBy: c.var.user.id });
    if (!run) return notFound(c); // the document was deleted in between
    if (run === "busy") return fail(c, 409, "run_in_progress");
    try {
      await enqueue({ queue: "ai", jobId: run.id, orgId: run.orgId });
    } catch (err) {
      // Still a 201: the run exists and the worker's sweep will pick it up. Failing the request would
      // invite a retry, and a second run (idempotency keys are E9).
      process.stderr.write(`${JSON.stringify({ level: "warn", path: c.req.path, message: `enqueue failed, left to the sweep: ${describeError(err)}` })}\n`);
    }
    return c.json(run, 201);
  });

The worker's side of the bargain is claim(): one UPDATE that turns queued into running and returns the row. A message that arrives twice finds nothing to claim the second time. A stale message for a finished job finds nothing. A message that names a job of another queue, or of another org, finds nothing: the WHERE checks all three before anything is written.

From apps/worker/src/worker.ts

Because Redis can be flushed (SPEC §2a measured it: FLUSHALL loses every job) and the api can die between its INSERT and its enqueue, the worker sweeps: every few seconds it asks Postgres "what is still queued?" and offers those to the queue again. The jobId makes a second offer harmless: BullMQ drops an add for an id it already holds, and if it did not, claim() would.

From apps/worker/src/worker.ts

  // Redis is not the truth (SPEC §2.9): it can be flushed, and the api can die between its INSERT
  // and its enqueue. Whatever Postgres still calls `queued` is offered again; jobId + claim() make
  // a second offer harmless. ponytail: a poll; LISTEN/NOTIFY or an outbox if `sweepMs` is ever too slow.
  const producer = createProducer({ redisUrl, ...scoped });

    }

2 · A state machine that cannot lie

A job has five statuses and three timestamps. In most codebases the rules between them live in application code: "if you set failed, also set error". Any new code path can forget one. Here the rules live in the table, as CHECK constraints, so no path can store a half-finished row: not the worker, not a migration script, not a person at psql.

From packages/db/migrations/0004_jobs.sql

create table jobs (
  id          uuid primary key default gen_random_uuid(),
  org_id      uuid not null references orgs (id) on delete cascade,
  document_id uuid not null,
  queue       text not null check (queue in ('ai', 'git', 'ship', 'sandbox')),
  status      text not null default 'queued' check (status in ('queued', 'running', 'succeeded', 'failed', 'cancelled')),
  input       jsonb not null,
  -- A short named reason, never a stack trace or a database message: the user reads this.
  error       text check (length(error) between 1 and 200),
  created_by  uuid references users (id) on delete set null,
  created_at  timestamptz not null default now(),
  started_at  timestamptz,
  finished_at timestamptz,
  -- The database, not the application, guarantees a job's org matches its document's org.
  foreign key (document_id, org_id) references documents (id, org_id) on delete cascade,
  -- A terminal status has an end time and only a failure has a reason. No path can store a half-finished row.
  check ((finished_at is not null) = (status in ('succeeded', 'failed', 'cancelled'))),
  check ((error is not null) = (status = 'failed'))
);

Read the last two checks slowly. (finished_at is not null) = (status in (...)) is a biconditional: terminal if and only if it has an end time. (error is not null) = (status = 'failed'): a reason if and only if it failed. Two lines, and a whole class of bug cannot exist.

The composite foreign key is the tenancy rule in the same style: a job's org must match its document's org, and the database, not the application, guarantees it.

The review added two more rules. A failure reason is a name: the user reads it and the UI turns it into a sentence, so it can never be an error message, which may carry a path, a request id or a piece of someone's prompt. And one unfinished AI run per document: a partial unique index, which is both the rule and the concurrency check.

From packages/db/migrations/0005_jobs_review.sql

-- A failure reason is a NAME (token_missing, rate_limited, internal): the user reads it, so it can
-- never be an error message, which may carry a path, a request id or a piece of someone's prompt.
alter table jobs drop constraint jobs_error_check;
alter table jobs add constraint jobs_error_is_a_name check (error ~ '^[a-z][a-z0-9_]{0,63}$');

-- One unfinished AI run per document. Two agents rewriting one tree at once help nobody, and from
-- E3.2 every run is a paid model call: without this, a loop of POSTs is a bill and a queue that
-- starves every other org. Per-org limits and the 429 are F31 (E9); this is the floor under them.
create unique index jobs_one_unfinished_run_per_document on jobs (document_id) where queue = 'ai' and status in ('queued', 'running');

The index is the check. "Count the unfinished runs, then insert" is two statements, and two requests in the same millisecond both count zero. One INSERT that violates the index is one statement, and Postgres decides who was first. The db layer turns that one constraint into the value "busy", and the route into a 409.

3 · Everything a program awaits needs an end

The theme of the epic, and the one you will meet again in every language: anything a program awaits needs an end from outside. Epic 3 met that wait five times over: a queue add, a whole run, a tool call, a poll loop and a shutdown. Not one of them had an end when first written.

The producer. With Redis away, ioredis reconnects for ever, and waitUntilReady() and add() never settle. The HTTP request that awaited them simply hung; 80 seconds later it still had. enableOfflineQueue: false alone does not help: the promise is the problem, not the queue. So every call a request waits on gets its own deadline:

From packages/queue/src/index.ts

  // While Redis is away ioredis reconnects for ever and nothing settles (measured: the HTTP request
  // simply hung, and 80 s later still had). The caller gets an answer within the deadline instead.
  async function withinDeadline(work: (queue: Queue) => Promise<unknown>, name: QueueName): Promise<void> {
    const queue = queueFor(name);
    const attempt = queue.waitUntilReady().then(() => work(queue));
    // When the deadline wins, `attempt` is still out there and may fail later. A rejection nobody
    // handles ends a Node process. (The case the review reproduced, a close() in mid-handshake, is
    // cured in close() below and tested; this line is for the failures we have not met yet.)
    attempt.catch(() => undefined);
    let timer: NodeJS.Timeout | undefined;
    const deadline = new Promise<never>((_, reject) => {
      timer = setTimeout(() => { reject(new Error(`redis did not answer within ${String(timeoutMs)} ms`)); }, timeoutMs);
    });
    try {
      await Promise.race([attempt, deadline]);
    } finally {
      clearTimeout(timer);
    }
  }

Three details carry the pattern. Promise.race picks the first to settle; the loser is still running. So the loser gets a .catch now, because a rejection nobody handles ends a Node process. And the timer is cleared in finally, or a fast success would leave a timer behind.

The run. A run must end, whatever happens around it. Left running, its row blocks the document's next run for ever and holds one of the worker's four slots. So the handler builds one promise, ended, that only ever rejects, and always with a name the user can read:

From apps/worker/src/ai.ts

    // A run must END, whatever happens around it. Left `running`, its row blocks this document's next
    // run for ever (one unfinished run per document) and holds one of the worker's few slots. So three
    // things can end it from outside, each with a name the user can read; whichever comes first wins.
    const abort = new AbortController();
    let watchdog: NodeJS.Timeout | undefined;
    const ended = new Promise<never>((_, reject) => {
      const end = (reason: string): void => { reject(new JobFailure(reason)); };
      stopping.addEventListener("abort", () => { end("worker_stopped"); }, { once: true, signal: abort.signal });
      cancelled.addEventListener("abort", () => { end("cancelled"); }, { once: true, signal: abort.signal }); // F10: the ops already applied stay // SIGTERM: say so NOW, inside the shutdown deadline
      const deadline = Date.now() + runTimeoutMs;
      let silentSince = Date.now();
      watchdog = setInterval(() => {
        if (peer.status === "live") silentSince = Date.now();
        // peer-client retries a lost server for ever, and an op it cannot send is never answered: the tool
        // call waiting on it would never return. Closing the peer (below) answers it: connection_closed.
        if (peer.closedBecause !== undefined || Date.now() - silentSince > connectTimeoutMs) end("sync_unreachable");
        else if (Date.now() > deadline) end("timed_out");
      }, 50);
    });
    ended.catch(() => undefined);

Then everything the run does is raced against it:

From apps/worker/src/ai.ts

    try {

Look at what finally does. It clears the watchdog. It aborts, which stops the model and removes the listener on stopping (the signal option of addEventListener: a listener that would otherwise outlive the run). And it closes the peer, which answers any tool call still waiting on an op with connection_closed. Three waits, three ends.

The shutdown. BullMQ's polite close() talks to Redis. With Redis gone it waits for a connection that is not coming back: docker stop worker took 9 seconds and exited 1. So the worker asks Redis first and forces the close if there is no answer. Nothing is lost by that: a job's result lives in Postgres, not in BullMQ's bookkeeping.

From apps/worker/src/worker.ts

    async close() {

      // Redis, and with Redis gone it waits for a connection that is not coming back: `docker stop`
      // took 9 s and ended in exit 1 (found by the re-verify). So ask Redis first; no answer = force.

export function checkInit(init: Init, tools: Pick<AgentTool, "name">[]): void {

  // writes plausible fake tool calls as text (SPEC §2a). The init message is the only place it shows.
  if ([...wanted].some((name) => !init.tools.includes(name))) throw new JobFailure("tools_missing");

  // directory; ours is empty, see EMPTY_DIR). Anything installed from outside is not.
  // Leftover skills and slash commands are NOT checked: they vary by SDK version and are inert without the Skill tool.

  // (a helper, a managed login): the run would be billed to an account nobody chose.
  if (init.apiKeySource !== "none") throw new JobFailure("wrong_credentials");

5 · A tool call is a request that can be refused

F11 says: an invalid AI op is rejected like any other and reported back to the agent as a tool error. That sentence hides a design problem. A person watches a canvas: a refused op simply disappears from it, and a quiet message says why. A program cannot watch a canvas. It needs an answer per op: applied, or not, and why.

So epic 3 added one thing to peer-client and nothing to the room: submit() now returns a promise of the op's outcome, settled when the server has answered.

From packages/peer-client/src/replica.ts

/**
 * The end of the story for ONE op of ours. A person watches the canvas; a program (the AI worker's
 * tool call, F11) needs an answer per op. `seq` is missing when the op was accepted but changed nothing.
 */
export type Outcome = { ok: true; seq?: number } | { ok: false; reason: Rejection["reason"] };

From packages/peer-client/src/peer.ts

      // A peer that has ended accepts nothing: finish() has already reported what was lost, and nothing
      // would ever answer (or even send) this op, so its `settled` would hang for ever.
      if (closedBecause !== undefined) return { ok: false, reason: "not_ready" };

      if (!result.ok) return result;

      const settled = result.queued ? new Promise<Outcome>((resolve) => waiting.set(result.opId, resolve)) : Promise.resolve<Outcome>({ ok: true });
      if (waitingBefore === 0 && replica.pendingCount === 1) lastHeard = Date.now(); // the silence clock starts with the first thing we wait for
      flush();
      onChange?.();

settled never rejects. Four things can happen to an op: applied with a seq; accepted but changed nothing (no seq); refused with a reason; or the connection ended before an answer, which is connection_closed. All four are values. A tool that awaited a promise that could reject would need a second error path; a tool that awaits one that always resolves has one.

The replica already knew when each op's story ended (that is where rollback happens). What was new was the promise, and with it an invariant: every op settles exactly once, ever. 6 · The instruction is data, and so is the document

The instruction is typed by a user. Any member of the org can start a run, and the model has a system prompt that grants it powers. There are two lines of defence, and only one of them is real.

The prompt fences the instruction in a tag whose name is random per run. Stripping a closing tag from the text does not work: a reviewer bypassed a string-strip eight ways (a spliced tag, a different case, whitespace inside the bracket, and so on). A tag nobody can guess cannot be closed early by any spelling. The test tries the hostile spellings and checks that the tag appears exactly twice, opening and closing, and nowhere inside:

From apps/worker/src/sdk.ts

/** The user's text inside a tag nobody can guess, so that no spelling of a closing tag can end the data early. */
export function wrapInstruction(instruction: string): { prompt: string; tag: string } {
  const tag = `instruction-${randomBytes(8).toString("hex")}`;
  // Invisible formatting characters (bidi overrides, zero-width joiners) pass the contract's
  // control-character rule; they have no business in a prompt.
  return { tag, prompt: `<${tag}>\n${instruction.replace(/\p{Cf}/gu, "")}\n</${tag}>` };
}

8 · Counting what it cost

What a run consumed is stored against the org. The first design question is where. Columns on the jobs row are the obvious place and the wrong one: a job is deleted with its document (cascade), and what was spent must not disappear with it. So usage is its own table, with the org as the only hard owner and every other link loose on purpose:

From packages/db/migrations/0007_usage.sql

-- F12: what a run cost, against the org. Its OWN table, not columns on jobs: a job goes when its
-- document goes (cascade), and what was spent must not disappear with it. So the links to the job,
-- the document and the user are loose on purpose; only the org is a hard owner.
create table usage (
  id                 uuid primary key default gen_random_uuid(),
  org_id             uuid not null references orgs (id) on delete cascade,

  // storable, or one absurd field from the provider would cost the run its whole row.

}

D3 · Explain a decision before reading mine. Answer out loud or on paper, then open the answer.

1. Why does the queue message carry only {queue, jobId, orgId}, and not the instruction itself?

Because then the message cannot matter. A message can be lost (Redis flushed), duplicated (a redelivery), stale (a finished job), or forged (anyone who can reach Redis). If it carried the input, each of those would be a way to run the wrong work, or the same work twice. Carrying only a pointer makes every one of them harmless: the worker claims the row with one UPDATE ... WHERE status = 'queued', reads the input from the row, and a message that finds nothing to claim does nothing. It also makes the sweep possible: what Postgres still calls queued can be offered again without knowing anything else. The price is one extra read per job, which is nothing next to a model call.

2. Why is usage its own table, and not four columns on the jobs row?

Lifetimes. A job dies with its document (cascade), and a document dies with its workspace; what an org spent must outlive all of them, or a bill can be made smaller by deleting things. So usage has one hard owner, the org, and its links to the job, the document and the user are loose on purpose: set null, or no foreign key at all. Two more things fall out of the table being separate: the unique job_id gives at-most-once billing for free, and the write can be an insert ... select from the job row, so tenancy comes from the row and never from a caller. The price is a join to show usage next to a run, which E9.5 will pay.

3. Why does the agent have no write path of its own? A direct "apply these ops to the document" call from the worker would be faster.

Because every property the room gives a person would then have to be built again for the AI, and one of them would be missed. Through peer-client the AI's ops are validated by the same rules, ordered by the same sequencer, rate-limited by their own bucket, stamped with an actor from the token (so a tool cannot claim to be a person), rolled back the same way when refused, and shown on every canvas one by one as they land. Concurrent human edits during a run are then an ordinary case, not a special one, and a prompt injection can at most do what a member with a mouse could do. The speed a direct path would buy is measured in milliseconds; the model call it sits inside is measured in seconds.

Check yourself

From outside: the worker is told to stop (worker_stopped, SIGTERM), the user pressed cancel (cancelled, polled from the row once a second), and the watchdog: the peer is not live for too long (sync_unreachable) or the run is over its deadline (timed_out). Whichever comes first wins, through one ended promise that only rejects. An op: applied with a seq; accepted but changed nothing (no seq); refused with a reason (by the replica now, or by the room later); or the connection ended first (connection_closed). All four are values of settled, and each op settles exactly once.

Then test it

Eight questions. Options are shuffled each visit.

1. A BullMQ message is delivered twice for the same run. What stops the run from happening twice?

The row is the truth. A duplicate, stale or forged message finds nothing to claim and ends there.

2. Two POST /runs for one document arrive in the same millisecond. Why does exactly one get a 201?

"Count, then insert" is two statements and both requests count zero. The index is the check, and Postgres decides who was first.

3. Promise.race([attempt, deadline]) and the deadline wins. What is true of attempt?

A race only picks the first to settle. The loser needs a .catch now, and usually an abort.

4. What does options.env do to the SDK's subprocess?

Measured. That is why the child gets PATH, HOME and the token, and never the database URL or the session secret.

A tool ANSWERS whatever happens. isError: true with a reason is how the model learns; a thrown error would be a second path to forget.

Read "how it is now" in a second statement: under READ COMMITTED each statement gets a fresh snapshot; inside one statement, nothing new.

The org is the only hard owner. Loose links on purpose, and unique (job_id) for at-most-once billing.
