D3 · Explain a decision before reading mine. Answer out loud or on paper, then open the answer.

1. The idempotency key is claimed with insert ... on conflict do nothing inside the transaction that makes the job, before the job exists; a replay is answered by reading the job's row; a run that was refused as busy rolls the claim back. Defend each against the obvious alternative (a look-then-insert, storing the first response, recording the refusal), and say what Postgres does to the second of two claims at the same moment.

A look-then-insert has an await between the look and the insert, and twenty requests that arrive together all look before any inserts: each finds nothing and each makes a job; the unique constraint then fails nineteen of them and the code must catch the error and read again, which is the same statement the design starts from, written the long way. With on conflict do nothing the claim and the check are one statement, and the second transaction to insert the same primary key blocks on the first's uncommitted row until it commits or rolls back: if it committed, the loser gets rowCount 0, reads the winner's row in a statement of its own (a statement started earlier would not see the commit) and answers with the winner's job; if it rolled back, the key is free and the loser becomes the winner. Storing the first response, as Stripe does, would answer queued to a retry of a run that is now running; the person retrying wants to know where the job is, and the job's row is the truth, so the replay reads it. Recording a refusal under the key is right for a declined payment and wrong for a busy document: the person who got the 409 waits and presses again with the same request, and a recorded 409 would answer 409 for 24 hours; rolling the claim back with the refused run makes the key as if never sent, so the retry after the busy run ends may use it. Scoping the key to (org, user) keeps a key from ever resolving to another tenant's job, and storing the request lets the same key with another instruction be refused as 422 rather than silently answered with the wrong job.

2. A running job heartbeats its row every second; a sweep requeues one silent for 15 s; every write of an attempt carries and attempts = $n. Why is a heartbeat not a lease, why does the sweep need the fence, and what does a worker that was only slow experience?

A lease (lesson 7) is a promise with a deadline: the holder knows until when it may act, renews before then, and gives up on its own clock; it is the right tool where the holder must act alone for a while, like a room ordering ops. A heartbeat is a report with no promise: the worker says "alive a second ago" and has no idea whether anyone still believes it; the decision to give the job away is made by whoever reads the row. That is enough where the work can be handed to someone else and the only harm of a wrong guess is a duplicate, provided the duplicate is made harmless, which is the fence's job. The sweep needs it because a timeout cannot tell slow from dead: a 20-second GC pause, a blocked event loop or a partition from Postgres looks exactly like kill -9 for 15 seconds, and the sweep will requeue a job whose worker is about to wake. Without the fence, that worker's finish("succeeded") lands on the row attempt 2 is running, and attempt 2's own finish later updates nothing because the status is no longer running. With it, the slow worker's next beat returns no row, the store reads that as lost, the worker aborts its handler with a warning, and its finish, its beats and its progress reports all match zero rows: they land nowhere. The sweep itself is one statement with for update skip locked so every worker process may run it and two never take the same row, coalesce(heartbeat_at, started_at) so rows from before the migration are judged too, and a bound of three claims so a job that kills its worker every time still ends, as worker_lost.

3. The AI run limit is one upsert on a rate_limits row, taken inside the run's transaction before the insert, with Retry-After computed from clock_timestamp(); Redis INCR was rejected. Why each, and what does a fixed window get wrong that a token bucket gets right?

Counting in Postgres makes the count shared across every api instance (a counter per process allows N times the limit) without a second store: with Redis, the code must decide what to do when Redis is away, and both answers are bad under load (open: every org unlimited exactly when the system is struggling; closed: no runs with Postgres healthy). Inside the run's transaction, before the insert, makes the count exactly the runs that exist: a busy document, a vanished one, a replayed key and a refused run are all rolled back with their hit, so nothing needs a compensating decrement, and a refused request's idempotency claim rolls back too, so the retry after Retry-After may reuse the key. The upsert is atomic per row, so two hits at one moment take turns, and greatest(win) keeps a hit that computed its window before a boundary but reached the row after one computed past it from moving the row back and resetting the count. clock_timestamp() rather than now() because now() is the transaction's start and this is several statements in, and the database's clock rather than the api's so two instances with drifting clocks give one wait; the wait is rounded up and never under one second so a client that waits exactly what it was told is let in. A fixed window lets a key spend its whole limit in the last second of one window and again in the first of the next, twice the rate for a moment; a token bucket refills at a steady rate and allows a burst only up to the bucket's size, which is the shape most public APIs want, and it costs two columns (level, last refill) and a little arithmetic in the same upsert. For sixty AI runs an hour the boundary burst is a nuisance and not a cost, so the fixed window stayed and the ponytail is named where it lives.

Recall first

Look away. Name the three parts of a retry system and what this epic uses for each. Then say which X-Forwarded-For entry is the client and under what condition the header is read at all. Then check.

Check yourself

Detection: a 1 s heartbeat on the row, read by a sweep that calls 15 s of silence stale. Redelivery: the row back to queued, offered again in the same sweep, at most three claims, then worker_lost. Fencing: the attempt number in every write's where, so a worker wrongly given up on writes nothing and learns lost on its next beat. The client is the rightmost entry that is not itself a trusted proxy, walking from the right and skipping trusted hops; and the header is read only when the TCP peer is a trusted proxy (TRUST_PROXY: loopback on the host, loopback and private in compose), otherwise the peer is the client and the header is ignored.

Then test it

Eight questions. Options are shuffled each visit.

1. Twenty requests carrying the same Idempotency-Key arrive within a millisecond. What happens?

No lock is named: the primary key does it. The test asserts twenty 201s, one row in jobs, one id in every answer.

2. The same key arrives with a different instruction. And a request refused as busy: what does its key do?

Stripe records refusals because a declined card must stay declined on retry; a busy document is a wait, not a verdict.

3. A worker's event loop blocks for 20 seconds mid-job. The sweep has requeued the job and another worker is running it as attempt 2. The first worker wakes and calls finish("succeeded"). What happens?

A timeout cannot tell slow from dead, so every false positive would be a duplicate without the fence; the test bumps attempts by hand under an open handler and watches the finish land nowhere.

4. Why does the AI run's op id hash the op's content, not only (job, step)?

Two runs never collide anyway: the job id is in the hash. The content makes "the same step, a different action" a different op.

5. Redis is flushed while three runs wait in bull:ai:wait and four are running. What brings the three back, and what happens to the four?

No production code changed for this bead; the chaos judge asks for attempts = 1 on every run and refuses a round that wiped an empty queue.

6. A slow dead attempt reports its steps after attempt 2 has started. What does the panel show?

The integration test reports from attempt 1 after the requeue and after attempt 2's claim, and asserts an empty list both times.

7. Why is the AI run limit counted in Postgres inside the run's transaction rather than with Redis INCR + EXPIRE?

The flush is true too, but incidental: the deciding questions are "what when the store is away" and "how is a refused run uncounted".

8. X-Forwarded-For: 10.0.0.1, 1.2.3.4, 198.51.100.1 arrives from a loopback peer with TRUST_PROXY=loopback. Who is charged?

From an untrusted peer the header is ignored entirely; the integration test sends four different headers over a real socket to an api that trusts nobody and gets [200, 200, 200, 429].
