The map: the loop closes

Epic 4 turned a document into one file and ran it. Epic 5 closes the loop: an engineer's push to that file becomes ops on the open canvas, a push that breaks the file's fixed shape becomes a banner and nothing else, and one press of Ship becomes one pull request that a second press updates. Along the way the sandbox lost its network and gained a token, because a preview reachable by anyone holding a document id is not a preview you can put behind a public URL. Nothing in the room changed. Git is one more peer, and like the AI and the preview it writes through the same door every browser tab uses.

Four ideas carry the epic. At least once plus a database key is exactly once (sections 4 and 5): Gitea does not retry, so there is a second door, and both doors meet at one unique constraint. Git is a peer, not a writer (section 6): every change to a document goes through the room, so the git peer submits ops and the room may refuse them one by one. The diff is three-way (section 6): what the engineer changed, replayed on the document as it is now, never the pushed file against the document. And idempotence lives in an index, and the commit is recorded before the push (section 8). Section 2 is a security boundary that had to be rebuilt before any of this could be shown to anyone.

1 · Gitea joins the stack, and the sandbox clones through the worker

The stack gains a git server it owns. Gitea runs in compose on the host's loopback (3002: the api and sync have 3000 and 3001), with SQLite, no install page, no registration, sign-in to view, and one permitted webhook host: api. Everything init.sh does to it is scripted and safe to run again: make the user noon (admin is a reserved name, measured in the learning test), keep the worker's token while Gitea still accepts it and mint one otherwise, then bootstrap the repo.

Read the shell carefully: the password and the token reach curl through a config file on stdin (curl_with), never as an argument, because arguments are visible to every process on the machine. The bootstrap is a TypeScript script run by Node directly (no build step), and its first job is to make the seed the same commit everywhere: git commit-tree HEAD:seed/sample-app with a fixed author and date builds a commit from objects already in this repository, so the same tree gives the same id on every machine and every run.

From scripts/gitea.ts

/**
 * The seed as ONE commit whose tree is seed/sample-app at HEAD, made from this repository's own objects:
 * no temp directory, nothing uncommitted. A fixed author and date, so the same tree gives the same commit
 * id on every machine and every run.
 */
export async function seedCommit(): Promise<string> {
  const who = { GIT_AUTHOR_NAME: "noon", GIT_AUTHOR_EMAIL: "noon@localhost", GIT_AUTHOR_DATE: "2026-01-01T00:00:00Z" };
  const env = { ...process.env, ...who, GIT_COMMITTER_NAME: who.GIT_AUTHOR_NAME, GIT_COMMITTER_EMAIL: who.GIT_AUTHOR_EMAIL, GIT_COMMITTER_DATE: who.GIT_AUTHOR_DATE };
  return (await exec("git", ["-C", REPO_ROOT, "commit-tree", "-m", "seed: the sample app", "HEAD:seed/sample-app"], { env })).stdout.trim();
}

/** Pushes the seed commit as `main` of `remote` (a URL or a local path). The token goes as a header, never into the URL. */
export async function pushSeed(remote: string, auth?: { user: string; token: string }): Promise<string> {
  const commit = await seedCommit();
  const header = auth ? { GIT_CONFIG_COUNT: "1", GIT_CONFIG_KEY_0: "http.extraHeader", GIT_CONFIG_VALUE_0: `Authorization: Basic ${Buffer.from(`${auth.user}:${auth.token}`).toString("base64")}` } : {};
  await exec("git", ["-C", REPO_ROOT, "push", "--quiet", "--", remote, `${commit}:refs/heads/main`], { env: { ...process.env, GIT_TERMINAL_PROMPT: "0", ...header } });
  return commit;
}

export async function bootstrapGitea(setup: GiteaSetup): Promise<void> {
  const api = async (method: string, path: string, body?: unknown): Promise<Response> => {
    const res = await fetch(`${setup.url}/api/v1${path}`, {
      method,
      headers: { authorization: `token ${setup.token}`, "content-type": "application/json" },
      ...(body === undefined ? {} : { body: JSON.stringify(body) }),
    });
    // 409 on create is "it exists already", which a second run expects.
    if (!res.ok && !(method === "POST" && path === "/user/repos" && res.status === 409)) throw new Error(`Gitea ${method} ${path} -> ${String(res.status)}: ${await res.text()}`);
    return res;
  };
  const repo = `/repos/${setup.user}/${setup.repo}`;
  // Private: the worker reads it with the token, and nobody else on this machine reads it at all.
  await api("POST", "/user/repos", { name: setup.repo, private: true, default_branch: "main" });
  // Only an EMPTY repo gets the seed: after the first run it holds the owner's commits, never overwritten.
  const { empty } = (await (await api("GET", repo)).json()) as { empty?: unknown };
  if (empty === true) await pushSeed(`${setup.url}/${setup.user}/${setup.repo}.git`, { user: setup.user, token: setup.token });
  // One hook per URL, its secret kept in step with .env: updated when it exists, made when it does not.
  const hook = { active: true, events: ["push"], config: { url: setup.webhook.url, content_type: "json", secret: setup.webhook.secret } };
  const hooks = (await (await api("GET", `${repo}/hooks`)).json()) as Hook[];
  const ours = hooks.find((each) => each.config.url === setup.webhook.url);
  if (ours) await api("PATCH", `${repo}/hooks/${String(ours.id)}`, hook);
  else await api("POST", `${repo}/hooks`, { type: "gitea", ...hook });
}

The sandbox cannot reach Gitea, on purpose. Since noon-9gz (section 2) each sandbox sits on its own --internal Docker network: no egress, no host.docker.internal, no other sandbox. So it cannot clone. The worker, which is on the compose network, keeps a bare mirror per seed URL, fetches it on every start, and hands main over as a git bundle by docker exec into the sandbox's /tmp, the way it already hands over the page. From apps/worker/src/sandbox.ts

/**
 * Hands the seed to a container that just started: `main` as a git bundle, written into its /tmp, where
 * start.sh waits for it and clones from it. The sandbox has no route to Gitea (its network is --internal,
 * noon-9gz), so the worker, which has one, fetches and hands the history over by `docker exec`, the way it
 * already hands over the page. The clone's `origin` is that file: no host, no credential for customer code
 * to read in .git/config (noon-9gz note e). Written under another name and renamed: start.sh never reads half.
 * Rejected: a route from the proxy to Gitea (customer code would reach every repo the token reads).
 */
async function deliverSeed(docker: string, name: string, seed: SeedRepo, deadline: AbortSignal): Promise<void> {
  const bundle = await bundleOf(seed, deadline);
  await dockerCli(docker, ["exec", "--interactive", name, "sh", "-c", `cat > ${SEED_BUNDLE}.part && mv ${SEED_BUNDLE}.part ${SEED_BUNDLE}`], deadline, bundle);
}

/**
 * `main` of the seed repo as a bundle, from this process's bare mirror of it, fetched first: every start
 * gets what Gitea has now. One git at a time per mirror. The pid is in the path: test files share a /tmp.
 * ponytail: the mirror lives in /tmp (a restarted worker clones it again) and the bundle is held whole in
 * memory, up to the sandbox's 64m /tmp. Ceiling: repos of that size; upgrade: the git peer's mirror volume
 * (SPEC §2.15) and a bundle piped straight into `docker exec`.
 */
function bundleOf(seed: SeedRepo, deadline: AbortSignal): Promise<Buffer> {
  const mirror = joinPath(tmpdir(), `noon-seed-${String(process.pid)}-${fingerprint(seed.url)}.git`);
  const git = async (...args: string[]): Promise<Buffer> => (await cli("git", args, deadline, { env: gitEnv(seed), name: `git ${args.join(" ")}` })).stdout;
  const next = (mirrors.get(mirror) ?? Promise.resolve(Buffer.alloc(0))).catch(() => undefined).then(async () => {
    // "--" : a URL is never an option. A clone killed halfway is finished by the next fetch.
    if (existsSync(joinPath(mirror, "HEAD"))) await git("-C", mirror, "fetch", "--quiet", "--prune", "origin");
    else await git("clone", "--quiet", "--mirror", "--", seed.url, mirror);
    return git("-C", mirror, "bundle", "create", "--quiet", "-", "main");
  });
  mirrors.set(mirror, next);
  return next;
}

Two details are the whole reliability story. The bundle is written under another name and renamed (cat > x.part && mv x.part x), so start.sh, which polls for the file, never reads half of one: a rename is atomic on one filesystem. And mirrors is a Map from mirror path to the last fetch-and-bundle promise: a new start chains onto the previous one with .catch(() => undefined).then(...), so two starts never run git in one mirror at once (git takes ref locks and the loser would fail). That is a mutex written as a promise chain, the JavaScript way of "one at a time per key". Section 8 uses the same shape for pull requests.

A sandbox with no route out could not clone, and routing the proxy to Gitea would have leaked every repo.

The obvious fix after noon-9gz's --internal network was a route from the pool's proxy to Gitea. 2 · One door with a token: the sandbox proxy, and the public URL

This section is two beads (noon-l96, noon-9gz) and a security review, and it had to land before the loop could be shown to anyone outside the machine. The problem: showing the app through a tunnel (ngrok's free plan: one hostname, no wildcards) meant the iframe's http://127.0.0.1:<port> was the visitor's loopback, and mixed content under https besides. So the preview had to ride the canvas's own origin, path-based: /preview/<document>/.... And once anyone with the URL can reach a preview, a document id alone must open nothing.

The token. Every sandbox's dev server serves under a base of /preview/<document>/<nonce>.<hmac>/, where the nonce is fresh for every container the worker creates and the HMAC signs document and nonce under a key only the worker and the pool's proxy hold. Two locks: the proxy refuses any token it did not see signed for that document (a guess, another document's, a bare id), and the sandbox refuses a token of an earlier container of the same document (its base does not match: a bare 404). A URL lives exactly as long as its container.

const sandboxAt = (documentId: string): { host: string; port: number } => ({ host: `noon-sandbox-${documentId}`, port: 5173 });

const mac = (key: string, documentId: string, nonce: string): string => createHmac("sha256", key).update(`${documentId}/${nonce}`).digest("hex").slice(0, 32);

/** The path segment after the document id. `nonce` is 16 hex digits, fresh for every container. */
export const previewToken = (key: string, documentId: string, nonce: string): string => `${nonce}.${mac(key, documentId, nonce)}`;

/** The document a request may reach, or undefined when it may reach nothing. */
export function previewDocument(key: string, url: string): string | undefined {
  const [, documentId, nonce, given] = PATH.exec(url) ?? [];
  if (documentId === undefined || nonce === undefined || given === undefined) return undefined;
  return timingSafeEqual(Buffer.from(mac(key, documentId, nonce)), Buffer.from(given)) ? documentId : undefined;
}

Read previewDocument: timingSafeEqual, not ===. A string compare returns at the first differing byte, and the time it takes tells an attacker how many bytes they have right. The regex fixes both strings at 32 hex digits before the compare, because timingSafeEqual throws on different lengths. The same two lines guard the webhook in section 4.

      forward.write(head);
      forward.pipe(socket);
      socket.pipe(forward);
    });
    forward.on("error", () => { socket.destroy(); });
    socket.on("close", () => { forward.destroy(); });

The proxy is Node's standard library and nothing else: node:http's createServer for requests, request to forward them, and the server's upgrade event for WebSockets, where the HTTP handshake is replayed by hand over a raw node:net socket and the bytes are piped both ways. It has to be stdlib-only because of where it runs: inside the sandbox image, handed to Node as a string (node --input-type=module-typescript -e: Node 24 strips the types of a script it was given on the command line too). No second image to build or keep in step; a label on the container names the program and key it runs, so a changed program or key is a container made anew.

3 · Reading the file back: parse is the inverse of generate

Keystone 8 has two directions. generate (lesson 4) takes a tree to one file of a fixed shape. parse takes a file back to a tree, only while it still has that shape, and every way out of the shape has a name and a line number, because that is what the conflict banner shows. The file is untrusted input: anyone who can push wrote it.

From packages/codegen/src/parse.ts

/**
 * Keystone 8, the way back: a generated file that an engineer edited and pushed becomes a document
 * again, but ONLY while it still has the shape `generate()` writes. Everything else is a conflict
 * (F16b), and the conflict must say why, so every way out of the shape has its own reason.
 *
 * The file is untrusted input: anyone who can push to the repo wrote it. So it is PARSED, never run
 * (TypeScript's own parser, syntax only, no program and no type checker), sizes are capped before

 * its syntax, never by evaluating it.

Three decisions follow from "untrusted". /** A refusal that carries the line it is about. Thrown inside the walk, caught once in `parse`. */
class OutOfShape extends Error {
  readonly reason: ParseReason;
  constructor(reason: ParseReason, message: string) {
    super(message);
    this.reason = reason;
  }
}

/** Never throws, like `generate`: the caller is the git webhook's job handler, and a reason is what the conflict banner shows. */
export function parse(tsx: string, manifest: Manifest): Parsed {
  try {
    if (typeof tsx !== "string") return { ok: false, reason: "malformed_doc", detail: "the file is not text" };
    if (tsx.length > MAX_BYTES) return { ok: false, reason: "too_large", detail: `larger than ${String(MAX_BYTES)} bytes` };
    const doc = read(tsx);
    // The contract is the trust boundary for everything a document may hold: node ids, prop values
    // (control characters, -0), sizes. What the room would refuse from an op is refused here too.
    const contract = Doc.safeParse(doc);
    if (!contract.success) return { ok: false, reason: "malformed_doc", detail: contract.error.issues.map((issue) => issue.message).slice(0, 3).join("; ") };
    const generated = generate(doc, manifest);
    return generated.ok ? { ok: true, doc } : generated;
  } catch (err) {
    if (err instanceof OutOfShape) return { ok: false, reason: err.reason, detail: err.message };
    // TypeScript's parser recurses: nesting far past MAX_DEPTH (still under MAX_BYTES) overflows its stack.
    if (err instanceof RangeError) return { ok: false, reason: "too_deep", detail: "nested too deeply to read" };
    return { ok: false, reason: "malformed_doc", detail: "the file could not be read" };
  }
}

OutOfShape is a class extending Error with a readonly reason field assigned in the constructor. Note what it is not: a parameter property (constructor(readonly reason: ...)), which this repo bans (erasableSyntaxOnly), because Node's type stripping cannot erase syntax that generates code. The walk throws it from wherever the shape breaks; parse catches once, at the top, and turns it into a value. A RangeError there is not a bug: TypeScript's parser recurses, and a file nested far past our depth cap overflows its stack before our cap is checked; that is a reason (too_deep), not a crash.

/** A prop's value, read from its syntax only: a string, a finite number (optionally negated), true or false. */
function literal(name: string, attribute: ts.JsxAttribute, out: Out): PropValue {
  const init = attribute.initializer;
  if (!init) return true; // `<Button disabled />` is JSX for disabled={true}
  if (ts.isStringLiteral(init)) {
    // A quoted JSX attribute has no escapes but DOES decode HTML entities when compiled: the text
    // TypeScript hands back is the raw one, so a `&` would mean one thing here and another in the page.
    if (init.text.includes("&")) throw out(init, "non_literal_prop", "a quoted attribute with & is decoded as HTML; write it as {\"...\"}");
    return init.text;
  }
  const expression = ts.isJsxExpression(init) ? init.expression : undefined;
  if (expression) {
    if (ts.isStringLiteral(expression)) return expression.text;
    if (expression.kind === ts.SyntaxKind.TrueKeyword) return true;
    if (expression.kind === ts.SyntaxKind.FalseKeyword) return false;
    const negative = ts.isPrefixUnaryExpression(expression) && expression.operator === ts.SyntaxKind.MinusToken;
    const operand = negative ? expression.operand : expression;
    if (ts.isNumericLiteral(operand)) {
      // TypeScript normalises the literal's text (0x10 -> "16", separators dropped), so Number() reads a decimal.
      const value = Number(operand.text);
      if (Number.isFinite(value)) return negative ? -value : value;
    }
  }
  throw out(init, expression ? reasonFor(expression, "non_literal_prop") : "non_literal_prop", `${name} must be a literal string, number or boolean`);
}

const HEX_SIGNATURE = /^[0-9a-f]{64}$/;

/**
 * True when `header` is the hex HMAC-SHA256 of these exact bytes under `secret` (X-Gitea-Signature,
 * learning-tests/gitea FINDINGS 3). The RAW body is signed: a parse-and-reserialise would verify
 * something Gitea never sent. Compared in constant time; a malformed header is refused before any compare.

export function signatureMatches(raw: Buffer, header: string | undefined, secret: string): boolean {
  if (header === undefined || !HEX_SIGNATURE.test(header)) return false;
  const expected = createHmac("sha256", secret).update(raw).digest();
  return timingSafeEqual(expected, Buffer.from(header, "hex")); // both 32 bytes: the regex fixed the length
}

/** What a VERIFIED push body says. Only ref/before/after are read: the commit list is truncated for big pushes, so the git peer reads the mirror. */
export function readPush(raw: Buffer): PushReading {
  let json: unknown;
  try {
    json = JSON.parse(raw.toString("utf8"));
  } catch {
    return { kind: "invalid", error: "invalid_json" };
  }
  const parsed = Push.safeParse(json);
  if (!parsed.success) return { kind: "invalid", error: "invalid_body" };
  const { ref, before, after } = parsed.data;
  if (!BRANCH.test(ref)) return { kind: "ignored", reason: "not_a_branch" };
  if (ZERO.test(after)) return { kind: "ignored", reason: "deleted" };
  // Registering the hook fires a push whose `before` is all zeros (FINDINGS 2). A real new branch looks the
  // same and is ignored too: the git peer's reconcile finds it in the mirror (SPEC §2a).
  if (ZERO.test(before)) return { kind: "ignored", reason: "synthetic" };
  return { kind: "event", ref, before, after };
}

Only ref, before and after are read. Gitea truncates the commit list for big pushes, so the file lists in the payload are not trusted for anything; the git peer reads its mirror instead. Two pushes are ignored rather than stored: a deleted branch (after all zeros), and the push Gitea fires the moment a hook is registered (before all zeros, learning-tests/gitea FINDINGS 2). A real new branch looks exactly like the registration push, so it is ignored too, and the reconcile finds it. The BRANCH regex with its three negative lookaheads ((?!-), (?!.*\.\.), (?!.*//)) narrows a ref name to what a person pushes, because the name becomes a row, a log line and, in section 6, a git argument.

5 · At least once, exactly once, and the second door

A webhook is at-least-once delivery at best, and Gitea's is worse: a failed delivery is never retried (SPEC §2a, measured in the learning test). So the api cannot be the only way a push is noticed, and a push noticed twice must be worked once. Both problems are solved in the same table.

  async function processNext(): Promise<boolean> {
    const event = await store.claim();
    if (!event) return false;
    const worktree = join(worktrees, event.id);
    try {
      if (!(await has(event.after))) {
        try {
          await fetch();
        } catch (err) {
          // Gitea is away: the event waits again rather than being lost (the reconcile would never re-record it).
          await store.finish(event.id, "pending");
          log(`fetch failed, ${event.ref} ${event.after} waits: ${describeError(err)}`);
          return false;
        }
        // Fetched, and still not there: force-pushed away before we looked. Nothing to apply, ever.
        if (!(await has(event.after))) throw new Error(`commit ${event.after} of ${event.ref} is not in the repo`);
      }
      await mkdir(worktrees, { recursive: true });
      await git("-C", mirror, "worktree", "add", "--quiet", "--detach", worktree, event.after);
      let base: Promise<string | undefined> | undefined;
      for (const page of await changedPages(event, worktree)) await apply(event, page, async () => pageBase(await (base ??= baseCommit(event)), page.path));
      await store.finish(event.id, "done");
    } catch (err) {
      log(`${event.ref} ${event.after} failed: ${describeError(err)}`);
      await store.finish(event.id, "failed");
    } finally {
      await removeWorktree(worktree);
    }
    return true;
  }

Each event is worked in its own worktree (git worktree add --detach), removed in finally by three steps that each tolerate the others' failure, and swept at start after a crash. A commit the mirror does not have is fetched; if the fetch fails, the event goes back to pending rather than failed, because the reconcile would never re-record it and a lost push is the one thing this design exists to prevent. Fetched and still missing means force-pushed away before we looked: nothing to apply, ever.

      await rm(worktrees, { recursive: true, force: true });

        try {
          // Taken BEFORE the fetch: a document opened while it runs asks again, and is not lost.
          if ((await store.takeReconcileRequest()) || Date.now() >= nextReconcile) {
            nextReconcile = Date.now() + reconcileMs;
            await reconcile();
          }
        } catch (err) {
          nextReconcile = Date.now() + Math.min(reconcileMs, 10_000); // Gitea away: again soon, not every tick
          log(`reconcile failed: ${describeError(err)}`);

        }

  } catch (err) {

Case study · found by review, by a learning test, or by a test that was written to refute a claim

A force-push back to an old commit reads as "known", and the comment says so.

Keying on (ref, after_sha) means a branch moved A → B → A records nothing the second time it points at A: the row for (ref, A) exists. This is a ponytail with a named ceiling (such reverts go unseen) and a named upgrade (key on (ref, before, after)). The reason it is acceptable today is what the loop does with events: a page that is already what the document holds produces no ops, so a missed revert is a missed no-op until the next real push.

The distributed-systems shape, in one paragraph: a producer that may deliver zero or one times; a receiver that writes an idempotent row keyed on the content, not the delivery; a second source of truth (the mirror) polled on a timer and on demand, writing through the same key; a claim that is one atomic update; and a failure mode ("the source is unreachable") that returns the work to the queue rather than ending it. Every piece is in Postgres, and none of it is in application memory.

6 · A push becomes ops: git is a peer

Keystone 2 says every change to a document goes through the room. The git peer honours it literally: it joins the document through @noon/peer-client like a browser tab, with a session token whose actor is git, and submits ops. The room stamps every op with the actor and the commit as its run, and the room may refuse any op, one by one. A push that wrote to Postgres directly would be a second write path, and the whole of epic 2 (ordering, budgets, presence, the journal to come in epic 6) would not apply to it.

export function pushOps({ base, target, current, earlierIds }: {
  /** The page before the push, if it was there and in shape. Missing: the document is the base (the push is taken as the whole page). */
  base: Doc | undefined;
  target: Doc;
  /** The document now: `peer.confirmed`, never the optimistic one. */
  current: Doc;
  /** Every node id the page has held in the repo's history up to the base: an id that is gone from the base was removed. */
  earlierIds: ReadonlySet<string>;
}): PushOps {
  if (target.rootId !== current.rootId) return { ok: false, reason: "root_mismatch", detail: `the file's page is ${target.rootId}, the document's is ${current.rootId}` };
  const from = base?.rootId === current.rootId ? base : current;
  // Keystone 4: an id that was removed is never added again, or an edit meant for the dead node would land
  // on the new one. A new id the document already holds is the same mistake, seen from the other side.
  for (const id of preorder(target)) {
    const was = nodeOf(from, id);
    if (!was && (earlierIds.has(id) || nodeOf(current, id))) return { ok: false, reason: "reused_node_id", detail: `${id} was part of this document before` };
    // No op changes what a node IS; a remove and an add would re-use its id.
    if (was && was.component !== nodeOf(target, id)?.component) return { ok: false, reason: "component_changed", detail: `${id} was a ${was.component}` };
  }

Before any op is made, two whole-page refusals. root_mismatch: the file's page is another document's. reused_node_id: keystone 4 says an id that was removed is never added again, or an edit meant for the dead node lands on the new one; "removed" is decided against every id the page ever held in the repo's history (earlierIds, from git log -p) and against the document now. component_changed: no op changes what a node is; a remove and an add would re-use its id.

      if ((Object.hasOwn(before, key) ? before[key] : undefined) !== value) emit({ type: "set_prop", nodeId: id, key, value: value ?? null });

  // subtree is one op (its descendants are gone from `working` by the time they come up).

Then the ops, in three passes over a working copy (structuredClone: a deep copy of plain data, built into modern JavaScript). Each op is tried on the copy with applyOpInto, the mutating applier from lesson 2, and only an op that changed the copy is kept: one whose node was removed on the canvas meanwhile, or whose value is already set, is dropped, which is the result the room would reach anyway. Adds first, parents before children, each placed after the previous sibling that is in place (anchor). Then props, in sorted key order, so the ops are the same on every run. Then removes, parents first, so a removed subtree is one op. /**
 * The siblings that need no move: of those that were already under this parent, the longest run that is
 * still in the old order (a longest increasing subsequence of their old positions, O(n log n)). Among
 * runs of the same length it keeps the one that ends lowest, the same one every time.
 */
function inOrder(now: readonly string[], before: readonly string[], wasHere: (id: string) => boolean): Set<string> {
  const position = new Map(before.map((id, i) => [id, i]));
  const ids = now.filter((id) => wasHere(id) && position.has(id));
  const tails: number[] = []; // tails[k]: index in `ids` of the smallest end of a run of length k+1
  const previous: number[] = [];
  ids.forEach((id, i) => {
    const p = position.get(id) ?? 0;
    let lo = 0;
    let hi = tails.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if ((position.get(ids[tails[mid] ?? 0] ?? "") ?? 0) < p) lo = mid + 1;
      else hi = mid;
    }
    previous[i] = lo > 0 ? (tails[lo - 1] ?? -1) : -1;
    tails[lo] = i;
  });
  const stays = new Set<string>();
  for (let i = tails.at(-1) ?? -1; i >= 0; i = previous[i] ?? -1) stays.add(ids[i] ?? "");
  return stays;
}

/**
 * Per document, the pull request call in flight in this process. Gitea's "one open pull request per branch" is a
 * look-then-insert on its side, not a constraint: two creates at the same instant could both pass it. So the
 * ships of one document ask one at a time. ponytail: one ship worker (compose runs one); ceiling: a second
 * process could still race Gitea; upgrade: a Postgres advisory lock per document around this call.
 */
const pullsInFlight = new Map<string, Promise<unknown>>();
function oneAtATime<T>(key: string, work: () => Promise<T>): Promise<T> {
  const next = (pullsInFlight.get(key) ?? Promise.resolve()).catch(() => undefined).then(work);
  pullsInFlight.set(key, next);
  const forget = (): void => { if (pullsInFlight.get(key) === next) pullsInFlight.delete(key); };
  next.then(forget, forget);
  return next;
}

1. The webhook already dedupes on X-Gitea-Delivery. Why is there a second unique key on (ref, after_sha), and why does dedupe live in Postgres rather than in the api?

Two reasons for the second key. First, the delivery id is a header and the HMAC signs only the body, so anyone who captured one delivery can replay the body under a made-up id and pass every check; a dedupe on the id alone is not a dedupe. Second, Gitea never retries a failed delivery, so the git peer reconciles its mirror on a timer and when a document is opened, and a reconcile has no delivery id at all. The reconcile and the webhook must meet somewhere, and (branch, commit) is the content they both know. It lives in Postgres because two doors can arrive in the same instant: a "select, then insert" in the api would let both pass, while insert ... on conflict do nothing returning id is one statement that Postgres serialises, and rowCount tells the caller who won. The test sends ten copies at once and expects one 202. The named ceiling: a branch force-pushed A → B → A reads as known; the upgrade is a key on (ref, before, after).

2. The git peer could write ops into Postgres directly; it is a trusted process on the compose network. Why does it instead open a WebSocket to our own sync server and submit ops like a browser tab? And why is the diff three-way?

Because keystone 2 says one write path, and everything epic 2 built hangs off it: the room orders ops and assigns seq, checks each op against the tree as it is now, charges the actor's budget, relays to the other peers, and (epic 6) journals for recovery. A second writer would have to reimplement all of that or bypass it, and either way two tabs and a push would no longer converge by one rule. Going through peer-client also means the room can refuse the git peer's ops one by one, exactly as it refuses a tab's, and every op is stamped actor.kind = "git" with the commit as runId, which is what the canvas shows and the e2e asserts. The diff is three-way because the engineer started from a file generated at some past moment, and the canvas has edited since. Diffing the pushed file against the document treats every one of those canvas edits as something the engineer reverted (drill 2 makes you watch it happen). Diffing base against target, and replaying onto the current document with each op tried on a copy first, sends only what the engineer changed, and lets a remove on the canvas beat an edit in the push, the same rule the room applies to two tabs.

3. "One unfinished sandbox job per document" was the right index in epic 4. Ship's index is "one queued ship per document". Why the different predicate, and why does Ship record its commit on the job before pushing it?

Because idempotence is a property of a key, and the key must be chosen from what the operation reads and when. A sandbox job reads the document continuously for as long as it runs, so a second one would be a duplicate at any point in its life: "unfinished" is right. A ship reads the document once, at the start, and then pushes what it read. A press while one runs must therefore become a second job, or the edit that prompted the press would be folded into a ship that already read the older document and would never ship. Only the waiting one is unique, so twenty presses at once make one job and a press during a run makes the next. Two ships running at once are safe without a lock because git refuses a push that is not a fast-forward (the loser builds again on top, three times, then branch_busy) and Gitea keeps one open pull request per branch (409, and the loser finds it by head.ref). The commit is recorded before the push because Ship's push comes back through the webhook like anyone's: the git peer asks "did Ship make this commit?" before it reads or opens anything, and if the answer were written after the push, the webhook could arrive first, diff Ship's page against the room, and undo a canvas edit made while the ship ran.

Check yourself

Two doors: the api's POST /webhooks/gitea (HMAC over the raw bytes, then one row with the delivery id), and the git peer's reconcile of its bare mirror (on a 30 s timer and when a document is opened; a row with no delivery id). They meet at git_events's unique key on (ref, after_sha), and on conflict do nothing makes the second arrival a duplicate whichever it was. Three documents: base, the page at the commit before the push (what the engineer started from); target, the pushed page; current, the room's confirmed document as it is now. The ops are the base-to-target changes, each tried on a copy of current and sent only if it changes something.

1. Gitea signs the webhook body. What exactly does the api compute the HMAC over, and why?

The header is not covered by the signature at all, which is why a replayed body under a fresh delivery id needs the second unique key.

The same two lines guard the sandbox proxy's token: a regex fixes the length, then a constant-time compare.

3. Gitea never retries a failed webhook delivery. What is the second door, and when does it open?

Taking the flag before the fetch means an open that arrives during the fetch sets it again and is not lost. The two doors meet at (ref, after_sha).
