The map: what identity, roles and a trail mean here

Epic 1 built the tenancy: every org route sits behind one membership query, a stranger and a missing org are the same 404 (F2), and the caller was whoever an x-dev-user header said. Epic 8 makes the caller real and asks the three questions that follow from it. Four ideas carry the epic, and they are what an interviewer will press on. Authentication is a fixed-cost function of its input (section 1): whoever you claim to be, sign-in does one slow hash and answers the same bytes, because anything that varies with whether the account exists (time, status, body) is a list of accounts for whoever asks. A session is a row, not a claim (section 2): a credential you can revoke is a row you can delete; a signed stateless token cannot be revoked without a deny list, which is a table anyway, so the browser gets a row and only the 60-second sync token stays a JWT. Authorization lives where the data is fetched (sections 3 and 4): the query that proves membership returns the role, the route declares what it needs, and the room re-reads the role where the socket lives, because a socket outlives every token. An audit trail is evidence only if its writer cannot rewrite it (section 5): the row is written by the action's own statement, and the database, not the application's manners, refuses every change.

1 · Passwords: a slow hash that describes itself, and a sign-in that costs the same for everyone

A password is a low-entropy secret: people choose them, and an attacker who steals the table will guess them offline at whatever speed the hash allows. So the hash must be slow, and, since a GPU has thousands of cores that are each slow, it must also be memory-hard, so that every parallel guess pays in RAM as well as time. SHA-256 is neither: it is designed to be fast. bcrypt is slow but uses 4 KiB; scrypt and argon2 are both. scrypt was chosen because it ships with Node (node:crypto), and argon2id, OWASP's first choice, would be the pick when a native dependency is acceptable.

From apps/api/src/password.ts

/**
 * E8.1 (F23): passwords and sign-in tokens, with Node's own crypto and nothing else.
 *
 * scrypt, because it is slow AND memory-hard (a GPU farm pays in RAM as well as time), and it ships with Node.
 * N=2^15, r=8: 32 MiB and some tens of milliseconds per guess. The stored string names its parameters, so they
 * can be raised later and every older hash still verifies.
 */
const COST = { N: 2 ** 15, r: 8, p: 1 };
const KEY_BYTES = 32;
const STORED = /^scrypt\$(\d+)\$(\d+)\$(\d+)\$([A-Za-z0-9_-]+)\$([A-Za-z0-9_-]+)$/;

function derive(password: string, salt: Buffer, cost: { N: number; r: number; p: number }): Promise<Buffer> {
  const options: ScryptOptions = { ...cost, maxmem: 256 * cost.N * cost.r };
  return new Promise((resolve, reject) => {
    // NFKC: the same password typed on two keyboards can arrive as two byte sequences (NIST 800-63B asks for this).
    scrypt(password.normalize("NFKC"), salt, KEY_BYTES, options, (err, key) => {
      if (err) reject(err);
      else resolve(key);
    });
  });
}

Read the numbers. scrypt's memory is 128 · N · r bytes: with N = 2^15 and r = 8 that is 32 MiB per guess, and some tens of milliseconds on a laptop core. Node's default maxmem is exactly 32 MiB and the derivation would throw at the boundary, so the options pass 256 · N · r: room for the parameters to rise. The stored string names N, r and p, which is what lets the cost go up next year without a migration: an old hash still verifies with the parameters it names, and the row is rewritten at the person's next sign-in if anyone wants that. Django and Spring's DelegatingPasswordEncoder store their hashes the same way, for the same reason. NFKC is NIST 800-63B's advice: the same password typed on two keyboards can arrive as two byte sequences (é as one code point or as e plus a combining accent), and without normalising, one of them would be refused.

From apps/api/src/password.ts

export async function hashPassword(password: string): Promise<string> {
  const salt = randomBytes(16);
  const key = await derive(password, salt, COST);
  return `scrypt$${String(COST.N)}$${String(COST.r)}$${String(COST.p)}$${salt.toString("base64url")}$${key.toString("base64url")}`;
}

/** Constant time over the derived key. A stored string that is not ours (or asks for absurd work) is simply "no". */
export async function verifyPassword(password: string, stored: string): Promise<boolean> {
  const match = STORED.exec(stored);
  if (!match) return false;
  const [N, r, p] = [Number(match[1]), Number(match[2]), Number(match[3])];
  // A row edited to ask for 2^40 would be a denial of service on every sign-in; ours never exceed these.
  if (N > 2 ** 20 || r > 16 || p > 4) return false;
  const expected = Buffer.from(match[5] ?? "", "base64url");
  if (expected.length !== KEY_BYTES) return false;
  // Parameters scrypt refuses (N not a power of two, say) reject: that is a no as well.
  const key = await derive(password, Buffer.from(match[4] ?? "", "base64url"), { N, r, p }).catch(() => undefined);
  return key !== undefined && timingSafeEqual(key, expected);
}

Three decisions in verifyPassword, each a small test. Constant time over the key. timingSafeEqual compares every byte whatever the first mismatch; a plain === on Buffers returns at the first difference, and a network attacker with enough samples can read the position of the mismatch out of the response time. Java's MessageDigest.isEqual and Python's hmac.compare_digest exist for the same reason. A ceiling on the parameters. The stored string is data from a database row, and a row that someone edited to ask for N = 2^40 would turn every sign-in of that account into a denial of service on the api; the ceiling refuses it as a plain false. A refusal by scrypt is a no, not a crash. N that is not a power of two makes Node throw; the .catch(() => undefined) turns that into "does not match", so a tampered row cannot 500 the route either.

Now the sign-in route itself, and the decision the whole section turns on: no user enumeration. Two branches look alike to a compiler, "no such email" and "wrong password", and the naive code answers the first one at once, without hashing anything. That answer arrives tens of milliseconds sooner, and a caller who times it learns which emails have accounts: the list a credential-stuffing run starts from. So an unknown email is verified against a real scrypt hash of a password nobody knows, both branches cost exactly one hash, and both answer the same bytes. The dummy is computed once and warmed at startup, in buildApp: were it lazy, the first unknown email would pay for two hashes, which is a tell of its own. Drill 2 plants the naive version.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

The dummy hash is warmed at startup, not on the first miss.

The obvious shape is a lazy dummyHash() that computes on first use. Then the first sign-in with an unknown email costs two scrypt derivations, the dummy's and the comparison's, and answers noticeably later than every later miss: one request that stands out is enough to say "that email was the first unknown one". buildApp starts the computation and drops the promise; dummy ??= makes every later caller await the same one.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

The parameter ceiling exists because a stored hash is input, not truth.

Nothing in the type system distinguishes a hash the app wrote from one an operator pasted into a row. Without the ceiling, a row asking for N = 2^40 would make every sign-in of that account allocate terabytes and time out, and a database write becomes a way to take the api down one account at a time. The test feeds scrypt$1099511627776$... and asks for a plain false, and the same test refuses N = 3 (not a power of two) without a throw.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

Sign-in that validated like sign-up was rejected.

Reusing SignUpBody for sign-in would answer 400 "must be at least 8 characters" to a short password, which tells the caller something about the account's rules before any hash is computed, and separates "malformed" from "wrong" in the status code. SignInBody keeps only the caps, so that everything that is not a match is one 401 with one body.

The principle: an authentication endpoint is a function whose cost and whose answer must not depend on the secret it is protecting. Slow hashing protects the table if it leaks; constant-time comparison protects the comparison; the dummy hash protects the existence of the account. Miss any one and an attacker learns something for free. The rate limiter that E9.6 plugs into allowAttempt is the fourth layer, against online guessing at scrypt's price per try.

2 · Sessions: a row, a cookie, and why not a JWT

Signing in produces a session, and the first design question is what a session is. This repo already had one signed stateless token (E1.5's HS256 JWT that opens a document's socket for 60 seconds), so the tempting answer was a second one for the browser. It was rejected for one reason that decides most session designs: revocation. A signed token is valid until it expires, wherever it is; to revoke one early you need a deny list the server consults on every request, and a deny list is a table. So the browser's session is a table row from the start, and the token is 32 random bytes that mean nothing except "look me up".

From apps/api/src/identity.ts

/** The cookie a signed-in browser carries (E8.1). HttpOnly and SameSite=Strict: see app.ts, where it is set. */
export const SESSION_COOKIE = "noon_session";

/**
 * E8.1 (F23): the caller is whoever holds a live sign-in session. The cookie's token is hashed and looked up;
 * a malformed one is never sent to the database. One indexed READ per request, no write (the E1.4 finding):
 * the expiry is fixed at sign-in, never slid forward.
 */
export const sessionIdentity: Identify = async (c, db) => {
  const token = getCookie(c, SESSION_COOKIE);
  return isSessionToken(token) ? db.userForSession(hashToken(token)) : undefined;
};

/** Development: a session first, so sign-in works there as it does everywhere, and the header when there is none. */
const developmentIdentity: Identify = async (c, db) => (await sessionIdentity(c, db)) ?? devHeaderIdentity(c, db);

/**
 * Only the literal "development" turns the header on. "test" does not: an image built in CI and
 * promoted with NODE_ENV=test must not accept it. Tests pass the strategy they want directly.
 */
export const chooseIdentity = (nodeEnv: "development" | "test" | "production"): Identify =>
  nodeEnv === "development" ? developmentIdentity : sessionIdentity;

Two hashes appear in this epic and they are chosen on opposite principles. The password gets scrypt, slow and memory-hard, because a password can be guessed. The session token gets one SHA-256, fast, because 256 random bits cannot be guessed at any speed: the hash is there so that a read of the table (a backup, a log line with a query in it) hands nobody a live session, not to slow an attacker down. Hashing a high-entropy token with a KDF would cost tens of milliseconds on every request for no security. isSessionToken refuses anything that is not exactly the 43 base64url characters newSessionToken makes, so a malformed cookie never reaches the database.

Each cookie flag is one attack. HttpOnly: a script on the page cannot read it, so a cross-site-scripting bug cannot exfiltrate the session (it can still act as the user while the page is open, which is why the rest of the app renders every string from the wire as text). Secure: the browser never sends it over plain http, except in development, where the app is served on localhost over http and a Secure cookie would never come back; config.ts turns it off for the literal development and nothing else. SameSite=Strict: the browser does not attach it to any request that starts from another site, which is the whole CSRF defence here. Epic 1 already refused bodies that are not application/json, which stops the form-post variant of CSRF; but POST /documents/:id/session reads no body and so never passed through body(), and only the cookie attribute protects it. The price of Strict is that a person arriving from a link in an email is signed out for that first navigation; the design accepts it.

signedIn mints a new token on every sign-in rather than reusing one a browser might already hold: the session-fixation attack is to plant a known cookie in a victim's browser and wait for them to sign in with it. And the expiry is fixed at sign-in, never slid forward on use, for the reason E1.4 found about the dev header: a sliding expiry makes every request a write (an UPDATE of expires_at), which takes a row lock and rules out a read replica; a fixed one makes userForSession a pure indexed read. One statement does three things: sweeps this user's expired rows (a ponytail: someone who never signs in again keeps dead rows, and a periodic delete is the upgrade), inserts the new session, and writes the sign-in into the audit trail of every org the user belongs to, which is section 5's rule applied here: the row cannot exist without the event, nor the event without the row. A writable CTE (with gone as (delete ...), s as (insert ... returning ...) insert ...) is Postgres's way to make several writes one statement, and therefore one atomic step, without an explicit transaction.

Principal-level point: pick the hash by the entropy of what it protects, and pick the token by how you will revoke it. Low entropy (a password): a KDF, slow and memory-hard. Must work across processes that never talk, for seconds (the sync token): a signature, with a short life as the only revocation, and section 4 shows what to do when even that is too long.

3 · Roles at the query: the row that proves membership carries the role

Epic 1's door is a join: select o.*, m.role from orgs o join memberships m on m.org_id = o.id where o.id = $1 and m.user_id = $2. A stranger and a missing org both get no row, and no row is a 404. E8.2 adds one column to what that query already returns, the role, and puts it on the request context next to the org. Nothing about the caller's authorisation is fetched separately: the same read that says "you may see this org" says "as a viewer". Then each route declares the least role it needs.

/** Every guard `need` made, and the role it asks for: how app.test.ts finds a route that declares none. */
export const GUARDS = new WeakMap<object, Role>();
/**
 * E8.2 (F24): the route needs at least `role` in the org (the parent's middleware put the caller's role on the
 * context, from the same row that proved membership). A member without it gets 403: they may see the thing, so
 * "not found" would be a lie; a stranger never gets this far (404, F2). Every org and document route declares one:
 * app.test.ts fails for a route that does not, so a new route is closed until someone decides who may use it.
 */
const need = (role: Role) => {
  const guard = createMiddleware<{ Variables: { role: Role } }>(async (c, next) => {
    if (!includes(c.var.role, role)) return fail(c, 403, "forbidden");
    await next();
  });
  GUARDS.set(guard, role);
  return guard;
};

need is a middleware factory typed over the context variable role, so c.var.role is a Role, never any, and it records itself in a WeakMap keyed by the middleware function. That map is for one test, and the test is the important half of the design: default deny. A handler compiles perfectly well without a guard, and in Spring or Django a route that forgot its @PreAuthorize or its decorator is open until someone notices. Here app.test.ts walks app.routes, looks every org and document route up in the map, and compares the whole table to the one it expects. A new route without need shows up as undefined and the test is red until someone decides who may call it; a role changed without meaning to shows up too.

  /** `work` in one transaction, committed only when `keep` says so (rolled back otherwise, as on a throw). */
  async function inTx<T>(work: (client: PoolClient) => Promise<T>, keep: (result: T) => boolean = () => true, begin = "begin"): Promise<T> {
    const client = await pool.connect();
    let broken: Error | undefined;
    try {
      await client.query(begin);
      const result = await work(client);
      await client.query(keep(result) ? "commit" : "rollback");
      return result;
    } catch (err) {
      await client.query("rollback").catch(() => undefined);
      broken = err instanceof Error ? err : new Error(String(err));
      throw err;
    } finally {
      client.release(broken); // after a failure the connection's transaction state is unknown: destroyed
    }
  }
  /** `work` in one transaction that holds the advisory lock named `lock`: whatever else takes that lock waits its turn. */
  const inTurn = <T>(lock: string, work: (client: PoolClient) => Promise<T>): Promise<T> =>
    inTx(async (client) => {
      await client.query("select pg_advisory_xact_lock(hashtext($1))", [lock]);
      return work(client);
    });

setMember is the one place in the epic that needs a transaction rather than a statement, and the reason is a race the types cannot see. 4 · Roles in the room: read before the upgrade, re-read at the op's turn, and revocation that beats the token

REST is easy: every request reads the row. A WebSocket is the hard case, because it is authenticated once and then lives for hours, and F24 demands that a role change reach an open session within ten seconds. The sync server never trusts the token for what someone may do (section 3's case study), so it reads the role itself, from Postgres, at three moments: before the upgrade, when the token arrives; at the join, once the socket is registered; and on every announcement and every 30 seconds, for as long as the socket lives. The result of a read is one boolean on the peer, mayEdit, and the room checks it when an op's turn comes.

Now two reads are in flight for one socket and can return in either order; asked and applied number them, and an older answer that arrives after a newer one is dropped (asked < entry.applied). Without that, a revoke could be undone by a read that started before it: the race test in role-change.int holds the first read's answer, revokes, lets the announcement's read land, then releases the old one, and asserts the peer never joins. A read that fails is retried until Postgres answers or the socket goes: a demotion must not be lost to one dropped connection. And the git peer is never asked: it is the service itself, not a person.

The announcement is a hint. The api commits the change, then publishes { orgId, userId } on one Redis channel; every sync node re-reads the role of the live sessions that pair concerns. The message carries no role, on purpose: a forged or stale message can only cause a re-read, never grant anything. Pub/sub keeps nothing for a subscriber that was away, so a node whose connection comes back is told "all" and re-reads every live session. And because the api announces once, best effort (a ponytail E8.2 named), E8.3 found that a revoke could stay open for good if Redis was away at the api when it happened; the fix is a sweep: every node re-reads all its live sessions every 30 seconds, never two sweeps at once. REST is never behind, because it reads the row per request; only the sockets need the push.

/**
 * A sync node's half. `onChange` hears every change, and "all" each time the connection is (re)established, the
 * first time included. ioredis reconnects for ever and subscribes again by itself; with Redis away at startup the
 * SUBSCRIBE waits in its offline queue. `subscribed` resolves once Redis has it (tests wait for it).
 * ponytail: "all" fires as the connection is ready, as the SUBSCRIBE is sent, not once Redis confirmed it; ceiling:
 * a change published in that round trip, after the re-read began, is missed; upgrade: re-read on the subscribe reply.
 */
export function accessSubscriber({ redisUrl, prefix = "", onChange }: { redisUrl: string; prefix?: string; onChange: (change: AccessChange | "all") => void }): { subscribed: Promise<void>; close(): Promise<void> } {
  const redis = new Redis(redisUrl);
  redis.on("error", (err: unknown) => { warn(err instanceof Error ? err.message || err.name : "unknown"); });
  const channel = channelOf(prefix);
  redis.on("message", (from: string, text: string) => {
    if (from !== channel) return;
    let parsed;
    try {
      parsed = AccessChange.safeParse(JSON.parse(text));
    } catch {
      parsed = undefined;
    }
    if (parsed?.success) onChange(parsed.data);
    else warn("an access change that is not one was ignored");
  });
  redis.on("ready", () => { onChange("all"); });
  const subscribed = redis.subscribe(channel).then(() => undefined);
  subscribed.catch(() => undefined); // closed before it connected: nothing to report
  return {
    subscribed,
    async close() {
      await redis.quit().catch(() => { redis.disconnect(); });
    },
  };
}

Polling the role from the room was rejected: the E1.5 review asked for push.

A read of the role every few seconds per live session would meet the ten-second budget and needs no Redis. Case study · found by review, by a learning test, or by a test that was written to refute a claim

A revocation epoch in the token was rejected.

The textbook answer to "a token outlives a revoke" is a counter in the token that the server bumps on revoke, so an older token fails a comparison. It needs the server to store the counter per user, which is a deny list by another name, and it does nothing for the live socket, which outlives every token anyway. Reading the row before the upgrade and re-reading it on the socket answers both cases with one mechanism.

Revocation must beat every lifetime you hand out. There are three here. The sign-in cookie (7 days): a row, so revocation is a DELETE and the next request fails. The sync token (60 s): the row is read before the upgrade, so its lifetime never matters. The socket (hours): the role is re-read on every announcement and every 30 seconds, and the room checks the result at each op's turn. A design that leaves any one of the three to "wait it out" has a window exactly that long, and F25's test asks for all three to be shut at once.

5 · The audit trail: written by the action, and the database refuses to change it

An audit trail has three properties or it is a log. It is complete: an action that happened has a row, and an action that did not happen has none. It is immutable: nobody who can write the trail can rewrite it, the application included. It is durable against deletion elsewhere: removing the org, the user or the document must not remove the record of what they did. Each property is enforced by the database rather than by the application, and the migration says how.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

Writing the audit row after the action returned was rejected.

The layered shape, await db.setMember(...); await audit.write(...), is what an AuditService looks like in most codebases. A crash, a timeout or a deploy between the two loses the row, and a rolled-back action can leave one, because the second write has no idea the first did not commit. The CTE and the shared transaction make both impossible, and the test for it ("a failed action leaves no audit row") refuses two actions and counts.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

Foreign keys on audit_log were rejected: the E1.2 finding, again.

Referential integrity is the reflex, and it is wrong for a trail: a cascade erases history when the thing it is about is deleted, and set null is an UPDATE the table refuses. The test deletes an org and its users and asserts the rows are unchanged, including the actor's id and email as they were.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

Per-row checks in the application were rejected: the app role could still UPDATE.

A repository method that only ever inserts is a promise the code makes about itself; the app role's privileges are a fact about what any code running as it can do, including a bug, a migration script or a stolen connection string. Revoking the privilege makes the promise checkable: has_table_privilege answers it, and the test asks.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

One global sign-in row was rejected: one per org.

A sign-in belongs to a person, not to an org, so one row seemed natural. But the trail is read per org, by its owners, and an org must see its members' sign-ins without seeing that a member also belongs elsewhere. The statement joins memberships and writes one row per org; a user in no org signs in unrecorded, which the test spells out.

The principle: an audit trail is a claim about the past that the present must not be able to edit. Making it in the same statement as the action gives completeness; taking the privilege away from the writer gives immutability against the application; the trigger gives it against everyone else who connects; copying values in and refusing foreign keys gives durability. Envers and simple-history give you the first for free and none of the others unless you do the database's part yourself.

What is deliberately simple. Sessions are checked with one indexed read and no cache: a cache would make revocation a two-place problem, and one read is cheap. Roles are three, nested, per org: a role hierarchy is a total order, which is why includes is one comparison; the moment two roles are incomparable ("billing" and "editor"), the design becomes permissions, not roles, and the route table becomes a matrix. Authentication is a password: no OAuth, no email, no second factor, because the spec calls them non-goals and each is a large surface of its own.

What is not solved. There is no email flow, so sign-up must say when an email is taken, there is no password reset, and a member is added by an email that must already have signed up. The rate limiter behind allowAttempt is E9.6's and allows everything today, so an online guesser pays only scrypt's price per try. The api announces a change once, best effort, and the sweep covers the gap at 30 seconds. The sync server reads the role twice per connect, at the upgrade and at the join. There is no member list, no removal from an org (a demotion to viewer is the nearest thing), and no sharing screen: shares are made through the api. A rejected push is attributed to git and its commit, not to the engineer who pushed. Expired sessions are swept at their owner's next sign-in only. Every one of these is named where it lives, with its ceiling and its upgrade.

The interview answer in one breath: scrypt with self-describing parameters and a dummy hash so sign-in costs the same for everyone; an opaque session token kept as its SHA-256 in a row, in an HttpOnly, Secure, SameSite=Strict cookie, revoked by a DELETE; a 60-second HS256 token between the api and the sync node, with the role deliberately not in it; the role read from the row that proves membership, declared per route and checked by a test over the router; the room reading the role before the upgrade, at the join and on every announcement, and checking it at each op's turn; and an audit trail written by the action's own statement in a table the app role cannot change and a trigger defends against everyone else.

export function useApiProcess(): (env: Record<string, string>) => Promise<{ url: string; stderr: () => string }> {
  const main = new URL("./main.ts", import.meta.url).pathname;
  let child: ChildProcess | undefined;
  afterEach(() => child?.kill("SIGKILL"));
  return async (env) => {
    const port = String(20000 + Math.floor(Math.random() * 20000));
    let stderr = "";
    child = spawn(process.execPath, [main], { env: { PATH: process.env["PATH"] ?? "", DATABASE_URL: TEST_DATABASE_URL, PORT: port, SESSION_TOKEN_SECRET: "m".repeat(32), SYNC_PUBLIC_URL: "ws://localhost:3001", REDIS_URL: "redis://localhost:6380", ...env } });

1. The browser's session is 32 random bytes in a row, kept as a SHA-256; the password is kept as scrypt; the sync token is a signed JWT with no role in it. Defend each choice against the obvious alternative (a JWT for the browser, scrypt for the token, a role claim in the sync token), and say what one property decides the first.

Revocation decides the first. A signed stateless token is valid until it expires wherever it is; signing out would delete the browser's copy only, and a stolen copy or another tab keeps working until exp. Revoking early needs a server-side list checked on every request, which is a session table with worse ergonomics, so the browser gets the row from the start and sign-out is a DELETE that kills the token on its next request. The hash is chosen by entropy: a password can be guessed, so it gets a KDF that is slow and memory-hard (scrypt, 32 MiB per guess, its parameters in the string so they can rise); the token is 256 random bits that cannot be guessed at any speed, so one fast SHA-256 is right, and its only job is that a leaked table hands nobody a live session; a KDF there would cost tens of milliseconds on every request for nothing. The sync token stays a JWT because its stateless property is the point (the api signs, the sync node verifies, they never call each other) and its lifetime is 60 seconds, which is the only revocation a signature allows; the role is not in it because a token is checked once at connect and the socket then lives for hours, so a role claim is stale the moment an owner changes anything. The sync server reads the role itself, at the moments section 4 names.

2. The api reads the role from the same row that proves membership and declares a role per route; the sync server reads the role before the upgrade, at the join, on every announcement and every 30 seconds, and the room checks mayEdit at the op's turn. Why each of those, and why did E8.3 have to move the first read to before the upgrade when the token only lives 60 seconds?

Authorise where you fetch: the membership query already returns the row, and the role is a column of it, so one read answers both "may you see this" (404 for a stranger, F2) and "as what" (403 for a member without the role). Declaring the role per route with need makes the requirement visible, and the test that walks app.routes makes a forgotten guard a red test instead of an open route, which is the failure mode of every handler-level scheme. The socket is the hard case because it is authenticated once and lives for hours: the role must be re-read where the socket lives. The join read sets mayEdit; the announcement (a Redis hint that names who changed and never the role, so a forged message can only cause a re-read) makes the node re-read the sessions it concerns within F24's ten seconds; the 30-second sweep covers an announcement the api could not publish; and the room checks the flag at the head of its queue so that an op queued before a demotion is refused too. The upgrade read exists because a revoked outsider's client holds a token that is validly signed for up to 60 more seconds; admitting on the signature and closing at the join would open a socket that should never exist and let a reconnecting client reopen one for a minute. Reading the row while the request is still HTTP makes that token a plain 401, and the socket's lifetime, the token's lifetime and the cookie's lifetime are all beaten by the same fact: the row is read at the moment of asking.

3. The audit row is inserted in a CTE of the action's own statement, or in its transaction; the table has no foreign keys; provisionAppRole revokes UPDATE, DELETE and TRUNCATE on every deploy; and a trigger refuses them to everyone. Why each, and why are both the revoke and the trigger needed?

Same statement or transaction, for completeness in both directions: an action cannot commit without its row (a crash between two separate writes would lose it), and a row cannot outlive an action that rolled back (a refused last_owner, a run that hit run_in_progress, a share of nobody write nothing). No foreign keys, for durability: on delete cascade from orgs would erase the trail exactly when someone wants to read it, and on delete set null from users is an UPDATE the trigger refuses, so the email is copied in and a row may name things that no longer exist. The revoke, for immutability against the application: the app role gets a blanket grant plus default privileges for new tables, so audit_log would be writable unless the three privileges are taken away after the grant, and doing it on every provisioning means a grant made by hand is gone after the next deploy; has_table_privilege answers whether it worked. The trigger, for immutability against everyone the grants do not bind: the table's owner (grants never restrict an owner) and any role widened between deploys. The app role cannot disable it because it owns nothing, so alter table is refused. Either layer alone leaves a path: grants alone let the owner edit; the trigger alone could be disabled by a role that owned the table. Together, the only way to change the trail is to be a superuser, which nothing in the stack connects as.

The stored string names N, r and p, so the cost can rise without a migration; Django and Spring's DelegatingPasswordEncoder store hashes the same way.

The sync token stays a JWT because the api and the sync node never call each other, and its 60-second life is its revocation; section 4 is about the one case where 60 s was too long.
