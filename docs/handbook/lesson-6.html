The map: what durability means here

Epics 2 to 5 built a room that orders every edit and three kinds of peer that write through it. None of it survived a crash: F8 saved the document when a room went idle, and a sync process killed mid-edit lost everything since. Epic 6 makes one promise and keeps it under two faults. The promise (F18): no acknowledged edit is ever lost, and no edit is ever applied twice. The faults: the sync process dies (kill -9, no goodbye), and the database goes away (stopped, or paused so that every query hangs). A third feature (F19) makes the promise affordable: a document with ten thousand journaled edits still opens in under two seconds.

Four ideas carry the epic. A write-ahead log (section 1): the op is written to a place that survives the process before the process tells anyone, so the acknowledgement a peer sees is a fact about the database, not about memory. At-least-once plus an idempotent resend is exactly-once (section 2): a client that never heard its answer sends the same op again with the same id, and the journal's unique key turns the second sending into the first answer. Fail visibly, recover from the log (section 3): when the log cannot be written the room stops acknowledging and says so; when it can, the room reads what landed without it before it writes again. A snapshot is a cache of the log (section 4): losing one loses nothing, so it is written best-effort and never retried, and the pointer to it is written only after the object exists.

1 · The journal: durable before anyone hears of it

The room already had a persist step between validating an op and applying it (lesson 2 awaited it so that ordering under a slow database could be tested). Epic 6 gives that step a table and a contract, and the room's whole promise follows from where the step sits: an op is written to op_journal, and only if the write succeeds is it applied to the in-memory document, remembered, and broadcast. The sender's own copy of the broadcast is its acknowledgement. So an acknowledged op is, by construction, a row that survives the process.

From packages/db/migrations/0012_op_journal.sql

-- E6.1a (F18): every op the room accepted, written BEFORE anyone hears of it. Append-only: rows are never
-- updated. Two unique keys, told apart by NAME when an insert breaks one (learning-tests/postgres):
--   op_journal_seq: one op per number. Broken = a second writer is numbering this document: refuse.
--   op_journal_op:  one row per sender's opId. Broken = a resend the room had forgotten: answer with the
--                   original row. Keyed by the SENDER, as the room's own memory is: every broadcast shows
--                   every opId to every peer, so another peer's opId is not a resend.
create table op_journal (
  document_id uuid not null,
  org_id      uuid not null,
  seq         bigint not null check (seq >= 1),
  op_id       uuid not null,
  actor_kind  text not null check (actor_kind in ('user', 'agent', 'git')),
  actor_id    text not null check (length(actor_id) between 1 and 200),
  run_id      text check (length(run_id) between 1 and 200),
  op          jsonb not null,
  created_at  timestamptz not null default now(),
  constraint op_journal_seq primary key (document_id, seq),
  constraint op_journal_op unique (document_id, actor_id, op_id),
  foreign key (document_id, org_id) references documents (id, org_id) on delete cascade
);
-- Keystone 4: a node id that was ever added is never added again. The room asks this before each add.
create index op_journal_added on op_journal (document_id, (op ->> 'nodeId')) where op ->> 'type' = 'add_node';

Read the two constraints as two different facts. op_journal_seq on (document_id, seq) says one op per number: if an insert breaks it, someone else is numbering this document, which must never happen with one room per document, and the right answer is to refuse and stop writing. op_journal_op on (document_id, actor_id, op_id) says one row per sender's opId: if an insert breaks it, the room forgot a resend, and the right answer is the original row. Same SQLSTATE (23505, unique violation) for both, so the code cannot tell them apart by code: it reads the constraint name the driver exposes (learning-tests/postgres, finding 1).

      async append(orgId, documentId, { seq, opId, actor, op }, claim) {
        if (!isId(orgId) || !isId(documentId)) throw new Error("journal: not a document id");
        try {
          // From the document's row, so that a document of another org (or one deleted meanwhile) takes no op.
          // The fence is in the same statement (F22): the row must still name this room's claim, and FOR UPDATE
          // locks it, so a claim either waits for this insert (and its reader sees the row) or comes first (and
          // Postgres re-checks the WHERE against the claimed row: nothing is inserted). Never read-then-write.
          const written = await pool.query(
            `insert into op_journal (document_id, org_id, ${JOURNAL_COLUMNS}) select id, org_id, $3, $4, $5, $6, $7, $8 from documents where org_id = $1 and id = $2 and fence_claim is not distinct from $9 for update`,
            [orgId, documentId, seq, opId, actor.kind, actor.id, actor.runId ?? null, JSON.stringify(op), claim ?? null],
          );
          if (written.rowCount !== 1) {
            // Only telling the two refusals apart, after the fact: nothing was written either way.
            const exists = await pool.query("select 1 from documents where org_id = $1 and id = $2", [orgId, documentId]);
            throw exists.rowCount === 1 ? new Fenced("journal: fenced, a newer owner claimed the document") : new Error("journal: the document is gone");
          }
          return undefined;
        } catch (err) {
          // Two unique keys, told apart by NAME: 23505 alone cannot say whether this is a resend or a rival writer.
          if (err instanceof Error && "constraint" in err && err.constraint === "op_journal_op") {
            const original = await one(JournalRow, `select ${JOURNAL_COLUMNS} from op_journal where document_id = $1 and actor_id = $2 and op_id = $3`, [documentId, actor.id, opId]);
            if (original) return original;
          }
          throw err;
        }
      },

Three TypeScript things in that append. insert ... select ... from documents where org_id = $1 and id = $2 is lesson 1's tenancy rule applied to the journal: the row is written from the document's row, so a document of another org (or one deleted meanwhile) takes no op; rowCount !== 1 is the tell. "constraint" in err is the in operator used as a type guard: err is unknown in a catch, instanceof Error narrows it to Error, and "constraint" in err narrows it further to Error & Record<"constraint", unknown>, so the comparison compiles without a cast. Java would catch PSQLException and read getServerErrorMessage().getConstraint(); psycopg gives err.diag.constraint_name. The row type is a Zod schema with a .transform: seq is a bigint in Postgres and the driver hands it over as a string (the same finding lesson 3 hit for usage counts), so JournalRow converts once, at the edge, and the rest of the process sees a number.

  /** An op the journal holds and the room does not yet: applied, remembered and announced like a fresh one. */
  function accept(sequenced: SequencedOp): void {
    applyOpInto(doc, sequenced.op);
    seq = sequenced.seq;
    nodeCount = sequenced.op.type === "add_node" ? nodeCount + 1 : sequenced.op.type === "remove_node" ? Object.keys(doc.nodes).length : nodeCount;

    onAccepted?.(seq);

Read step 3 slowly, because the whole epic is in its order. sequenced is built with seq + 1, but seq itself is not moved: the number is only taken inside accept, after the append resolved. A failed write therefore leaves no gap, and the next op gets the same number. journal?.append(sequenced) is optional chaining on a call: with no journal it evaluates to undefined and the await is a no-op. let original; with no type and no initialiser is not any: TypeScript infers its type from the assignments it can see (an "evolving" let), so after the try it is SequencedOp | undefined. And accept is the one function that applies, numbers, remembers and announces, so that recover() in section 3 can do exactly what a fresh op does, to a row it found in the journal.

The append happens inside the room's one-at-a-time queue. That is what makes the journal's order the broadcast order under concurrent submits: op 2 is not even validated until op 1's append has resolved. It costs one database round trip per op on the critical path (about a millisecond on the same machine, tens over a network), which is the price of the promise; batching appends is the named upgrade, and it would move the acknowledgement, not remove the rule.

E2.3's known limit: a client that resent its own forgotten op with a forged baseSeq got a second seq.

Lesson 2 named it and could not fix it: the room's memory of applied ops is bounded, and once an op fell out of it a resend looked like a new op. The room's stale guard (baseSeq < forgottenUpTo) caught honest clients, but a client claiming to have seen everything walked past it. The journal's unique key is the fix, and it is free: the append that would have created the duplicate breaks op_journal_op, the original row comes back, and the room answers with it and applies nothing. The test pushes an op out of a two-entry memory and resends it with baseSeq = room.seq.

Case study · found by review, by a learning test, or by a test that was written to refute a claim

A key on (document, opId) would have refused legitimate ops.

The obvious dedupe key is the opId. But every broadcast shows every opId to every peer, so a peer that saw another's opId could send it as its own, and, more to the point, a bare-opId key would treat that as a resend and answer with the other peer's op. Lesson 2's memory was already keyed by sender for this reason; the journal's constraint is keyed the same way, and the database test proves that two senders may use one opId and both are written.

The principle: an acknowledgement is a promise about the future ("this will still be true after a crash"), so it may only be given by the thing that will still be there after the crash. The room gives it after the database has spoken, never before. Section 8's first row is what happens when the order is reversed, and drill 2 makes you find it.

2 · Exactly once, again: the resend, the forgotten op, and the id that never returns

Lesson 2 already had exactly-once over a lying connection: a client keeps its opIds, resends what was not answered, and the room answers a resend from memory. Epic 6 removes the word "memory" from that sentence. With a journal, every question the room used to answer from a bounded map can be answered from a table, including after a restart.

    //    the original answer; validating first would turn an ordinary retry into "duplicate_node".

    // Without a journal the room cannot tell, and applying it twice would move a node twice: resync.
    // A client that forged a high baseSeq (buggy or lying) skips that check, so every refusal below,
    // and the no-op ack, asks the journal first too: a resend gets its first answer, whatever it claims to
    // have seen (noon-mo3.1.1). Asked at most once per op, and only on those rare paths.
    let asked = false;
    /** True when the op has been answered: with its original row, or "unavailable". */
    const answeredFromJournal = async (): Promise<boolean> => {
      if (!journal || asked) return false;
      asked = true;
      let original;
      try {
        original = await journal.find(peer.actor.id, opId);
      } catch {
        refuse("unavailable");
        return true;
      }
      if (original) peer.send({ type: "op", ...original });
      return original !== undefined;
    };
    if (baseSeq < forgottenUpTo) {
      if (!journal) {
        refuse("stale");
        return;
      }
      if (await answeredFromJournal()) return;
    }

The dedupe is a two-level cache. The Map answers most resends in memory. An op whose baseSeq is behind everything the room remembers used to be refused as stale ("I cannot tell whether I applied this"); now the journal is asked with find: found, the original answer; not found, the op is judged now like any other. The stale path is kept for a room without a journal, so the simulator and lesson 2's tests still hold. Note the shape of the error handling: a journal that cannot be read refuses the op as unavailable, the same reason as a failed write, because in both cases the room does not know and must not guess.

    /**
     * Leaves read-only if the journal answers again. It first REPLAYS whatever the journal holds past the
     * room's seq (an append whose reply was lost, or a rival's row) and announces it, then tells every peer
     * "writable": a held op that did land is thus confirmed before its sender sends it again. Takes its turn
     * in the op queue, so no op is judged halfway through. True = writable. Never rejects.
     */
    recover(): Promise<boolean> {
      const done = tail.then(async () => {
        if (!readOnly || !journal) return true;
        let missed;
        try {
          missed = await journal.since(seq);
        } catch {
          return false;
        }
        for (const row of missed) accept(row);
        readOnly = false;
        broadcast({ type: "status", readOnly: false });
        return true;
      });
      tail = done.then(() => undefined, () => undefined);
      return done.catch(() => false);
    },

recover() is the design decision of the bead. The obvious version is a health probe: ping the database, and if it answers, say "writable". It was rejected for two failures it would cause. First, an append can land and still throw (the connection dropped after the commit): the room refused the op, the client holds it, and if the room goes writable without reading, the client's resend hits op_journal_op, gets the original row, and the room applies it, which is fine, but every other peer never heard the op, because the original broadcast never happened. Second, a rival row at the room's next seq (section 1's other constraint) would keep the room refusing until a restart. So recover() first replays since(seq) through accept, the same function a fresh op goes through, and only then says writable. It takes its turn in the queue, so no op is judged halfway through a replay.

Two idioms. tail = done.then(() => undefined, () => undefined) puts the recovery on the queue and makes sure a failure in it cannot jam the queue for every later op (then with two arguments handles both outcomes). return done.catch(() => false) gives the caller a boolean that never rejects. The room has no clock, so it cannot retry by itself; onReadOnly tells the server to start.

  function bounded<T>(work: Promise<T>, what = "journal"): Promise<T> {
    let timer: NodeJS.Timeout | undefined;
    const late = new Promise<never>((_, reject) => { timer = setTimeout(() => { reject(new Error(`${what} timed out`)); }, journalTimeoutMs); });
    return Promise.race([work, late]).finally(() => { clearTimeout(timer); });
  }

  /**
   * The room went read-only (E6.1b): ask it to recover every `recoverMs` until the journal answers.
   * ponytail: a read-only room that was dropped meanwhile keeps asking too, one cheap read a tick, until
   * the database is back; ceiling: one timer per such room, for as long as the outage lasts.
   */
  function heal(room: Room): void {
    void (async () => {
      while (room.readOnly && !closing) {
        await new Promise((resolve) => setTimeout(resolve, recoverMs).unref());
        await room.recover();
      }
    })();
  }

bounded is the timeout: Promise.race between the work and a timer that rejects, with finally clearing the timer so a fast answer does not leave one ticking. A paused database (the second half of the chaos check) never refuses a query; it hangs, and without this the room would wait for ever with every peer's ops queued behind it. Note what the timeout means: "treat as failed", not "it failed": the append may still land later, which is exactly why recover() reads before it writes. heal is an async IIFE (void (async () => { ... })()) that loops with a setTimeout promise whose timer is unref()'d so it cannot keep the process alive at shutdown.

A push during a database outage must therefore not end at all: WaitAgain puts the event back to pending, and the next poll tick tries the whole event again. The ceiling is named (pages already applied are diffed again against the room as it is then, which is a no-op) and the alternative (a per-page cursor on the event) is the upgrade.

The distributed-systems shape: a single writer that stops writing the moment it cannot confirm a write; clients that keep their intent and re-offer it under the same identity; and a recovery that reconciles the writer with the log before it accepts anything new. Every piece is visible on a screen ("read-only", "waiting to save 1"), because a failure nobody can see is a failure nobody can act on.

4 · Snapshots: a cache of the log, written once, named after it exists

With a journal, a document is fully defined by its rows: replay them from an empty page and you have it. That is correct and slow, and it grows without bound. F19 caps the cost: a room writes its whole document to MinIO every 500 accepted ops, every 30 seconds while anyone is connected, and when its last peer leaves or the server stops; opening a document loads the newest snapshot and replays only the rows after it. The journal stays the truth. A snapshot that fails to write loses nothing; it only leaves more rows for the next open.

export function snapshotKey(orgId: string, documentId: string, seq: number): string {

  return `${orgId}/${documentId}/${String(seq).padStart(16, "0")}.json.gz`;
}

/** Gzipped by hand: the SDK neither compresses nor decompresses (learning-tests/minio). */
export const encodeSnapshot = (doc: Doc): Uint8Array => gzipSync(JSON.stringify(doc));

/** The document, or undefined when the bytes are not a well-formed tree: a room must never open on top of that. */
export function decodeSnapshot(bytes: Uint8Array): Doc | undefined {
  let parsed;
  try {
    parsed = Doc.safeParse(JSON.parse(gunzipSync(bytes).toString("utf8")));
  } catch {
    return undefined;
  }
  return parsed.success && checkDoc(parsed.data).length === 0 ? parsed.data : undefined;
}

/**
 * When a room snapshots (SPEC §2.9): every `everyOps` accepted ops, every `everyMs` while peers are connected
 * (a session that is never idle still snapshots), and when asked (the last peer left, the server stops).
 * One write at a time; a trigger during a write is dropped, and the next op or tick catches up.
 */
export function snapshotter({ room, from, cadence, write }: { room: Source; from: number; cadence: SnapshotCadence; write: (seq: number, body: Uint8Array) => Promise<void> }) {
  let saved = from;
  // The newest seq a write was ATTEMPTED at (never behind `saved`). While MinIO is away `saved` stays put, and an op-triggered retry on every
  // op past the threshold was a gzip, a failing PUT and a log line per op (noon-mo3.3.3); the timer still retries.
  let attempted = from;
  let writing: Promise<unknown> | undefined;

  /** Snapshots the room as it is now, if it moved since the last one. True: stored (or nothing to store). Never rejects. */
  async function take(): Promise<boolean> {
    while (writing) await writing;
    const seq = room.seq;
    if (seq <= saved) return true;
    // Read in the same tick as `seq`: the room edits `doc` in place, and only here is it exactly the document at `seq`.
    attempted = Math.max(attempted, seq);
    const work = write(seq, encodeSnapshot(room.doc)).then(() => { saved = Math.max(saved, seq); return true; }, () => false);
    writing = work.finally(() => { writing = undefined; });
    return work;
  }

  const timer = setInterval(() => { if (room.peerCount > 0 && !writing) void take(); }, cadence.everyMs);
  timer.unref();
  return {
    get saved() { return saved; },
    /** The room accepted an op numbered `seq`. */
    accepted(seq: number): void {
      if (!writing && seq - attempted >= cadence.everyOps) void take();
    },
    take,
    stop(): void { clearInterval(timer); },
  };
}

The cadence is a pure module fed by the room's onAccepted hook and a timer. while (writing) await writing; is "wait for any write in flight": a plain loop over a promise field, the same one-at-a-time idea lesson 5 wrote as a promise chain. The comment marked Read in the same tick as seq is the correctness heart: the room edits doc in place, so the document is exactly the document at seq only until the next await. encodeSnapshot(room.doc) is called synchronously, before write is awaited. Move it after an await and a snapshot named seq could hold seq+3's document.

// proved nothing, and says so.

From scripts/chaos/no-loss.ts

export function createLedger() {
  const entries: LedgerEntry[] = [];
  const settling: Promise<unknown>[] = [];
  let faulted = false;
  return {
    entries: entries as readonly LedgerEntry[],
    track(peer: string, submitted: Submitted): void {
      if (!submitted.ok) return;
      const entry: LedgerEntry = { peer, opId: submitted.opId, atFault: faulted ? "after" : "unsettled", outcome: "unsettled" };
      entries.push(entry);
      settling.push(submitted.settled.then((outcome) => { entry.outcome = outcome; }));
    },
    /** Call right after the fault is opened: what has settled by now counts as "before the fault". */
    fault(): void {
      faulted = true;
      for (const entry of entries) if (entry.atFault === "unsettled") entry.atFault = entry.outcome;
    },
    /** Wait for every op to settle, at most `timeoutMs`; whatever has not by then stays "unsettled" (lost). */
    async settle(timeoutMs: number): Promise<void> {
      let timer: NodeJS.Timeout | undefined;
      await Promise.race([Promise.all(settling), new Promise((resolve) => { timer = setTimeout(resolve, timeoutMs); })]);
      clearTimeout(timer);
    },
  };
}

/** Every broken guarantee, in words; empty = PASS. `docs`: each peer's confirmed document, serialized. */
export function noLossViolations({ ledger, journal, docs }: { ledger: readonly LedgerEntry[]; journal: readonly JournalRow[]; docs: readonly string[] }): string[] {
  const violations: string[] = [];
  if (!ledger.some((e) => typeof e.atFault === "object" && e.atFault.ok && e.atFault.seq !== undefined)) violations.push("vacuous: no op was acknowledged before the fault");
  if (!ledger.some((e) => e.atFault === "unsettled")) violations.push("vacuous: no op was in flight at the fault, so nothing was resent");

  const seqs = journal.map((row) => row.seq);
  if (seqs.some((seq, i) => seq !== i + 1)) violations.push(`the journal's seqs are ${seqs.join(",")}, not 1..${String(seqs.length)} without a gap or repeat`);
  const seqsOf = new Map<string, number[]>();
  for (const row of journal) seqsOf.set(row.opId, [...(seqsOf.get(row.opId) ?? []), row.seq]);
  for (const [opId, at] of seqsOf) if (at.length > 1) violations.push(`op ${opId} is journaled ${String(at.length)} times (seq ${at.join(", ")})`);
  const tracked = new Set(ledger.map((e) => e.opId));
  for (const row of journal) if (!tracked.has(row.opId)) violations.push(`journal seq ${String(row.seq)} holds op ${row.opId}, which no tracked peer submitted`);

  const bySeq = new Map(journal.map((row) => [row.seq, row.opId]));
  for (const e of ledger) {
    const refusedBefore = typeof e.atFault === "object" && !e.atFault.ok;
    const what = `${e.peer} op ${e.opId}${refusedBefore ? "" : e.atFault === "unsettled" ? " (in flight at the fault)" : e.atFault === "after" ? " (made after the fault)" : " (acknowledged before the fault)"}`;
    if (e.outcome === "unsettled") violations.push(`${what} never settled: lost`);
    else if (!e.outcome.ok) {
      if (!refusedBefore) violations.push(`${what} was refused (${e.outcome.reason}): lost`);
      else if (seqsOf.has(e.opId)) violations.push(`${what} was refused (${e.outcome.reason}) but is journaled`);
    } else if (e.outcome.seq !== undefined && bySeq.get(e.outcome.seq) !== e.opId) {
      violations.push(`${what} was acknowledged at seq ${String(e.outcome.seq)}, but the journal has ${bySeq.get(e.outcome.seq) ?? "nothing"} there`);
    }
  }

  docs.forEach((doc, i) => { if (doc !== docs[0]) violations.push(`peer ${String(i)}'s confirmed document differs from peer 0's`); });
  return violations;
}

This is what "no loss" means precisely, and it is worth saying in words, because an interviewer will ask. An op acknowledged before the fault must be in the journal at exactly the seq it was acknowledged with. An op in flight at the fault (sent, unanswered) or made while the server was gone must settle ok and appear exactly once. Nothing may be refused for a reason the run did not cause, and nothing refused before the fault may be in the journal. The journal's seqs are 1..n with no gap or repeat, no opId appears twice, and every row belongs to a tracked peer. And every peer's confirmed document is byte-identical. Then two vacuity guards: a run in which nothing was acknowledged before the fault, or nothing was in flight at it, proved nothing, and says so as a violation. SPEC §4a's rule, "every always has a sometimes", is that pair of lines.

The Outcome and Submitted types are copied from peer-client's public shape rather than imported, so the module depends on nothing. ledger.fault() is the one moment that matters: whatever has settled by then counts as "before", everything else is "in flight". settle(timeoutMs) is Promise.race between "every op settled" and a timer, with the timer cleared afterwards, so an op that never settles is left as "unsettled" and reported as lost rather than hanging the run.

async function round(n: number): Promise<{ round: number; ops: number; journaled: number; violations: string[] }> {
  const doc = idOf(await post(`/orgs/${org}/workspaces/${workspace}/documents`, { title: `chaos kill sync ${String(n)}` }));
  const session = async () => SessionResponse.parse(await post(`/documents/${doc}/session`));
  const peers = {
    person: connectPeer({ manifest, session }),
    // The api's address (the room's owner, E7.1) with the worker's kind of token: the AI routes as the worker does.
    ai: connectPeer({ manifest, session: async () => ({ wsUrl: (await session()).wsUrl, token: signSessionToken({ userId: me, orgId: org, documentId: doc, secret, ttlSeconds: 600, actor: { kind: "agent", runId: randomUUID() } }) }) }),
  };
  const all = Object.entries(peers);
  const ledger = createLedger();
  let made = 0;
  let victim = "sync";
  const edit = (count: number): void => {
    for (let i = 0; i < count; i++) for (const [name, peer] of all) ledger.track(name, peer.submit(add(`${name}-${String(made++)}`)));
  };
  try {
    await until(() => all.every(([, p]) => p.status === "live"), "both peers live", 15_000);
    edit(5);
    await ledger.settle(10_000); // acknowledged before the fault

    victim = ownerOf(doc);
    edit(20); // on the wire...
    compose("kill", "--signal", "SIGKILL", victim); // ...and the server dies under it. execFileSync: no ack is heard meanwhile.
    ledger.fault();
    await until(() => all.every(([, p]) => p.status !== "live"), "both peers see the server gone", 30_000);
    edit(5); // made while the server is gone: held, sent after the next welcome

    // Back at once: the peers land on it or on the other node (E7.2); either waits the dead lease out (LEASE_TTL_MS).
    compose("start", victim);
    await until(() => all.every(([, p]) => p.status === "live" && p.pendingCount === 0), "both peers reconnected unaided, nothing pending", 60_000);
    await ledger.settle(15_000);
    await until(() => all.every(([, p]) => p.seq === peers.person.seq), "both peers at the same seq", 10_000);

    const journal = psql(`select seq || ' ' || op_id from op_journal where document_id = '${doc}' order by seq`)
      .split("\n").filter(Boolean).map((line) => { const [seq, opId] = line.split(" "); return { seq: Number(seq), opId: opId ?? "" }; });
    const docs = all.map(([, p]) => JSON.stringify(p.confirmed));
    return { round: n, ops: ledger.entries.length, journaled: journal.length, violations: noLossViolations({ ledger: ledger.entries, journal, docs }) };
  } finally {
    for (const [, p] of all) p.close();
    compose("start", victim); // whatever failed above, the server comes back
  }
}

The kill is a synchronous docker compose kill --signal SIGKILL sync through execFileSync, called right after a burst of twenty edits per peer. Because the call blocks the event loop, no acknowledgement can be processed between the last submit and the kill: the burst is guaranteed in flight, and some of it is in the state the journal's dedupe exists for (journaled, acknowledgement never heard). The server is started again and the peers are left alone: F18 says they reconnect unaided, so the run waits on status === "live" && pendingCount === 0 and nothing else. Each round uses a fresh document and one fault (several kills on one ledger would blur "acknowledged before which fault"), and ROUNDS=3 repeats, because a one-shot pass proves nothing. finally starts sync again whatever happened.

/** A journal in memory with the table's two unique keys, outliving any room built on it: a stand-in for op_journal. */
function memoryJournal(): Journal & { rows: SequencedOp[] } {
  const rows: SequencedOp[] = [];
  const find = (actorId: string, opId: string) => rows.find((r) => r.actor.id === actorId && r.opId === opId);
  return {
    rows,
    append(op) {
      const original = find(op.actor.id, op.opId);
      if (original) return Promise.resolve(original);
      if (rows.some((r) => r.seq === op.seq)) return Promise.reject(new Error("op_journal_seq"));
      rows.push(op);
      return Promise.resolve(undefined);
    },
    find: (actorId, opId) => Promise.resolve(find(actorId, opId)),
    everAdded: (nodeId) => Promise.resolve(rows.some((r) => r.op.type === "add_node" && r.op.nodeId === nodeId)),
    since: (seq) => Promise.resolve(rows.filter((r) => r.seq > seq).sort((x, y) => x.seq - y.seq)),
  };
}

/** memoryJournal behind a switch: while `down`, every call rejects; `committedAnyway` makes the next append land AND reject (a lost reply). */
function flakyJournal() {
  const inner = memoryJournal();
  const state = { down: false, committedAnyway: false, appends: 0 };
  const guard = <A extends unknown[], R>(call: (...args: A) => Promise<R>) => (...args: A): Promise<R> => (state.down ? Promise.reject(new Error("db down")) : call(...args));
  const journal: Journal = {
    append: async (op) => {
      state.appends++;
      if (state.committedAnyway) {
        state.committedAnyway = false;
        await inner.append(op);
        throw new Error("connection lost after commit");
      }
      return guard((each: SequencedOp) => inner.append(each))(op);
    },
    find: guard((actorId: string, opId: string) => inner.find(actorId, opId)),
    everAdded: guard((nodeId: string) => inner.everAdded(nodeId)),
    since: guard((seq: number) => inner.since(seq)),
  };

}

D3 · Explain a decision before reading mine. Answer out loud or on paper, then open the answer.

1. The room could apply and broadcast an op, then journal it, and refuse it if the write fails. That is faster for the sender. Why is the acknowledgement given only after the append, and why is the sequence number taken only then?

Because an acknowledgement is a promise about the future: "after a crash this will still be true". Only the database can make that promise, so the room may only relay it after the database has spoken. Announce first and three things break at once. Every other peer applies an op that may not exist after a restart, so two tabs diverge from the truth. The sender's client marks the op confirmed and forgets it, so nothing will ever resend it: the op is lost while everyone saw it. And the room's seq has moved for a row that is not in the journal, so the next append's number is one ahead of the table, which is the room's own signal for a rival writer; under the reversed order it becomes a permanent read-only after the first failed write. Taking the number inside accept, after the append resolved, means a failed write leaves no gap and the next op simply gets the same number. The cost is one database round trip per op inside the room's queue, which is the price of the promise. Drill 2 plants the reverse order; its first assertion is peer B having received seq 2.

2. When the journal fails, the room could ping Postgres every second and say "writable" when it answers. Instead recover() reads since(seq) and replays it first. Why, and what exactly does "no acknowledged op is lost, none is applied twice" require of the client and the journal together?

Because "the database answers" and "the room agrees with the database" are different facts. A rejected append may have landed (the connection died after the commit) and a timed-out one may land later; a rival row may sit at the room's next seq. If the room goes writable without reading, the landed op is in the journal and in nobody's document, and the next append from anyone breaks op_journal_seq and puts the room back into read-only for ever. Replaying through accept applies and announces what landed, moves the room's seq past it, and only then says writable; the sender's held resend is then answered from memory with the seq it got. The promise needs three things. From the journal: a unique key on (document, sender, opId), and the original row returned when it is broken, so a second sending gets the first answer. From the client: keep the op under the same opId until it is answered, and re-offer it after every welcome and every "writable", in order. From the room: acknowledge only what is durable, refuse everything while it cannot write, and read the journal before it writes again. Remove any one and the promise is gone: no key, and a resend is applied twice; no held resend, and an in-flight op is lost; no replay, and a landed op is heard by nobody.

3. Snapshots are written to MinIO with IfNoneMatch: "*", and documents.snapshot_seq is updated only afterwards and only forwards. A failed snapshot is logged and never retried, and F8's idle save was deleted. Defend each of those four choices in one sentence, then say what a snapshot is.

A snapshot is a materialised prefix of the log, so everything follows from the journal being the truth. Conditional put: two rooms (or one room twice, after a crash) may reach the same seq, and the same journal prefix gives the same document, so the loser of the race loses nothing and a plain overwrite would only open a window where the object is half-written. Pointer after the object, forwards only: a crash between the two writes leaves an orphaned object (harmless) rather than a pointer to nothing (a document that cannot open), and a slow write of an older snapshot finishing late must not move the document backwards. Never retried: a snapshot that failed to write costs nothing but more rows to replay at the next open, so a retry loop would be complexity spent protecting a copy. F8 deleted: F8 had to retry for ever because the room's memory was the only copy of the edits since the last save; with the journal that is never true, and keeping two save paths means two truths. The key is zero-padded because S3 sorts strings, and the newest snapshot is found by the pointer rather than by listing because S3 lists ascending in pages of 1000, measured. What it is: a cache of the log that may be lost but must never be wrong, which is why the document is encoded in the same tick as its seq.
