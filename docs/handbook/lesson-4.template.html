Lesson 4 · Epic 4

The document becomes code, and the code runs

The win: you can explain, to an interviewer or to yourself, how a tree of nodes becomes one file whose bytes never surprise anyone, how one container per document is started exactly once even when ten callers ask at the same moment, why a child process needs an end from outside and what Node 24 does when you ask for one, how a page framed under an opaque origin is served and healed, and why a reaper must look before it asks; and you can point at the line of code for every claim.

How to use this page. Every code block is cut from the repo at commit {{COMMIT}}, so what you read is what runs. It is long: one section a day is a fine pace. Sections 1, 3, 4, 6 and 8 are the ones an architect interview will dig into.

./init.sh                                             # Postgres + Redis + api + sync + worker + worker-sandbox; builds noon-sandbox:dev
docker compose logs -f worker-sandbox                 # "worker draining queues: sandbox", then each preview job
pnpm exec vitest run apps/worker/src/sandbox.int.test.ts    # real Docker: starts, races, deadlines, the reaper
pnpm exec playwright test e2e/preview.spec.ts             # the canvas, the real sandbox worker, a container killed under it

Try it: open a document, press Show the running page, add a Button and type a label; it appears in the frame within a moment and the frame is not reloaded. Then docker rm --force noon-sandbox-<document id> and watch "Rebuilding the preview…" turn back into your page, on its own. Never run two Docker-using suites at once: each one's cleanup removes the other's containers.

D3 · Explain a decision before reading mine. Answer out loud or on paper, then open the answer.

1. Why does the worker choose the host port itself, once, from the document id, instead of letting Docker pick a free one? And if the port never changes, why must the canvas still re-read the URL?

Because Vite's client heals a lost connection only on the same origin: it polls the server it was loaded from and calls location.reload() when it answers again (measured in the sandbox learning test). Docker's own choice (-p 127.0.0.1::5173) is re-rolled on every docker start (measured: 49755, then 49767), so a restarted container would come back on a port nobody was watching. Choosing the port here and writing it into the container's configuration makes a restart land on the same origin. It is not a guarantee, only a preference: a stopped container does not hold its port, and if another document (or a host process) takes it meanwhile, docker start fails with "port taken" and the sandbox is recreated on the next candidate. That is why the URL is read after ready, from the container that answered, and why the canvas asks once a second instead of keeping the first answer. Epic 4.3 then added a second reason: inside the canvas's opaque-origin frame Vite cannot heal at all, so every start announces a distinct URL anyway. The stable port still matters for a tab opened on the preview directly.

2. Why does a worker process drain exactly one queue (WORKER_QUEUE=ai|sandbox), when the code can drain both and one process would be simpler to run?

Because of what each queue needs. The sandbox queue talks to the Docker daemon, and the daemon's socket is root on the host: whoever holds it can start any container with any mount. The AI queue runs a model's subprocess, whose input is other people's documents and prompts, under a capability ceiling that took a whole section of lesson 3 to build. Put both in one process and the ceiling is decoration: one escape from the subprocess, one bug in the SDK, and the model is holding the Docker socket. So the split is not about load, it is about blast radius: worker-sandbox is the only compose service with /var/run/docker.sock, and the AI worker never has it. The handler map being partial is what makes this cheap: a process drains only the queues it has handlers for, and a message for the other queue is left alone before any claim. Concurrency per queue falls out too: an AI run costs a model call, a sandbox job holds 1 CPU and 1 GiB for as long as a document is open, and neither should starve the other.

3. "One unfinished sandbox job per document" is a partial unique index. "At most four previews per org" is a count inside the INSERT, and its comment admits a small overshoot. Why are the two rules built differently?

Because they cost different things to get exactly right, and they cost different things to get wrong. One per document is a uniqueness rule, and Postgres has a primitive for exactly that: a unique index over a predicate. One statement, no window, and Postgres decides who was first; violating it is the concurrency check. At most four per org is a counting rule, and there is no index for "fewer than N rows match". Making it exact means serialising every open in an org (an advisory lock on the org, or SELECT ... FOR UPDATE on its row), which is a queue in front of every preview for the sake of a limit that exists to protect a shared pool, not to bill anyone. A count inside the same INSERT ... SELECT leaves a window the width of one statement: two opens in the same instant can both count three and both pass, so an org can hold five or six for a moment, never unbounded. The rule for the per-document index is that the wrong outcome (two containers fighting over one port and removing each other) is a bug; the wrong outcome for the cap is one container too many. The comment names the ceiling and the upgrade, which is what a ponytail shortcut owes the next reader.

Recall first

Look away. Name the three things that make "one starter per document" true, each at its own scope. Then name the two systems the reaper asks and the order it must ask them in, and why. Then check.

Check yourself

One starter: inside a process, startSandbox is single-flight (a Map of the attempt in flight per document, so ten callers share one); across processes, the partial unique index jobs_one_unfinished_sandbox_per_document means only the one process holding the document's unfinished sandbox job ever starts it; and Docker's container name is the document's, which stops two containers but, on its own, never stopped two starters from removing each other's. The reaper: it lists Docker first, then asks Postgres what is in use. The other way round, a job that starts a sandbox between the two answers is in the list and not in the answer, and its container is removed mid-start. Listing first means a listed container existed before the answer, so any job that made it is in the answer.

Then test it

Eight questions. Options are shuffled each visit.

1. A component name with a lying toString answered "Button" to the identifier check and code to the template. What is the fix?

A value converted twice can answer twice. The generator asks typeof and writes a literal from what the value IS, never from what the manifest says it is, so no toString is ever consulted.

2. Docker refuses a second container with the same name. Why did ten concurrent starts of one document still remove each other's containers?

Uniqueness is not ownership. "Taken" can mean taken by the winner. Fix: one starter per document, single-flight in-process and a unique job across processes.

3. A shell script starts with set -e and runs git init && git fetch && git checkout on one line. The fetch fails. What happens?

Measured: a failed clone went on to serve an empty app. One command per line, so each one is a statement set -e can see.

4. On Node 24 you pass execFile(cmd, args, { signal, killSignal: "SIGKILL" }) and abort the signal. What does the child receive?

So dockerCli listens for the abort itself and calls child.kill("SIGKILL"). The test stub traps TERM and proves the pid is gone.

5. Why is the AI worker kept from the sandbox queue by a separate process, rather than by a flag?

Blast radius, not load. worker-sandbox is the only compose service with the socket; the handler map is partial so a process drains only what it handles.

6. The reaper asks Postgres "which documents are in use?" and lists the containers with docker ps. Which order is safe, and why?

Ask-then-list lost a container to a job that started in between (found by the re-verify). reapSandboxes takes a function so the order is its own.

7. The canvas frames the preview with sandbox="allow-scripts" and no allow-same-origin. What did the dev server see, and what was done about it?

The E4.2a note said "lock cors to the canvas origin", which could never work: requests never come from the canvas origin. Measured, then fixed; the test checks the echoed header for "null", an evil origin and localhost.

8. After a container restart, why does the worker announce a URL with a fresh &started= even when the port is unchanged?

The iframe is keyed on the URL. A new address is a new page; the same address would have left a frame polling a server it can never rejoin.
